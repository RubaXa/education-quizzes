# Правила работы с education-quizzes

## Проверки и коммиты

- Используй Conventional Commits: например, `feat: add geometry questions` или `fix: reject empty numeric answers`. При squash merge назови pull request в том же формате, чтобы коммит в `main` тоже соответствовал правилу.
- После `npm install` установи хуки командой `npm run prepare`, если они не установились автоматически. Lefthook запускает линтер перед коммитом, commitlint проверяет сообщение коммита, а перед push выполняются линтер, тесты и сборка.
- Перед завершением работы запусти `npm run check`. Исправь ошибки проверок до коммита. Не обходи хуки ради ускорения обычной работы.
- Перед изменением существующего поведения зафиксируй его приемлемую часть характеризационными тестами и запусти их на исходном коде. Найденную ошибку отдельно воспроизведи падающим регрессионным тестом, затем исправь код и добейся зелёного прогона. Каждую находку привяжи к спецификации и проверке; не закрепляй ошибочное поведение как норму.
- Для запуска и чтения данных всегда разделяй тесты **холодного старта** (нет полного локального снимка) и **повторного старта** (есть проверенный снимок). Проверяй первый кадр, промежуточный локальный ответ Firestore, серверное подтверждение, сбой, восстановление и отзыв доступа там, где они применимы. Контракт сценариев — [local-first startup](docs/architecture/local-first-release-plan-2026-10-12.md#startup-regression-contract). Перед выпуском пройди оба режима и живой сценарий на опубликованной версии.

## Сквозная сверка каждого изменения

- Перед изменением назови факт и владельца в [модели данных](docs/product/firestore-data-model.md#ownership), вычисляемую ролевую проекцию в [продуктовом контракте](docs/product/dashboard.md#dashboard-scope) или соответствующем ViewModel и существующий компонент в [реестре](docs/product/component-system.md#registry). Для поля различай источник, производное значение, локальный выбор и серверную запись; не превращай вычисляемую дату или статус в новое поле Firestore без доказанной необходимости.
- Сверь реализацию с теми же правилами: путь публикации или чтения, совместимость старых документов, поведение при отсутствии данных и роли, интерактивность компонента, холодный и повторный запуск. Зафиксируй исходное допустимое поведение и ошибку тестами до правки; после неё проверь все затронутые границы и карту файлов. Новую сущность, компонент или подписку добавляй только после проверки, что действующие не выражают нужный смысл.
- Перед коммитом и выпуском повтори путь «источник → модель данных → ViewModel → компонент → тест → спецификация». Исправь расхождения в этом же ходе; если схема и данные не менялись, явно зафиксируй это в спецификации или отчёте. После выпуска сопоставь проверенную публичную сборку с исходниками и запиши оставшиеся ограничения; не объявляй визуальную проверку устройства выполненной по одним локальным тестам. [Обоснование разделения компонентов](docs/product/component-system.md#change-gates).

## Дизайн-система интерфейса

- Перед новым экраном или макетом прочитай [дизайн-систему Education](docs/product/design-system.md), действующий `Shell` в `src/App.tsx` и CSS затронутых компонентов. Текущая шапка, знак Education, колокольчик, шрифт, карточки и обозначения статусов — исходная система; не создавай параллельную шапку или произвольную палитру.
- Общие значения бери из `src/education-design-tokens.css`. Сохраняй `@see` на нужный раздел спецификации в React-компоненте и CSS. В макетах условных детей и числа помечай как примеры.
- Для главной взрослого выбран раскрывающийся список всех доступных детей: краткий статус и подтверждённый прогресс в каждой строке, предметы и действия при раскрытии, готовые предметы отдельно. Под ним — отдельные карточки управления семьёй, приглашениями и входом детей. Сверяй реализацию с [семейным контрактом](docs/architecture/family-data-model.md#parent-home); отсутствие опубликованных данных не подменяй вымышленными ссылками, нулями или действиями.

## Тесты по программированию

- Если вопрос спрашивает, что выведет или как выполнится программа, покажи полный нужный для ответа листинг рядом с вопросом, перед вариантами. Проверяй, что код реально виден в опубликованном предпросмотре, а не только сохранён в Firestore.
- Подсвечивай синтаксис, сохраняй строки и отступы. На узком экране длинная строка кода прокручивается внутри блока и не расширяет страницу.
- Формулируй варианты как осмысленные результаты программы. Перед выдачей ссылки проверь все вопросы, ключи и отображение каждого листинга в режиме предпросмотра.

## Разбор результатов всех онлайн-тестов

- После отправки для каждого неверного ответа показывай рядом данный и правильный ответы. Главный учебный блок: ясное правило или принцип, почему он применим к этому вопросу, точное место в учебнике или исходном тексте и прямое действие для повторения. Ссылку на материал добавляй, если есть проверенный публичный адрес; подписывай её по реальному назначению.
- Для каждого вопроса нового теста, включая открытый ответ с ручной проверкой, заполни `answer.learning` (`rule`, `why`, `textbook`, `nextStep`). `quiz create` отклоняет спецификацию без этих полей. Не используй условное «если хочешь повторить» вместо конкретного задания. Не выдумывай книгу, страницу или URL.
- Старые назначения не переписывай задним числом ради формата; их существующие объяснения показываются в обозначенных блоках. Текст обратной связи уже отправленной попытки исправляй без изменения ключа и баллов. При доказанной неоднозначности ключа используй отдельный [протокол исправления](../skills/online-quiz/references/question-quality.md): сохраняй исходный ключ и попытку, проверяй все затронутые результаты, документируй изменение оценивания и сверяй его в обеих ролях. Ответ ученика не редактируй.

## Карточки тестов в списках

- У каждого нового теста дай короткое содержательное `description`: о чём проверка и какой навык она затрагивает. Не заменяй описание числом вопросов: счётчик показывается отдельно.
- Заполни `board.materials` точными проверенными материалами (учебник, страницы, задания), `board.review` конкретными темами для повторения, `board.purpose` целью проверки. Ученический и родительский списки показывают описание одной строкой и раскрывают эти подробности по нажатию. Не выдумывай источник; собственные задания называй самостоятельно составленными.

## Реактивность и связанная диагностика

- Каждый выбор ученика отправляй в Firestore сразу, без таймера ожидания; быстрые записи упорядочивай, а завершение выполняй после них. Страницы теста и обоих списков должны получать изменения через `onSnapshot`, включая статус завершения и ручной разбор.
- Ученический список `#/my/…` не показывает оценок. Родительский `#/review/…` отдельно показывает новые результаты до просмотра. Когда родитель открывает результат или нажимает «Отметить просмотренным», сохраняй отметку в Firestore; просмотр ученического списка её не меняет.
- Кнопка копирования задания агенту доступна у завершённого теста. Инструкция должна ссылаться на конкретную попытку, требовать анализа ошибок и сильных ответов, связанных новых вопросов с адресным повторением и переносом, без дословного повтора или чрезмерного зацикливания на одной проблеме.

## Публикация

- Генерируй новый день в два состояния по [контракту плана](docs/product/plan-generation.md#raw-mesh-stage): сперва точная запись МЭШ с `needs-review` без придуманных шагов и фото, затем подтверждённый разбор. При изменении условия сбрасывай прежнюю трактовку, сохраняя загруженные работы отдельно. Для каждого обязательного пункта запиши происхождение: точную цитату МЭШ с совпадающим фрагментом или страницу назначенного упражнения. Проверка формата данных не заменяет смысловой сверки: прочитай пункт рядом с исходным условием и убери всё, что учитель не требовал. Неподтверждённый совет не попадает в `submission.items`, `steps` и описание ожидаемого фото. Для письменной работы не добавляй агентский тест. [Контракт происхождения](docs/product/day-page.md#instruction-provenance).
- При каждом новом или изменённом ДЗ сверяй точный текст МЭШ с проиндексированным PDF учебника и указывай `taskPages` в закрытом `.local/material-pages.json`. Это относится ко всем 12 ученическим учебникам, а не только к книгам из прежнего списка `books`. Если PDF или нужного текста нет, укажи явный статус и проверенную причину. Не обходи остановку `day publish` при `textbook-page-needed`; [контракт источников](docs/product/materials.md#mandatory-source-link).
- Сначала определи [вид ожидаемого результата и адаптер карточки](docs/product/card-generation-policy.md#decision-graph), затем применяй предметные правила. Для нового нумерованного задания по математике или спецкурсу после сверки оригинала подготовь закрытый [математический маршрут](docs/product/math-solution-route.md#pipeline) для **каждого номера**. Профиль `compact / standard / extended` выбирается по глубине конкретной задачи, а не названию предмета; данные, связи, вычисление и ответ с проверкой остаются понятными даже при объединении видимых блоков. Ответ впервые появляется в последнем этапе, полный путь хранится только в `dayTaskGuides`; по фото связывай проверку с теми же ID этапов. `mathRoutePolicyVersion: 1` останавливает выпуск нового разобранного листа при пропуске номера или маршрута. Список многих коротких примеров пока требует отдельной композиции.
- Для листа спецкурса дополнительно применяй [слой оригинала учителя и нумерации](docs/product/special-course-card-overlay.md#teacher-sheet); этот слой не выбирает профиль решения и не действует для обычной математики.

- Исходники находятся в `main`; готовый сайт публикуется из ветки `gh-pages` по адресу https://rubaxa.github.io/education-quizzes/. GitHub Actions сейчас недоступны в этом аккаунте, поэтому push исходников сам по себе сайт не обновляет.
- После завершения изменений, которые влияют на сайт, доведи код до готового, проверенного и отправленного состояния, проверь необходимость выпуска через `npm run publish:pages -- --dry-run` и **предложи пользователю публикацию**. Если публикация уже разрешена в текущем разговоре, выполни её без повторного вопроса. Не объявляй работу опубликованной до проверки готового сайта.
- Перед выпуском данных дня проверь [модель Firestore](docs/product/firestore-data-model.md): форму документов, уникальность `taskId`, ровно одну действующую связь теста и существование обоих ролевых списков. После выпуска запусти `npm run day -- audit` для всех опубликованных дат; при ошибке не объявляй синхронизацию завершённой. Для старой ошибочной связи используй узкую миграцию с сохранённым снимком, а не полный перепуск исторического дня.
- Для прямой отправки изменений из чистой ветки `main` используй `npm run push:publish`: команда сначала выполняет push, затем `npm run publish:pages`. После слияния pull request обнови локальную `main` и выполни `npm run publish:pages` после решения о публикации.
- `npm run publish:pages` сравнивает отпечаток исходников с последней опубликованной сборкой. Если исходники сайта не изменились, повторную сборку и публикацию пропускает. При изменении сайта дождись статуса `built` в GitHub Pages и проверь доступность URL.
- Новость в колокольчике выпускай только для крупного изменения, которое меняет действие пользователя или важный учебный статус. Несколько небольших улучшений группируй в один содержательный выпуск; повторную проверку, техническую оптимизацию чтений и очередное развёртывание сайта не превращай в отдельные сообщения. Для значимого выпуска используй `.local/release-*.json` с `releaseId`, `audience`, `title`, `body`, `changes` и `npm run publish:pages -- --release-note .local/release-*.json`; повтор с тем же ID не создаёт дублей. Для остальных выпусков используй `--silent-reason "конкретная причина"`. Если код уже опубликован, подготовленную значимую новость отправь через `npm run notifications -- publish .local/release-*.json` без повторного выпуска PWA.
- Если изменились `firestore.rules`, отдельно опубликуй их через `firebase deploy --only firestore:rules --project education-9d7c6` и проверь правила до выдачи ученической или родительской ссылки.

## Доступ и расходы

- Родитель уже перевёл Firebase на Blaze; не меняй тариф, не добавляй Cloud Functions или обязательный вход для ученика без нового решения пользователя. Тариф не заменяет контроль чтений.
- Не коммить `.local/`, токены, ключи и реальные ответы ребёнка. Ссылки ученика, предпросмотра и кабинета являются ключами доступа.
- Перед добавлением или изменением чтения Firestore открой [реестр путей](docs/architecture/firestore-read-paths.md) и оцени размер результата, частоту изменения, холодный и тёплый запуск, необходимость listener, локальный снимок, стоимость Rules и безопасность роли. `npm run index:reads` обновляет машинный список; каждый новый вызов получит `review-required`, пока решение не записано. `npm run check:reads` и общий `npm run check` не пропускают неразобранный путь. По сопоставимому сценарию измеряй доставленные документы и оплачиваемые чтения; наличие вызова в исходниках не равно стоимости в счёте.
