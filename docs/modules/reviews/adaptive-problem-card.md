# Адаптивная карточка задачи

Основания: [синтез исследований](../../research/adaptive-problem-scaffolding.md), [критическая проверка](../../research/adaptive-problem-critical-review.md), [оригинал и помощь по запросу](../../research/condition-transcript-and-scaffold.md), [проверка решения по фото](../../research/photo-math-solution-review.md), [обратная связь после ошибки](../../research/feedback-after-errors.md). Связанные контракты: [страница дня](../school-diary/day-page.md#несколько-страниц-одного-задания), [материалы](../materials/materials.md#ридер), [разбор работы](../school-diary/day-page.md#разбор-загруженной-работы), [данные и подписки](../families/access-and-state.md#владение-состоянием).

Эта карточка описывает нумерованную математическую задачу. Её источник, история попыток, разделение родителя и ребёнка и адресная помощь являются частью [общего пути разбора](subject-aware-guidance.md) для обычного ДЗ, спецкурса и применимых письменных работ по другим предметам. Спецкурс не задаёт отдельную архитектуру проверки. Действующий закрытый родительский маршрут `ParentTaskGuide` дополняет видимый педагогический слой `problem.support`, не заменяя его. [Матрица решений о виде компонентов](problem-card-design-decisions.md) фиксирует их порядок и проверку регрессий.

## Слои

1. **Источник:** `problem.original.text` — визуально сверенная дословная запись конкретного номера, `attachmentRef` — `sourceRef` исходного листа учителя в `materialLinks[task.id]`. Если на листе несколько номеров, `problem.original.crop` задаёт прямоугольник **именно этого номера вместе с его рисунком** в координатах исходного изображения (`x`, `y`, `width`, `height`, `sourceWidth`, `sourceHeight`, `sourceSha256`). В карточке всегда виден сам фрагмент исходного изображения, даже когда `original.text` заполнен. Транскрипция и ошибка загрузки пикселей не заменяют его текстовой плашкой; при ошибке нужен повтор загрузки. Просмотрщик позволяет увеличить фрагмент и переключиться на весь лист. Дословный текст показывается один раз под изображением. Целый оригинал остаётся по той же публичной ссылке и не заменяется пересказом или перерисованной схемой. `problem.detail` — прежний пересказ для совместимости; его запрещено подписывать «оригинал».
2. **Пояснение Education:** `problem.support` хранит `skill`, `state`, `evidence`, `evidenceRefs`, `facts`, `find`, `firstQuestion`, `revision`. Все значения выводятся из подтверждённой траектории и визуально сверенного источника; `facts/find` только повторяют данное и искомое, не сообщают вывод или ответ. Каждый различимый факт записывай отдельной парой `label/value` и показывай [отдельной ячейкой](problem-card-design-decisions.md#fact-tiles), а не одним перечислением. Ученик сразу видит оформленные `facts/find`; это помощь в чтении, а не инструкция к решению. Родитель видит также основание выбора опоры. Это не дополнительное требование учителя.
3. **Попытки и запрос:** фото и разборы остаются на `problem.id`. Ученик сам раскрывает «Нужен ориентир?», отмечает вид затруднения, по желанию пишет вопрос и нажимает «Отправить». `dayHelp/{studentToken}/items/{problemId}` хранит `requestKind`, короткий `requestText`, ревизию и время; писать может только ученический сеанс. Запрос не равен ошибке. После отправки текущая версия интерфейса показывает заранее подготовленный `firstQuestion` и честно обозначает его происхождение; текст запроса оператор читает через `npm run submissions -- help` при следующем разборе, автоматического индивидуального ответа сейчас нет. Полный разбор и история хранятся в родительском `dayReviewPrivate`, а `dayProgress` содержит только проверенную ученическую проекцию. Исправление после помощи не считается самостоятельным освоением.

Для письменной математики `dayProgress.mathReasoning` разделяет правильность ответа (`answer`) и минимальную проверяемость записанного хода (`argument`). `observed` передаёт только видимое на фото; `minimumNeeded` называет один недостающий переход, не готовое решение. «Верный ответ, но ход не показан» выводится именно так, а не как неверный ответ. Достаточность не измеряется числом строк: проверяющий должен суметь проследить существенную идею, опорную связь и вывод, не дописывая доказательство за ученика. Простые промежуточные вычисления разрешено опустить. Если условие учителя явно принимает только ответ, `argument: not-required` допустим лишь с `criterionSource`; это не новое требование к школьной работе. История разбора сохраняет оба измерения.

После сверенной проверки родитель может отдельно [засчитать верный ответ с неполным ходом](../school-diary/day-page.md#parent-acceptance). Карточка покажет короткие статусы ответа и хода; решение изменит семейное завершение пункта, сохранив педагогический разбор и открытый вопрос об обосновании. Оба маршрута карточки используют одно событие Firestore и одинаковый компонент, без частного правила под номер задачи.

После сообщения ученика о раскрытом ответе свободные поля `summary`, `items.note/expected`, `minimumNeeded`, `nextStep` и тексты истории исключены из ученического документа: они не проходили проверку на отсутствие ответа. Полная экспертная проверка публикуется в `dayReviewPrivate/{studentToken}/items/{taskId}` с доступом только родителю; `dayProgress` хранит проекцию из `storage/review-projection.mjs`. `WorkReview` показывает проверенное `studentFeedback`; если у старого разбора его нет, компонент сообщает, что адресный вопрос ещё уточняется. Новая публикация `partial` или `needs-fix` без этих полей отклоняется. Старые записи переносятся командой `npm run submissions -- migrate-private-reviews`; после неё обязательна проверка `npm run submissions -- review-privacy-audit`. До её успешного завершения приватность прежних записей не подтверждена.

<a id="адресный-разбор"></a>
## Адресный разбор после фотографии

Один универсальный компонент для любого предмета получает из проверенных данных **три отдельные ученические фразы**: (1) что конкретно получилось в этой попытке, (2) где находится первое наблюдаемое расхождение с заданием или первый непроверяемый переход, с привязкой к строке, позиции, рисунку или фрагменту фото, (3) один вопрос или малое действие именно к этому месту. Место и вопрос показываются сразу после проверки; отдельный запрос помощи остаётся для следующего уровня. Статус и внутренние `mathReasoning.answer/argument` управляют цветом и логикой, но не превращаются в фразы «Ответ: есть ошибка», «Ход: нужен один переход» или «Сравни с условием» без указания места.

Проверяющий сначала сопоставляет **точный оригинал, весь видимый ход, предыдущее фото и предыдущую обратную связь**. Он отделяет описанный на фото факт от предположения о причине: вычислительная неточность, неверно применённое правило и отсутствие объяснения могут сосуществовать. Для ученика выбирает один самый ранний подтверждённый пробел; другой пробел может быть виден родителю в диагностике и становится следующей целью после исправления первого. Если символ или граница шага не читаются уверенно, пишет «не могу прочитать этот фрагмент» и запрашивает именно его, а не приписывает ошибку мышления.

После новой попытки сравнивается то же место: исправлено ли оно, изменился ли способ, какая помощь была запрошена. При исправлении прежнего пробела переходят к следующему реальному пробелу; при повторении дают более узкий вопрос или аналогичную малую задачу и проверяют предпосылку. Не повторяют прежний шаблон слово в слово и не раскрывают готовый ответ. Текущая `dayProgress.history` хранит прежний разбор с `studentFeedback` и `uploadIds`, а `WorkReview` показывает в истории заголовок и место прошлой трудности. Запрос помощи хранится отдельно в `dayHelp`. Обязательная сверка всей истории и уровня помощи пока выполняется оператором по этим данным и закрытому source-pack; автоматическое сравнение попыток и отдельное подробное родительское представление ещё не реализованы.

`dayProgress.studentFeedback` — отдельное проверенное оператором поле с `title`, `confirmed`, `focus`, `question` и необязательным `anchor` (`uploadId`, читаемое местоположение). Привязка указывает на тот же оригинал фото. Для будущей визуальной рамки допустима координатная область с размерами и хэшем, но это пока не реализовано; отдельный кроп-файл не создаётся. `submissions review` останавливает публикацию `needs-fix` или `partial` без этих фраз, а `submissions feedback` исправляет старый разбор только при совпадении ребёнка, статуса, ревизии самого разбора и набора уже проверенных фото; если страница дня позже обновлена, требуется ещё дословное совпадение исходного и текущего `meshText`. Поправка не создаёт фиктивную ученическую попытку. Старые непроверенные свободные тексты автоматически в поле не переносятся. Общий `WorkReview` показывает эти три фразы и скрывает машинные рубрики. Для старого разбора без проверенного поля он честно сообщает, что адресный ориентир ещё уточняется; такие записи требуют отдельной ручной ревизии.

## Показ ученику

По умолчанию видны исходный лист учителя **один раз** и список всех номеров со статусами. Номера свёрнуты. В раскрытом номере идут три неизменных слоя: **видимый точный crop оригинального листа вместе с рисунком → видимая дословная текстовая запись → оформленное «Как читать условие» с данными и искомым**. Текст помогает прочитать изображение, но не заменяет его; опечатку источника не исправляют молча. При отсутствии crop виден точный текст и ссылка на целый лист; при отсутствии проверенного текста виден оригинал и честная пометка. Ниже отдельно находятся загрузка нескольких фото, текущий разбор, история попыток и помощь по запросу. Первый ориентир не должен повторять уже показанный факт или раскрывать решающую связь. При неизвестном навыке система не объявляет пробел. При новой ошибке агент выбирает один следующий вопрос по первой наблюдаемой трудности; исправленная с помощью работа не считается самостоятельным освоением.

Родительский экран показывает тот же лист и свёрнутый список; внутри номера доступны точная запись и цветной блок `Дано / Найти` независимо от наличия `math-route`. Подробный родительский маршрут ниже свёрнут отдельно. Основание выбора уровня опоры хранится в `support.evidence`; его компактный показ остаётся открытым UI-решением, без добавления новой полноширинной панели. Полный ответ не попадает в ученический `problem.support`.

<a id="происхождение-задачи"></a>
## Происхождение задачи

Перед подготовкой листа спецкурса и до проверки фото выполняй [поиск прототипов, вариантов и ключей](../../research/special-course-source-provenance.md) **для каждого номера**. Сопоставляй не только имена, но структуру, числа, рисунок, класс, сборник, организатора, год, ответ и критерии. Точный учительский оригинал остаётся текущим заданием независимо от совпадения с прежним вариантом. Различай кандидата из поискового сниппета, визуально подтверждённый источник и отдельно сверенный ключ. Отсутствие совпадения честно отмечай; слово «ВсОШ» не выводи из олимпиадной формы задачи.

`sourceResearch` содержит только **родительские метаданные**: `status`, `title`, `url`, `match`, `keyStatus`, `note`; полный ключ и решение остаются в закрытом источник-пакете. `day publish` и `problem-support` удаляют `sourceResearch` и `parentGuide` из **обоих** документов `dayPages`, которые читаются по ссылкам, и помещают их в `dayTaskGuides/{studentToken}/items/{problemId}` с проверкой роли взрослого в Firestore. Ролевое разделение выполняется на уровне документов Firebase, а не простым скрытием поля в JSX. Старые опубликованные документы требуют отдельной миграции и проверки удаления поля. В интерфейсе родитель видит один знак у заголовка номера; подробности открываются по нажатию без отдельной постоянной строки. `not-found` означает записанный неудачный поиск, отсутствие `sourceResearch` — поиск не записан; оба состояния не смешиваются. Конкретный охват поиска пока записывается свободным текстом в `match`/`note`; структурированного поля нет.

## Выпуск и безопасность

`day publish` обязан отклонить номер с оригиналом без совпадающего `attachmentRef`, текста и опоры `support`; содержимое текста оператор сверяет глазами с оригиналом. Для листа с несколькими номерами оператор визуально отмечает границы каждого полного условия и рисунка в оригинале, проверяет размеры и SHA-256 исходного изображения; если фрагментация задана хотя бы одному номеру, она нужна всем номерам этого задания. Изображение не разрезается с потерей первоисточника: координаты лежат в данных Firestore, интерфейс показывает нужный участок того же оригинала. Координаты с выходом за границы или с несовпадающим хэшем публикация отклоняет. Базовая страница и текущие разборы приходят по `onSnapshot`, поэтому новые координаты, подсказки и попытки не требуют выпуска PWA. Изменение самого компонента требует `publish:pages`. Обновление данных не стирает исходник или историю. Если старый документ не содержит `original`, интерфейс показывает лист и честную пометку, что точная текстовая версия ещё не подготовлена; прежний `detail` не выдаётся за оригинал.

Для изменения только нумерованного задания и его поддержки есть `npm run day -- problem-support YYYY-MM-DD`. Команда сверяет оба ролевых документа, `meshText`, IDs/номера задач и опубликованный `attachmentRef`, затем транзакционно обновляет публичную поддержку в `subjects[].tasks[].problems`, закрытый ориентир и исследование в `dayTaskGuides`, `problemSupportRevision` и отдельный журнал `problemSupportChanges`. `planRevision` и `changes` неизменны: уже загруженные фото и текущие разборы остаются привязаны к прежнему заданию. Расписание, оценки, ссылки, загрузки и разборы команда не трогает; при расхождении источника требует полный разбор дня. Так можно изменить уровень помощи после новой попытки без повторного выпуска сайта или перезаписи живого состояния.

Это модель данных, а не отдельная страница под каждый лист: бинарный оригинал хранится на Яндекс.Диске, а Firestore содержит его ссылку, хэш, номера, координаты фрагментов, педагогическую опору, статусы и результаты. `DayPage` и `WeekendMathSlot` используют общие `useDayEvidence`, `MaterialReader`, `ProblemGroup`, `ProblemTaskCard`, `ProblemCard`, `ProblemStatement`, `ProblemUploadButton` и `WorkReview`; единая палитра статусов и [правило сворачивания завершённого листа](../school-diary/day-page.md#completed-problem-group) применяются к обоим экранам. Распознавание и разметка следующего исходного листа меняют данные, а не код или сборку сайта. Новая сборка нужна только при изменении самого движка или его общих компонентов. Ученические фото также уходят напрямую на Диск по [очереди загрузки](../materials/storage-privacy.md#upload-queue); в Firestore нет новых бинарных копий.

<a id="shared-problem-view"></a>
## Общее представление номера

`ProblemTaskCard` собирает одну и ту же карточку номера в дне и выходном слоте: `ProblemCard` для заголовка, состояния и родительского значка происхождения, `ProblemStatement` для оригинала и разрешённого ориентира, ролевой маршрут помощи в одном месте после условия, `WorkReview` для результата, `ProblemUploadButton` для новой фотографии только у ученика. Это существующий `PhotoUploadControl`, не отдельный загрузчик. У родителя маршрут содержит полный закрытый разбор и команды выборочной отправки; у ребёнка тот же раскрываемый рисунок блока появляется только для отправленных этапов. [Матрица ролевых проекций](problem-card-design-decisions.md#role-projection) фиксирует точный порядок и границу доступа. Маршрут предоставляет только свой способ загрузки и галерею уже полученных файлов. Два маршрута получают фото и результаты через общую подписку `useDayEvidence`; пользовательский статус не вычисляется отдельно в каждом экране. Описание листа и порядок работы конкретного ребёнка приходят из данных дня и его персональной модели, а не из ветки по `subject.id` в JSX. Текущая персональная опора `DayProblem.support` находится в переходном документе дня; [семейная модель v2](../families/README.md#sync) пока не стала действующим источником этих карточек.

Числового порога «100% освоено» здесь нет. `support.state` — рабочая оценка доказательств по конкретному навыку (`unknown`, `provisional`, `practicing`, `demonstrated`), а не характеристика ребёнка.
