# Реестр путей чтения Firestore и выбор способа обновления

Перед публикацией перехода task → source-only notice оператор адресно проверяет `dayReviewPrivate/{studentToken}/items/{entryId}` вместе с существующими progress/uploads guard. Чтение ограничено затронутыми source entries и подтверждёнными собственными/history day tokens; оно запрещает скрытие прежнего закрытого разбора даже при отсутствии публичного progress. Подписки и глобальный скан не добавляются.

`sync:project audit --run RUNID` читает `syncStatus/current` точного владельца каждого manifest job перед проверкой и повторно перед private receipt. Это два ограниченных point reads на owner для fencing конкурентного изменения запуска; запрос не пишет статус и не закрывает queue jobs.

Операторский `sync:queue list --id` адресно читает один `operatorSyncJobs/ID` и, при корректном artifactPath, один `operatorSyncTaskArtifacts/ID`. Это явно запрошенное оператором чтение без subscriptions, обновления артефакта и глобального скана; оно нужно для сопоставления события с уже проверяемой работой и исключения повторного разбора.

Загрузка фото читает адресно владельца дня, существующую заявку и актуальную серверную страницу только при действии пользователя. Серверная ревизия заменяет потенциально устаревший cache; сравнение условия защищает от привязки к изменённому заданию. Повторный receipt читается после неоднозначного commit. Эти проверки не добавляют подписок, polling или чтения глобальной очереди; [контракт загрузки](../materials/storage-privacy.md#upload-queue).

`sync:project collect` дополнительно читает семейные задания только для текущей подтверждённой пары `familyId/childId` и диапазона дат уже собранного снимка. Этот один ограниченный запрос на ребёнка нужен для сравнения календаря с тем же family-origin overlay, который строит `day publish`; включаются только активные записи, явно отмеченные `dayProjectionVersion: 1` и прошедшие общий валидатор семейного назначения. Он не перечисляет семьи или задачи за пределами текущего ребёнка и окна сбора.

19.10 — исправление канонических коротких ключей: явная `quiz repair-canonical-short-answers` адресно читает назначение, ключ и ручной разбор одного токена; `--apply` повторно читает назначение/ключ в compare-and-set транзакции и после записи. Межсемейный обход отсутствует, владелец проверяется по закрытому реестру. Клиент получает исправление через прежний listener ключа; новых подписок и polling нет. [Узкий контракт](../assessments/quizzes.md#canonical-short-repair).

Каникулы: `publishSchoolCalendar` читает только два уже известных dashboard ребёнка в одной транзакции, проверяя роль/владельца и сохранённое содержимое. Если изменилось содержимое либо расширился горизонт, обновляет затронутые документы и адресно перечитывает их (до двух дополнительных чтений). Неизменный повтор обходится без writes/readback. Это операторский запрос, не polling; браузер использует прежнюю подписку на dashboard без дополнительных чтений. Источник МЭШ запрашивается один раз на ребёнка за сбор.

18.10 — [восстановление изменённой личности устройства](../../decisions/device-binding-recovery-2026-10-18.md): только при подтверждённом расхождении/permission-denied, в том числе у просроченного startup-профиля, один адресный `getDoc(deviceSessions/ownUid)`. При другом токене добавляется `getDoc(accessLinks/newBinding)` и существующий граф профиля; одинаковые параллельные recovery присоединяются к одной попытке. SDK fromCache не считается серверным подтверждением. Обычный тёплый запуск и число listener не меняются, polling и сканирования устройств нет. Отдельные тесты проверяют 0 новых чтений на тёплом старте, 1 device read на параллельное восстановление и 0 записей прав.

18.10 — восстановлена отсутствовавшая подписка помощи в выходном блоке: один `useTaskGuidance` на исходный день вместо отдельных потоков на каждый номер. Она обоснована показом помощи ученику и исключением дубликата у родителя. Обычный DayPage сохранил прежний поток. Коллекция/команда/проверка guide и атомарный inbox прежние; подписка закрывается при уходе, taskId фильтрует фрагменты. Счётчик source sites не равен числу runtime-подписок: новых onSnapshot sites нет, но Weekend раньше вообще не получал эти данные.

18.10 — компактные Telegram сводки: progress observation адресно читает masked day owner/page для точного предмета/задания/даты, повторно используя taskContext. Новых polling источников нет; partial context не продвигает baseline. Enqueue читает group pointer и открытую группу только для конкретного получателя; перенос quiet deadline читает pending members одной группы, ограниченной50событиями/256KiB. Due claim читает только ту же группу и соответствующие ledger events, атомарно замораживая immutable digest. GroupId/state индекс добавляется к scoped manifest без замены глобального списка. Операторский review-check запускается явно и обходит inventory, затем адресные masks/ledger query по hashed record key; groupedInto читается адресно с проверкой eventJobIds. Upload diagnostic использует такой же readback. Эти чтения не происходят при открытии сайта и не являются замером счёта.

18.10, повторная проверка корневого входа: PersonalEntry использует прежние grant/device/member подписки после Auth как барьер роли, с metadata-only подтверждением. Для одной семьи по-прежнему3подписки и0дополнительных профильных чтений на обычном тёплом запуске. Подтверждённое расхождение роли/детей вызывает один loadPersonalProfile и переподписку только членства; в LearningRoute та же сверка сохраняет три listener, а исторический день повторяет одно точное чтение identity. Нового polling нет. Ожидание до подтверждения заменяет преждевременный ролевой кадр; [решение](../../decisions/personal-entry-role-confirmation-2026-10-18.md) и интеграционные тесты фиксируют исключение и бюджет.

18.10 — [общий адрес, роль из сессии](../families/access-and-state.md#authenticated-learning-routes): три адресных listener контроля grant/device/member перенесены из App в LearningRoute; теперь они защищают также подробный учебный день. Это максимум3документа контроля на смонтированный учебный маршрут, не опрос коллекций. До серверного подтверждения карточка не показывается как ученическая. Календарь разрешается из shortcut уже загруженного профиля без дополнительного чтения индекса; лишь старый кэш без aliases требует одного обновления профиля. Исторический день добавляет одно getDoc(dayPages/token) для поиска владельца и пары проекций; скрытые guides не запрашиваются в этом этапе. Миграция attach-current-day добавляет4точечных обратных чтения двух календарей/текущих дней по явной команде, не на каждом открытии. Смена роли/отзыв закрывает экран, polling нет. Это обоснование мест вызовов, не заявление о стоимости Firestore.

## Что индексируется и чего индекс не доказывает

AST-проход по продуктовым `src/`, `scripts/`, `sync/`, `packages/` нашёл **346 кандидатов**: 45 предварительно оправданных действий, 283 условно оправданных, 11 путей высокого риска и 7 совпадений, не относящихся к Firestore. Категория `conditional` означает «нужно проверить размер результата, частоту и альтернативу», а `high-risk` — направление аудита, **не** доказанную долю в счёте. Вызовы `Map.get()` отдельно исключены или помечены `excluded`; проверки `get()/exists()` в Firestore Rules и внутренние чтения SDK этим AST-проходом не охвачены. Динамическое создание `ref` может скрывать точный путь, поэтому реестр содержит исходное выражение, а не обещает полностью вычисленный URL.

Реестр охватывает Web SDK `getDoc/getDocs/onSnapshot`, серверные `get/getAll/onSnapshot`, агрегаты `count().get()`, транзакционные `get` и другие прямые варианты. Тесты и фикстуры не включаются. Новый способ чтения SDK требует расширить сканер, реестр и этот контракт. При изменении файла пересчитывается отпечаток вызова; прежнее решение не переносится без просмотра. Исторические данные по [нагрузке](../../audits/firestore-usage-2026-10-12.md) и [плану этапов](../../plans/local-first-release-plan-2026-10-12.md) дают исходные гипотезы, но не заменяют причинное сравнение.

## Telegram recovery и EducationSync19.10

Новые IDs Firestore обнаруживаются collection listeners только внутри подтверждённых семей и canonical dayOwners: assignments/dayOwners по familyId, files/items по точному dayToken. Snapshot payload остаётся в адаптере, наружу выходят descriptors. Начальный query snapshot и последующие deltas/reconnect создают дополнительные SDK reads; существующие record listeners сохраняются для безопасного восстановления при ошибке discovery. Callback известного ID не запускает повторный pipeline; owner/child guard refs дедуплицированы по пути. Новый candidate проходит адресную проверку владельца, затем транзакционно читает ровно context/scope origin marker; нового context-complete marker эта операция не создаёт. Активные candidate операции ограничены concurrency. Firestore и Mesh имеют независимые очереди и inventory, переиспользуя общий family graph/адаптеры; фоновые registry/fallback чтения не объявляются бесплатными. Read counters и фактическая тарификация различаются. [Решение](../../decisions/firestore-live-discovery-2026-10-19.md).

`mesh-delivery-check` — явная read-only диагностика: все разрешённые scopes из общего registry, один notify checkpoint на scope, адресные ledger queries по sourceEventKey с последующей строгой проверкой family/child/scope, outbox по eventId и точный groupedInto digest с проверкой eventJobIds. Окно detectedAt определяет отчёт; технический limit явно делает охват неполным. Проверка не добавляет фоновых observers и не вызывается из PWA. SDK counters не выдаются за billed reads.

EducationSync dispatcher — opt-in административный consumer: транзакционно читает один event-dedupe документ и один current queue документ при принятом Mesh delta; в idle loop читает только current с bounded backoff, не сканирует школьные данные. Claim/heartbeat/complete/fail/block/resume читают тот же точный request и проверяют state/token fencing. Явный enqueue-event адресно читает существующий natural Mesh ledger event и текущий семейный registry для owner validation. Полная синхронизация использует прежний operator workflow; отдельного повторного сканера учебных данных нет.

## Решение по текущим классам данных

`notifications backfill-grades` — явное восстановление по двум локальным полным журналам: точные family/child/sourceIdentity для общего owner predicate, одно чтение членов конкретной семьи, адресный inbox getAll после записи для каждого нового предметного события и существующие чтения stageFamilyNotice. Проверяются active/role/childIds и одна точная исходная личность обоих журналов; нет нового обхода семей, источников МЭШ или подписок клиента. Create-only precondition не переписывает даже одновременно прочитанное уведомление; при ALREADY_EXISTS до трёх повторных адресных сверок.

Адресная диагностика `family inspect-access`18.10: только по операторскому запросу одного зарегистрированного человека читаются его профиль/семейный указатель/членство, дети из подтверждённого семейного scope, shortcuts, две ролевые проекции текущего дня/календаря, источники weekendWork и его grants. Одно get на уникальный путь внутри запуска; ноль записей/подписок, нет обхода книг/ответов/всех семей. Полученный аудит16документов не добавляет чтений клиенту. Исправление concurrent redemption присоединяет существующий restore к Promise входа и не добавляет новых серверных вызовов.

Временная role projection probe18.10: клиент использует уже открытый member listener и не читает отдельную конфигурацию. Включение/остановка окна:1точное чтение членства до update и1обратное; чтение отчёта:1членство+1query personId/familyId limit20 без live listener. Это явная диагностика одного участника, не часть sync/старта приложения. Клиентские записи выключены по умолчанию, ограничены expiry и дедуплицированы по фактическому состоянию; закрытые учебные данные не включаются.

### Первый срез Telegram worker: границы чтения

Первый worker не устанавливает Firestore source observers: он не читает и не опрашивает учебные источники. `telegram-bot check` проверяет Telegram identity через `getMe` без создания Firestore client. Только явно запущенный `worker` делает одну стартовую проверку доступности ADC/project через `telegramBotRuntimeChecks/{projectId}` до polling. Доставка остаётся выключенной, пока оператор отдельно не передаст `--enable-delivery`.

Регистрация аккаунта и `/stop` доступны только в личных командах. `/start` выполняет одну транзакционную проверку существующего статуса; `/stop` адресно перечисляет связи пользователя и при подтверждении в транзакции повторно проверяет владельца, срок и одноразовость challenge, актуальную активную связь и пишет историю отключения. Эти пользовательские действия не являются фоновыми чтениями.

После исправлений 17 октября private `/start` и проверенный `my_chat_member` дополнительно читают account транзакционно для version/ordering guard состояния канала. Только фактический `403` вызывает отдельную транзакцию с expected channel version; известная доступность читается адресно перед job и каждой частью. Новых observers/collection scans нет; цена этих проверок растёт с числом parts. При добавлении одинаковых `tx.get` AST ID с ordinal может сохранить чужую старую классификацию: все Telegram transaction read sites пересверены по фактической функции, а не только по совпадению ID.

При приёме события recipient lookup ограничен одной семьёй. Перед постановкой outbox каждый получатель проверяется по актуальным link и membership, затем те же link/member условия читаются и проверяются в транзакции event ledger вместе с идемпотентным event ID и отсутствием duplicate job. Кешировать этот доступ нельзя: отключение связи должно учитываться до enqueue. Во время доставки членство проверяется перед job и перед каждой частью сообщения; после каждой отправленной части транзакция проверяет актуальный lease и порядок receipt. Эти проверки дают дополнительные чтения пропорционально адресатам и частям, но ограничивают отправку после отзыва доступа.

Outbox poll работает только при `--enable-delivery`: claim выбирает не более 20 due jobs, затем перед выдачей lease транзакционно перепроверяет состояние каждого кандидата. При простое worker ждёт с jitter и backoff от 1 до 60 секунд. Восстановление истёкших leases выполняется не чаще раза в минуту, одной выборкой не более 200 записей с транзакционной проверкой перед возвратом каждой записи в очередь. Если очередь восстановления больше лимита, остаток проверяется следующей минутной итерацией. Это ограниченный opt-in цикл, не наблюдение школьных источников.

Два composite index для outbox claim и recovery перечислены в [конфигурации индексов](../../../packages/telegram-notifications/firestore.indexes.json) и карте файлов. Все 18 новых site классифицированы по конкретной функции и границе выше; `Map.get()` в in-memory registry не является Firestore чтением и не включается в список.

### Подтверждение upload и адресная диагностика — 18 октября

Для подтверждённого upload observer адресно перечитывает owner и дневную страницу этого токена, чтобы проверить дату/вид страницы, taskIds и точное название задания. Это чтение выполняется только для подтверждённого storage-файла; оно добавляет серверные reads к обработке сигнала, не клиентские subscriptions. Storage mask содержит только provider/state/syncedAt, без оригинала, path/URL или хэша файла. Одна и та же чистая task-context функция используется inbox и Telegram.

Операторский upload-check явно запускается по запросу разбора инцидента: проходит общий семейный inventory, выбирает недавние upload записи и адресно проверяет discovery origin, checkpoint и связанные ledger/outbox. Он не вызывает SourcePipeline.process/accept, не пишет baseline или jobs и не отправляет сообщений. Изменение числа семей не ограничивается ручными IDs; фильтр времени задаёт диагностический охват, который не подменяет полный мониторинг. Конкретные SDK reads и решения фиксируются в машинном реестре; это не замер billed reads.

### Подключение Telegram source adapters — 17 октября

Срез выше описывает foundation до подключения источников. Новые observers включаются явно флагами `--enable-firestore-source`/`--enable-mesh-source`, а доставка — отдельно `--enable-delivery`. Source shadow всё равно читает inventory/источники и пишет служебные baseline; это не бесплатный dry-run.

Inventory автоматически проходит все семьи и scoped members/children/sourceAccounts, затем family assignments/dayOwners и refs-only upload/progress страницы. Keyset pagination не обрезает семьи и детей по количеству. Reconciliation по умолчанию каждые30 секунд: стоимость зависит от общего объёма registry/назначений, а не только от числа изменений. Это текущий простой алгоритм; incremental registry cursors/partition ownership нужны перед большим эксплуатационным масштабом. Техническая очередь bounded по числу одновременных запросов, не по числу семей. Ошибки одной семьи видимы и не выдают неполный inventory за пустой успешный.

Firestore listeners получают сигналы документов и владельцев. SDK может передать полный snapshot; callback не сохраняет/не логирует его и делает разрешённый reread через `db.getAll(ref,{fieldMask})`. Этот API проверен по локальному SDK; у DocumentReference.get нет такого fieldMask контракта. Частые owner/member rereads защищают от отзыва и смены владельца; повторы и reconnect также стоят reads. Служебные `telegramNotificationSourceCheckpoints` используют транзакционные lease/fencing, renew heartbeat, pending и baseline; `telegramSourceDiscovery` хранит неизменный bootstrap/live origin для безопасного restart. Эти reads — плата за durable дедупликацию, а не учебные данные.

Mesh credentials resolver адресно проверяет семью, ребёнка, sourceAccount, sourceIdentity и parent membership перед запросом и публикацией observation. Он не ищет credentials глобально и не переносит source account между детьми. `Map.get`, pipeline collection lookup и локальные cache/locks в source modules исключаются из Firestore read index. Runtime замер billed reads, listener reconnect, API нагрузки и задержки пока не проводился.

Переключатель этапа родительского разбора делает два адресных серверных чтения только после нажатия: текущий `dayTaskGuides` и `dayProgress`. Они нужны для защиты выбора от устаревшей ревизии разбора и новой проверки фото. На открытии страницы новых чтений нет; до живого замера нельзя приравнивать два вызова к двум оплачиваемым документам, поскольку Security Rules также читают связанные записи. Классификация этих двух вызовов зафиксирована в реестре.

«Прочитать все» в колокольчике запускает чтение только по явному нажатию, не при открытии панели: `users/{personId}/inbox` последовательно страницами по 400, с курсором `createdAt`. Это необходимо, поскольку постоянная подписка ограничена последними 100 документами и не покрывает старые непрочитанные события. Объём равен истории данного человека и может быть большим; действие не вызывается автоматически, а фактические чтения и расходы требуют живого замера. Запись `readAt` идёт только для непрочитанных записей уже существующим пакетом.

Порог повторных тестов 14.10.2026 добавляет одно адресное транзакционное чтение назначения **по явному нажатию родителя**. Периодический сканер читает две ограниченные выборки `submittedAt` и `followupRequestedAt` от текущего понедельника, дедуплицирует их и только затем адресно проверяет наличие продолжения, ключ и ручной разбор. Старую историю `status=submitted` он читает лишь при явном `--full-audit`; это потенциально дорогой операторский проход, которому нужен отдельный подсчёт документов. `quiz create` однократно читает ключ исходной попытки, чтобы запретить неверный размер продолжения или ненужный новый тест. Новых клиентских listeners нет; холодный и тёплый запуск экрана используют существующую подписку на попытку и связанный результат. ## Варианты из первичных источников и границы их применения

1. **Меньше возвращённых документов.** Адресный документ, фильтр по активному состоянию, `limit` и курсор уменьшают результат; `offset` тарифицирует пропущенные документы. Пустой запрос всё равно стоит минимум одно чтение. Использовать для истории, операторской очереди и календарного горизонта. [Firebase: pricing](https://firebase.google.com/docs/firestore/pricing), [best practices](https://firebase.google.com/docs/firestore/best-practices).
2. **Listener только там, где нужна немедленная реакция.** Начальный результат и обновления оплачиваются; без веб-персистентности повторное подключение тарифицируется как новый запрос. При постоянном кеше повторное подключение после более чем 30 минут снова тарифицируется как новый запрос. Локальный снимок может появиться до сервера, но это не подтверждение свежести. Сохранять listeners для отзыва доступа, активных фото/тестов и открытого дня; статичные страницы и архив переводить на разовый запрос и инвалидацию. [Firebase: pricing](https://firebase.google.com/docs/firestore/pricing), [realtime listeners](https://firebase.google.com/docs/firestore/query-data/listen).
3. **Постоянный локальный кеш SDK — отдельный пилот.** Веб SDK по умолчанию использует память; `persistentLocalCache` доступен, но данные переживают сессию. Для личных семейных данных нужен режим доверенного устройства, разделение ролей, две вкладки и очистка при отзыве. Кеш ускоряет кадр, но не решает сам вопрос частоты серверной сверки. [Firebase: offline persistence](https://firebase.google.com/docs/firestore/manage-data/enable-offline).
4. **Манифест/хэш для неизменяемого.** Одна запись с изданием, количеством страниц и хэшем позволяет проверить локальный набор и читать страницы только при пропуске. Это уже применено к книге; нельзя повторно читать все страницы для одной проверки наличия. `count()` читает индекс, поэтому не является бесплатной проверкой. [Firebase: aggregation queries](https://firebase.google.com/docs/firestore/query-data/aggregation-queries), [pricing](https://firebase.google.com/docs/firestore/pricing).
5. **Сводка при записи либо журнал изменений — только после расчёта.** Для экрана, многократно собирающего много документов, компактная ролево-семейная проекция может быть дешевле. Она добавляет записи, миграцию и проверку согласованности. Для операторского цикла локальный снимок + курсор выгоден, если все писатели производят событие; пока есть старые клиенты, нужен редкий полный аудит. Один глобальный документ создаёт лишние обновления для других семей. Это наш вывод из модели продукта и [рекомендаций Firestore по данным/нагрузке](https://firebase.google.com/docs/firestore/best-practices), не готовая гарантия экономии.
6. **Считать Rules и разные типы запросов.** Клиентские `get()/exists()` в Security Rules могут добавить платные чтения; Admin SDK правила обходит. [Usage Insights](https://firebase.google.com/docs/firestore/enterprise/usage-insights) разделяет коллекции и streaming reads. [Query Insights](https://cloud.google.com/firestore/native/docs/query-insights) показывает нормализованные запросы, но **не включает realtime listeners** и запаздывает на 1–2 часа. [Query Explain](https://cloud.google.com/firestore/native/docs/query-explain) помогает исследовать один серверный запрос; `analyze` оплачивается как исполненный запрос. [Pricing](https://firebase.google.com/docs/firestore/pricing), [secure queries](https://firebase.google.com/docs/firestore/security/rules-query).

Ни React Query, ни Dexie, ни RxDB сами по себе не сокращают число оплаченных документов: политика обращения к серверу и гранулярность данных остаются нашей ответственностью. Их сравнение по текущим задачам уже зафиксировано в [решении по горячим путям](../../decisions/local-first-hot-path-decision-2026-10-12.md). Добавлять библиотеку следует только после пилота на одинаковом маршруте с доказанной пользой и миграцией локальных данных.

## Очерёдность и условия изменения

1. **Сначала** для каждого кандидата сохранить характеризационные тесты холодного и тёплого старта, исходный путь чтения, число доставленных документов, пересоединения и размер результата. Указать семью, роль, число вкладок, открытую дату и фон EducationSync. Статический счёт сайтов не является read budget.
2. **Первый кандидат на клиенте:** статичные `bookPages` и редко меняемые `books/bookRequirements`; сравнить имеющийся манифест/IndexedDB с текущими fallback listeners. Нельзя отключать старый listener до подтверждённой инвалидации от каждого писателя.
3. **Первый кандидат оператора:** широкие сканы `sync-inbox` и глобальный `dayOwners` listener. Прототип с локальным снимком источников/активным индексом сначала на fake Firestore; резервный полный проход сохраняет совместимость со старыми клиентами.
4. По выбранному сценарию выпускать только при **≥20%** снижении доставленных документов в сопоставимом тесте и отсутствии ухудшения побочных сценариев более 5%; затем проверить Usage/Query Insights и Monitoring на одинаковых живых окнах. Сохранность фото и незавершённого теста, отзыв права, две вкладки и старый клиент обязательны. Прежний формат Firestore остаётся читаемым до отдельной проверенной миграции.

Отчёт по каждому изменению: `путь → почему читали → прежний/новый режим → холодный/тёплый read budget → фактические метрики → корректность/миграция → решение оставить или откатить`. Если потребность в свежести не доказана, по умолчанию выбирать локальный снимок и адресную фоновую сверку; при защите записи нужна серверная проверка.

## Продолжение по полной истории: 16.10.2026

В sync-queue сохранены две адресные выборки свежих отправок/родительских запросов и проверка существующего продолжения; предки при discovery не читаются. targetCount=null требует quiz history, а не повторного сканирования семей. При create/revise-open существующий loadLineage читает только цепочку этой семьи до корня (до16попыток), переиспользуя уже прочитанные assignment/key/review последней попытки. Это необходимая проверка старых ошибок и fingerprint перед записью. Один дополнительный запрос родителя по100% использует прежнюю транзакцию — одно чтение назначения. Сортировка, закрытие истории и видимость иконки не добавляют сетевых вызовов. check:reads:359 прежних классифицированных мест, новых SDK-вызовов нет.

Операторский `telegram-design-preview` использует существующий resolveProbeTarget и проверенную семейную связь; новое чтение — адресный outbox receipt по вычисленному jobId до/после отправки. Оно выполняется только явной командой, не polling UI, выводит агрегаты. Для демонстрации не читаются новые семейные задания и не создаются вымышленные школьные события.
