# Единая очередь событий Education

## Назначение и единственная подписка

Прямое уточнение пользователя19.10 отменяет архитектуру фонового обнаружения действий через множество подписок на документы и коллекции. У Education одна внутренняя входная очередь `educationEvents`. Действия приложения и адаптеры внешних источников публикуют в неё события. Постоянный диспетчер имеет **одну Firestore subscription на очередь**, детерминированно разбирает события и передаёт работу скриптам, Telegram и EducationSync.

Фоновые per-document/per-family/per-day Firestore subscriptions для обнаружения действий не являются целевой архитектурой и отключаются после подключения производителей. Подписки экранов приложения относятся к показу данных и не заменяют эту очередь. МЭШ опрашивается общим HTTP-адаптером: подтверждённая разница публикуется в ту же очередь. Классификация, дедупликация и маршрутизация не используют LLM.

`operatorSyncJobs` остаётся существующим устойчивым состоянием исполнения задач; Telegram outbox остаётся механизмом транспортных retry/receipts. Они не являются альтернативными источниками бизнес-событий. Другой executor queue или отдельная подписка на каждый вид действия не вводятся. Новые виды событий добавляются через общий каталог и handlers; неизвестный вид видим как blocked, а не пропускается.

## Конверт и идентичность

Один документ `educationEvents/{eventId}` содержит:

| Поле | Контракт |
|---|---|
| `schemaVersion` | Версия1; неизвестная версия не исполняется молча |
| `eventId` | SHA-256 канонического объекта идентичности |
| `eventType` | Тип из каталога; не произвольная исполняемая команда |
| `familyId`, `childId` | Точный владелец; перепроверяется по текущим полномочиям |
| `source` | `firestore` или `mesh` |
| `sourceRef` | `kind`, `documentPath`, необходимые `dayToken`/`recordId`/`quizToken`/`taskId`; точный адрес источника |
| `operationId` | Устойчивая идентичность одного действия/ревизии; повтор не создаёт новое событие |
| `actor` | Клиент: `{type:user, uid}`; сервер: `{type:system, id}`; роль определяется полномочиями, не доверием к клиенту |
| `createdAt`, `availableAt` | Firestore timestamps; клиентские создания используют serverTimestamp |
| `state`, `attempts` | При создании `pending`,0; дальнейшие состояния меняет только dispatcher |

Идентичность хэширует канонические `eventType/familyId/childId/source/sourceRef/operationId`, исключая часы наблюдения, lease и retry. Последующие запросы помощи к той же работе имеют новый operationId; повтор одной отправки сохраняет прежний. Backend может сохранить нормализованное подтверждённое Mesh событие для точного воспроизведения. Клиент не помещает в конверт фото, ответы, тексты помощи, секреты или произвольные agent instructions.

## Производители и атомарность

Событие создаётся в месте подтверждённого действия вместе с изменением его источника, через тот же batch/transaction. Разрыв «данные записаны, событие потерялось» недопустим. При неоднозначном ответе сети producer проверяет доступный ему исходный operation receipt; он не сбрасывает состояние уже обрабатываемого события.

| Событие | Условие и назначение |
|---|---|
| `upload.transfer_requested`, `upload.bytes_uploaded` | Запрос ссылки и подтверждение передачи байтов; только детерминированный broker, ещё не проверка работы |
| `upload.delete_requested` | Подтверждённое удаление непроверенной работы и ограниченная очистка staging |
| `upload.confirmed` | Только финальное подтверждённое хранение файла; сообщение родителю и задача проверки |
| `quiz.submitted` | Подтверждённая отправка попытки; проверка/разбор |
| `quiz.started` | Первый подтверждённый старт попытки; уведомление без педагогического запуска, черновые нажатия новых событий не создают |
| `help.requested` | Запрос ученика/родителя; адресная задача помощи |
| `quiz.followup_requested` | Явный новый запрос теста; адресная задача генерации |
| `quiz.requirement_changed` | Решение родителя об обязательности; уже выполненное действие, без повторной генерации |
| `parent.guidance_sent` | Подсказка отправлена; уже выполненное действие, без повторного запроса LLM |
| `parent.decision` | Принятое решение родителя с собственной идентичностью |
| `material.upload_requested`, `material.bytes_uploaded`, `material.ready` | Запрос ссылки, переданные байты и проверенный материал — разные стадии |
| `review.published` | Подтверждённый новый результат проверки; доставка результата без рекурсивной проверки |
| Mesh изменение | Нормализованный подтверждённый diff общего source pipeline; та же очередь |

Промежуточный выбор файла, неподтверждённая передача и черновик ответов не становятся `upload.confirmed`/`quiz.submitted`. Служебные heartbeat, receipts и изменения очереди не порождают новые бизнес-события. Каталог расширяем; эта таблица не является лимитом действий или семей.

## Маршрутизация и готовое задание

Один dispatcher выбирает обработчики по типу события. Проверяемые данные читаются адресно по sourceRef через существующие source ports; глобальный inbox или МЭШ не перечитывается только ради выяснения, что произошло. Готовая операция с входами, версией, хэшем и условиями readback следует [execution artifact](execution-artifact.md). `operatorSyncJobs` хранит выполнение, event receipt — связь с поручением. Идентичность и актуальные полномочия проверяются и при подготовке, и перед публикацией результата.

Telegram получает нормализованное событие через прежний renderer/ledger/outbox. EducationSync запускается для непустого подтверждённого набора агентских задач; помощь, повторный тест и работа ученика маршрутизируются явно. Завершённая отправка подсказки или публикация review не вызывает второй LLM цикл. Неизменный источник и пустой набор задач не запускают исполнителя.

## Обработка и восстановление

Единственная подписка выбирает `state=pending`, сортирует по `availableAt` и читает техническую порцию. Claim транзакционно переводит запись в `processing`, фиксирует lease/token/attempt. После claim первая порция освобождается для следующих событий; размер порции не ограничивает число семей. Будущие retries сортируются после готовой работы и не блокируют новые события.

Истёкшие processing leases восстанавливаются ограниченными служебными чтениями, без второй subscription. Dispatcher хранит устойчивые результаты fanout; ack возможен только после сохранения всех применимых результатов. Сбой между Telegram enqueue и task enqueue повторяет незавершённую стадию идемпотентно. Доставка Telegram и завершение педагогической работы имеют собственные receipts; queue ack не выдаётся за их фактическое завершение.

Повторы ограничены, причины `blocked`/`dead_letter` видимы, старый lease не может подтвердить новый claim. Остановка снимает одну subscription, прекращает новые claims и дожидается текущих операций в пределах бюджета. Телеметрия различает публикацию, ожидание, claim, адресную подготовку, маршрутизацию, dispatch и фактическую доставку. Персональные payload не экспортируются.

## Доступ и приватность

Клиент создаёт только разрешённые события своей текущей семьи/ребёнка в atomic source write. Rules проверяют точный источник через getAfter, actor UID и допустимые поля/начальное состояние. Клиент не читает глобальную очередь, не назначает себе system actor, не меняет lease/ack и не переписывает принятое событие. Backend использует действующие owner/membership predicates; sourceRef не является произвольным разрешением чтения.

## Миграция и проверки

Исторический backfill сохраняет semantic identity и прежние receipts: уже обработанная работа не рассылается повторно. Старые клиенты без producer требуют явной совместимости/обнаружения пропущенных событий; подготовленный producer не считается завершённой миграцией. Основной поток после переключения работает через очередь. Коллекционные источники остаются только явными диагностическими инструментами либо обозначенным временным reconciliation, без фонового множества подписок.

Проверки: atomic source+event write; actor/scope spoofing; запрещённые client reads/updates; повтор operationId; разные действия одной работы; больше одной порции; fencing/expired lease; сбой между fanout стадиями; будущий retry перед новой работой; неизвестный тип; работа всех маршрутов; отсутствие LLM цикла на guidance/review; ровно одна dispatcher subscription; отсутствие document discovery subscriptions в постоянном runtime; unsubscribe/drain; неизменные данные не создают работу. Live выпуск требует актуального main, индексов/Rules, producer версии приложения, установленного worker и адресного event→receipt→task readback. Незавершённые части отмечаются отдельно.
