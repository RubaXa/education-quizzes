# Обнаружение изменений и сверка состояния Education

Статус: **контракт процесса; педагогический наблюдатель и пробуждение сессии ещё не реализованы**. Работающий `storage:worker` обслуживает передачу фото на Яндекс.Диск и не выполняет проверку работы. Связанные контракты: [порт МЭШ](../school-diary/README.md), [план из МЭШ](plan-generation.md), [очередь фото](../materials/storage-privacy.md#review-queue), [dashboard](../school-diary/dashboard.md), [адресные события](../notifications/inbox.md).

## Зачем нужен отдельный наблюдатель

Пустая проверка не должна запускать модель и тратить токены. Небольшой локальный процесс может читать изменения Firestore и по доступному окну проверять МЭШ, сохранять своё состояние на диске и передавать агенту **только подтверждённое новое событие**. Это не расписание задач Codex и не автоматическая педагогическая оценка. Пока нет проверенного API для адресного пробуждения существующей сессии, процесс может только подготовить событие и сигнал оператору; нельзя писать в документации, что Codex уже пробуждается напрямую.

## Сигнал и подтверждённое изменение

| Источник | Дешёвый сигнал | Сверка перед действием |
| --- | --- | --- |
| Фото и запрос помощи в Firebase | Подписка на допустимые изменения или восстановление курсора после перезапуска | Прочитать живой `submissions inbox` **без фильтра даты**, владельца, `childId`, день, `taskId`, ревизию, все страницы и `uploadIds`. Новое фото готово только при `pending` и подтверждённом файле на Диске. |
| МЭШ | Ограниченная проверка доступного горизонта и периода оценок через адаптер | Сравнить полный новый снимок с последним полным снимком по устойчивым ID и содержательным полям. Изменившийся `fetchedAt`, порядок выдачи, пустой/неполный ответ и сетевой сбой не являются новым ДЗ или отменой. Сомнительную дельту перечитать. |
| Результаты тестов | Изменение статуса/попытки Firestore | Сверить владельца, `testId`, последнюю попытку, ключ и ревизию; спорный ответ сначала проверить по условию. |

Снимок МЭШ хранится вместе с временем, полнотой, исходным ID и нормализованным отпечатком значимых полей. Хэш служит сигналом для точного сравнения, а не доказательством смысла изменения. Сохраняются прежняя и новая версии; при сбое прежний полный снимок остаётся действующим с видимым возрастом. Периодический обход МЭШ нужен, потому что подтверждённого канала событий от него нет; частота и предел запросов выбираются по фактическим ограничениям источника. Редактируемый исходник плана сейчас локален, каноническая версия задания с полной историей отмен ещё не реализована.

## Один набор фото — один разбор

Набор определяется `childId + dayDate + taskId` и включает **все** ожидающие фото, в том числе снимки с несколькими номерами. Начинать содержательную проверку можно не раньше чем через 30 секунд после последней загрузки; после этого очередь перечитывается без фильтра даты, чтобы собрать поздние страницы. До старта сверяются владелец, ID и ревизия. Если `processing` относится к тем же `uploadIds`, его фаза не `paused`, а `updatedAt` моложе 10 минут, второй разбор не запускается. После истечения времени это лишь повод перечитать фактическое состояние, не разрешение безусловно перезаписать результат. Для нескольких одновременно работающих процессов нужна атомарная аренда/захват в Firestore; одного поля `processing` недостаточно для гарантии отсутствия гонки.

Оригиналы находятся на Яндекс.Диске, закрытые копии для разбора — в `.local/`. Фазы `download → source → review → publish` и итог публикуются в Firestore; при неразрешимой сейчас проблеме записывается `paused` с конкретной причиной и нужным действием. `reviewed` означает завершённый разбор фото, а учебный вердикт хранится отдельно. Повторный запуск сверяет уже опубликованный результат и не создаёт фиктивной новой попытки. Точное условие, происхождение критерия и история предыдущих попыток обязательны до вердикта; методическая помощь не расширяет задание учителя.

## Восстановление и выпуск

После включения Mac процесс восстанавливает курсор и перечитывает живое состояние. Пропущенные изменения не выводятся из одного локального уведомления. Отсутствие доступа к МЭШ, Firebase или Диску фиксируется как сбой соответствующей границы; уведомление родителю требуется для реального результата, сбоя или действия, а пустой проход остаётся тихим. При восстановлении нельзя запускать несколько конкурирующих разборов одного набора.

Операторские изменения содержания идут в Firestore и должны появляться в открытых ролевых страницах по подписке. `publish:pages` нужен при изменении кода движка. Состояния «назначено», «сообщено выполненным», «фото передано», «проверяется», «проверено», «критерий спорен» и «отменено» различаются; один зелёный значок файла не закрывает задание автоматически. При повторной генерации сверяются все связанные страницы **одной даты сдачи**: доказанный результат не становится новым долгом, а указатель на файл не превращается в отдельное действие.

## Граница текущей реализации

`diary sync` сохраняет полные снимки и diff; `submissions inbox` читает живую очередь и `processing`; `day build/publish` формирует и выпускает страницу; клиент подписан на Firestore; `storage:worker` переносит новые фото. Автономного наблюдателя МЭШ/очереди с курсором, устойчивого канала пробуждения Codex и атомарной аренды педагогического разбора нет. До их появления полный педагогический цикл запускается вручную по [навыку синхронизации](petr-private:skills/education-sync/SKILL.md) либо по конкретной просьбе проверить работу.
