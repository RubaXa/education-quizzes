# Хранение медиа и приватность

Связанные контракты: [материалы](materials.md), [страница дня](day-page.md#photo-preview), [владение состоянием](access-and-state.md#state), [масштабирование ссылок и архива](../architecture/family-artifact-access.md). Карта: [README](README.md).

<a id="privacy-boundary"></a>
## Граница публичного репозитория

В `main`, `gh-pages` и истории Git не должны находиться персональные данные ребёнка, реальные работы, фото, страницы учебников, токены, привязка конкретного задания к конкретной семье или локальные снимки дневника. `.local/` и `public/materials/` игнорируются, но одного `.gitignore` недостаточно для уже опубликованной ветки или старых коммитов. Если файл был в истории, удаление новым коммитом не делает историю приватной.

Хук `scripts/check-privacy.mjs` блокирует случайное добавление типовых медиа, локальных файлов, имён и токенов в исходную ветку. Перед push он проверяет всю достижимую историю, а скрипт публикации проверяет историю ветки сайта и останавливается, если сборка содержит `materials/`. Эти проверки дополняют просмотр изменений: они не распознают любой возможный персональный текст.

Публичная ссылка Яндекс.Диска открывается любым обладателем URL. Её показывают только в странице с токеном доступа; она не помещается в исходный код или документацию. Полные PDF учебников не публикуются — только требуемые изображения страниц.

<a id="upload-queue"></a>
## Временная очередь фото

Статический сайт не содержит OAuth-токен Яндекс.Диска. После выбора фото браузер сохраняет **исходный файл без сжатия** в локальном IndexedDB и создаёт в `dayUploads` только метаданные: владельца через токен дня, `taskId`, ревизию, UID устройства, MIME, размер, SHA-256 и `status: requested`. Локальный доверенный процесс `npm run storage:worker` сверяет личную сессию, семью, ребёнка и актуальное задание, получает одноразовый адрес записи Яндекс.Диска и помещает его в этот документ. Браузер делает `PUT` исходных байтов **непосредственно на Яндекс.Диск**. Процесс скачивает файл, сверяет размер, сигнатуру и SHA-256, публикует ссылку и лишь затем меняет статус на `pending`. В Firestore нет изображения, base64 или производного кропа. Педагогический разбор скачивает подтверждённый файл с Диска отдельно.

При выборе нескольких файлов каждый сразу создаёт отдельную заявку с тем же `taskId`; клиент не ждёт завершения первого перед отправкой второго. Статусы `requested`, `awaiting-upload` и `uploaded` означают передачу/подтверждение файла; `pending` — ожидание педагогической проверки, `reviewed` — законченный разбор. При перезагрузке страницы браузер возобновляет незавершённую передачу из IndexedDB. Если Mac выключен, оригинал остаётся только на том устройстве, где его выбрали; локальный процесс возобновляется при запуске Mac, а передача — когда страница на этом устройстве вновь открыта. Другой телефон не может восстановить исходные байты по метаданным Firestore. Фотография становится готовой к проверке только после подтверждения Диска.

Адрес записи выдаёт только доверенный локальный процесс; OAuth-токен не попадает в JavaScript сайта. Адрес кратковременен и виден только устройствам семьи по правилам Firestore. Для семей вне этого Mac потребуется постоянный доверенный сервис выдачи адресов с изоляцией собственных хранилищ и прав; это отдельное архитектурное решение.

На текущем Mac `npm run storage:install-worker` устанавливает LaunchAgent `com.petr.education.upload-worker` с автозапуском и восстановлением после выключения. Из-за защиты macOS служебный код и отдельные копии секретов размещаются в закрытой папке `~/Library/Application Support/PETR/upload-worker/`; при обновлении кода запусти установку повторно. `launchctl print gui/$(id -u)/com.petr.education.upload-worker` показывает состояние; журналы лежат в `.local/` этой служебной папки. Обычный `npm run storage:worker` пригоден для ручной отладки, но не должен работать одновременно с LaunchAgent. Сам процесс не оценивает работу и не создаёт тесты.

Ранее уже созданные документы с `dataUrl` поддерживаются только миграционной командой `storage sync`; новые клиентские правила запрещают такие записи. CORS прямого `PUT` подтверждён для текущего адреса загрузки Яндекс.Диска браузерным preflight с разрешённым Origin сайта; работу на конкретном iPhone следует проверить отдельно.

<a id="photo-deletion"></a>
## Удаление фото до проверки

Владелец связанного ребёнка может удалить запись в любом состоянии до `reviewed`. Правило Firestore сверяет активную семейную сессию и `dayOwners`; клиент может менять только статус на `deleted` и время удаления. Локальная копия в IndexedDB удаляется. Проверенная запись через клиент неизменяема. Удалённая запись сразу скрыта со страницы, из dashboard и из очереди педагогического разбора.

Если фото уже на Яндекс.Диске, локальный процесс закрывает публичную ссылку, переносит файл работы в корзину и очищает служебную запись после срока действия выданной ссылки записи. Ошибка удаления оставляет tombstone для повтора. Прежняя публичная ссылка может короткое время оставаться доступной до обработки удаления.

<a id="review-publication"></a>
## Публикация педагогического разбора

Агент сохраняет закрытый `.local/review-....json` с датой, `taskId`, `planRevision` и `uploadIds`. До скачивания запускает `npm run submissions -- progress .local/review-....json download`; затем по ходу работы переключает этапы `source`, `review`, `publish` той же командой. Она проверяет владельца, план и все ожидающие фото и записывает в `dayProgress/{studentToken}/items/{taskId}` фазу, текст для интерфейса, время начала и последнего изменения. Если работа остановилась, агент записывает `paused`; интерфейс перестаёт показывать активную анимацию. Эти команды меняют только Firestore, не публикуют сайт.

После проверки агент добавляет в тот же закрытый JSON итог, подпункты, следующее действие и источник и запускает `npm run submissions -- review .local/review-....json`. Команда повторно проверяет владельца через `dayOwners`, ревизию плана, связь каждого фото с заданием, его статус `pending` и наличие на Диске. Один пакет Firestore переводит все фото этого разбора в `reviewed` и записывает результат в `dayProgress/{studentToken}/items/{taskId}`, убирая активный этап. Если условие или набор фото изменились, запись отклоняется до повторной сверки. Клиентские правила запрещают ученику менять статус проверки; интерфейс получает разбор через живую подписку. Предыдущие разборы хранятся в истории документа. **Выпуск сайта не входит в обычный цикл проверки работы.**

<a id="multi-task-photo"></a>
### Один снимок — несколько решений

Кнопка загрузки остаётся внутри каждой задачи. Исходный `taskId` снимка обозначает **точку входа**, а не границу его содержания: на снимке могут быть решения нескольких номеров. Разборщик осматривает весь оригинал и фиксирует только реально видимые номера. При таком случае закрытый JSON содержит общий `date`, `planRevision`, уникальные `uploadIds`, массив `photoCoverage` (`uploadId`, `taskIds`, словесное `observed`) и массив `reviews` с отдельным `taskId`, точными `uploadIds`, вердиктом и подпунктами для каждого номера. Номера в `photoCoverage` обязаны точно совпадать с использованными в `reviews`; пустая или догаданная привязка запрещена. Этот формат применяется и когда на фото лишь один номер, отличный от кнопки загрузки.

`submissions progress` публикует этап для каждого номера и временное `processingTaskIds` на снимке, `submissions review` одной операцией записывает отдельные результаты и историю в `dayProgress`, а в метаданные **одного** снимка записывает `coveredTaskIds` и `coverageNote`, убирая временную привязку. Оригинал остаётся один на Яндекс.Диске. Открытые карточки и dashboard через подписку Firestore показывают снимок у всех найденных номеров уже во время разбора, а после него — у всех подтверждённых; до классификации он виден в карточке отправки. Если на снимке номера не видно, не приписывай ему ни выполнение, ни ошибку этого номера. Отсутствие снимка для номера означает неизвестное выполнение. Старый JSON одного задания и старые фото без `coveredTaskIds` продолжают работать по исходному `taskId`.

У письменного математического пункта (включая отдельный номер геометрии или спецкурса) издатель требует `mathReasoning`: `answer`, `argument`, наблюдаемую запись `observed` и, когда ход неполон или отсутствует, один `minimumNeeded`. `verified` допустим при верном ответе и достаточном ходе. Если ответ верен, но ход требуется и не показан, итог `partial`; это не оценка ответа как неверного. Значение `argument: not-required` возможно только с `criterionSource` из точного требования учителя. Эти поля публикуются вместе с итогом и остаются в истории попыток. [Подробный критерий](../research/photo-math-solution-review.md).

<a id="review-queue"></a>
## Очередь разбора с владельцем и заданием

Ученическое фото становится `pending` в `dayUploads/{studentToken}/files/{uploadId}` лишь после подтверждённой передачи на Диск. Запись содержит точный `taskId`, ревизию плана, UID загрузившего устройства, время, SHA-256 и путь файла. Отдельный закрытый документ `dayOwners/{studentToken}` связывает страницу дня с `familyId`, `childId` и датой. `family attach-current-day` заполняет карту для опубликованных дней; браузер не читает её. Само задание и точный текст МЭШ берутся из `dayPages/{studentToken}`. Из имени файла и предмета связь не угадывают.

`npm run submissions -- inbox [YYYY-MM-DD]` находит все ожидающие работы и показывает ребёнка, дату, предмет, точное задание, состояние файла и необходимость ручной сверки. `relatedTasks` перечисляет ID соседних номеров того же листа **только как справочник**, а не как доказанное содержание фото. `npm run submissions -- pull [YYYY-MM-DD]` скачивает их в закрытую, исключённую из Git папку `.local/submission-inbox/` вместе с манифестом. Если задание исчезло или его ID не совпадает, работа остаётся в очереди с `needs-manual-link`; её не относят к похожему заданию автоматически. Скачивание не меняет `pending` и не считается педагогическим разбором.

Перед разбором агент сверяет исходное условие и вложения, затем фиксирует результат и только после этого меняет статус работы. Локальный процесс передаёт фото на Диск; педагогический разбор остаётся отдельным действием. Новое поле `deviceUid` сохраняет устройство загрузки и проверяется по семейной сессии; это не заменяет учебную оценку или авторство решения.

<a id="upload-verification"></a>
## Проверка полного пути фото

`node scripts/verify-upload-flow.mjs YYYY-MM-DD` сохраняется для сверки ранее перенесённых файлов. Его режим `--exercise` использует устаревшую схему записи `dataUrl` и после ужесточения правил не подходит для нового пути; для нового пути проверяй запрос метаданных, выдачу адреса, прямой PUT, подтверждённый SHA-256 и видимость результата на телефоне. Автоматические проверки контракта находятся в `storage/direct-upload.test.mjs`; сквозная проверка на реальном iPhone пока открыта.

Новая работа находится в очереди педагогического разбора при `status: pending` и только после сверки файла на Диске. `day pull` скачивает её для агента, но не выполняет OCR и не запускается сам при появлении фото. `storage:worker` автоматически обслуживает **передачу файлов**, а не педагогическую проверку.

<a id="storage-migration"></a>
## Повторная миграция и сверка

`storage sync` обрабатывает и ранее перенесённые записи: повторно сверяет файл на Диске, затем удаляет оставшуюся копию из Firestore. Если контрольная сумма недоступна или не совпадает, копия не удаляется и операция сообщает об ошибке. `storage sync-pages` обновляет ссылки материалов и убирает устаревшие поля локального кэша страниц из опубликованных планов.

После переноса нужно проверять **историю** обеих публикуемых веток, а также готовую сборку сайта. Если приватный файл уже попал в Git, удаление из очередного коммита не устраняет старые объекты; для очистки требуется отдельная проверенная операция переписывания истории и повторная сверка удалённого репозитория.

Если разбор был приостановлен именно из-за переноса фото, `storage sync` после сверки **всех** фотографий этого набора удаляет устаревшую техническую паузу. Фото остаются в очереди педагогической проверки; пауза по другой причине сохраняется. Изменение статуса приходит в открытую страницу через подписку Firestore.

<a id="private-archive"></a>
## Закрытый архив локальных оригиналов

`npm run archive:local` из приложения переносит изображения работ, PDF учебников и другие локальные медиа семейного проекта в закрытую папку `app:/PETR/Личный архив/` на Яндекс.Диске. Для каждого файла сохраняет путь, размер, MD5 и SHA-256 в игнорируемом `.local/archive-manifest.json`; повторный запуск сверяет оригинал и удалённый файл. Скрипт **не публикует ссылки** на работы и полные PDF. Локальные оригиналы остаются для индексации и педагогической проверки, но корневой Git PETR игнорирует весь семейный архив.
