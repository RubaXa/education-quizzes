# Хранение медиа и приватность

Связанные контракты: [материалы](materials.md), [страница дня](day-page.md#photo-preview), [владение состоянием](access-and-state.md#state). Карта: [README](README.md).

<a id="privacy-boundary"></a>
## Граница публичного репозитория

В `main`, `gh-pages` и истории Git не должны находиться персональные данные ребёнка, реальные работы, фото, страницы учебников, токены, привязка конкретного задания к конкретной семье или локальные снимки дневника. `.local/` и `public/materials/` игнорируются, но одного `.gitignore` недостаточно для уже опубликованной ветки или старых коммитов. Если файл был в истории, удаление новым коммитом не делает историю приватной.

Хук `scripts/check-privacy.mjs` блокирует случайное добавление типовых медиа, локальных файлов, имён и токенов в исходную ветку. Перед push он проверяет всю достижимую историю, а скрипт публикации проверяет историю ветки сайта и останавливается, если сборка содержит `materials/`. Эти проверки дополняют просмотр изменений: они не распознают любой возможный персональный текст.

Публичная ссылка Яндекс.Диска открывается любым обладателем URL. Её показывают только в странице с токеном доступа; она не помещается в исходный код или документацию. Полные PDF учебников не публикуются — только требуемые изображения страниц.

<a id="upload-queue"></a>
## Временная очередь фото

Статический сайт не имеет токена Яндекс.Диска. После выбора фото браузер кладёт сжатую копию во временный документ `dayUploads` со статусом `pending`. Локальная команда `storage sync YYYY-MM-DD` переносит её на Диск, сверяет размер и MD5, записывает URL и удаляет поля `dataUrl` и исходного имени **в одном обновлении документа**. При ошибке исходная копия остаётся в очереди для повтора. Педагогический разбор запускается отдельно командой `day pull`, которая скачивает уже перенесённый оригинал с Диска.

При выборе нескольких файлов каждый сразу создаёт отдельный документ с тем же `taskId`; клиент не ждёт завершения первого перед отправкой второго. Сбой одной записи не блокирует остальные. Часы на миниатюре означают ожидание педагогического разбора, а не ожидание нажатия «Отправить». Перенос из Firestore на Диск по-прежнему требует запуска локальной команды.

Это временное хранение в Firestore до ручного запуска, а не прямой браузерный upload на Диск. Для полного отказа даже от временной копии потребуется доверенный серверный посредник; нельзя помещать OAuth-токен в JavaScript сайта.

<a id="photo-deletion"></a>
## Удаление фото до проверки

Владелец связанного ребёнка может удалить только запись со статусом `pending`. Правило Firestore сверяет активную семейную сессию и `dayOwners`, допускает только переход `pending → deleted` и одновременно удаляет сжатое изображение и имя файла из документа. Запись `reviewed` через клиент неизменяема. Удалённая запись сразу скрыта со страницы, из dashboard и из очереди педагогического разбора.

Если фото уже на Яндекс.Диске, запись временно сохраняет только путь и контрольную сумму для очистки. Следующий `storage sync YYYY-MM-DD` закрывает публичную ссылку, переносит файл работы в корзину Диска и удаляет служебную запись Firestore. Если файл с тем же путём используется другой действующей работой, общий файл сохраняется. Ошибка удаления оставляет запись для повторной синхронизации; удалённые снимки никогда не возвращаются в очередь разбора. Между нажатием и синхронизацией прежняя публичная ссылка может ещё работать.

<a id="review-queue"></a>
## Очередь разбора с владельцем и заданием

Ученическое фото сохраняется в `dayUploads/{studentToken}/files/{uploadId}` с точным `taskId`, временем загрузки и `status: pending`. Отдельный закрытый документ `dayOwners/{studentToken}` связывает прежнюю страницу дня с `familyId`, `childId` и датой. `family attach-current-day` заполняет эту карту для опубликованных дней; браузер не читает её. Само задание и точный текст МЭШ берутся из `dayPages/{studentToken}`. Из имени файла и предмета связь не угадывают.

`npm run submissions -- inbox [YYYY-MM-DD]` находит все ожидающие работы и показывает ребёнка, дату, предмет, точное задание, состояние файла и необходимость ручной сверки. `npm run submissions -- pull [YYYY-MM-DD]` скачивает их в закрытую, исключённую из Git папку `.local/submission-inbox/` вместе с манифестом. Если задание исчезло или его ID не совпадает, работа остаётся в очереди с `needs-manual-link`; её не относят к похожему заданию автоматически. Скачивание не меняет `pending` и не считается педагогическим разбором.

Перед разбором агент сверяет исходное условие и вложения, затем фиксирует результат и только после этого меняет статус работы. Перенос фото на Диск командой `storage sync` и педагогический разбор независимы. Пока эти команды запускаются вручную, очередь не является автоматическим OCR или уведомлением. Прежний способ загрузки не сохраняет, какой именно взрослый или ребёнок нажал кнопку: известны владелец работы и задание, но не автор действия.

<a id="upload-verification"></a>
## Проверка полного пути фото

`node scripts/verify-upload-flow.mjs YYYY-MM-DD` только читает статусы `dayUploads` и сверяет размер и MD5 каждого уже перенесённого файла с Яндекс.Диском. Режим `--exercise` выбирает доступное письменное задание, создаёт отдельную тестовую PNG через клиентский Firestore SDK, запускает `storage sync`, затем `day pull` и сверяет полученные байты. После проверки удаляются только тестовая запись и тестовый файл; при прерывании останется закрытый маркер `.local/upload-flow-check-recovery.json`, а `--cleanup` повторит очистку. Проверку на реальном телефоне она не заменяет.

Новая работа находится в очереди педагогического разбора при `status: pending` и после переноса на Диск. `day pull` скачивает её для агента, но не выполняет OCR и не запускается сам при появлении фото. На статическом сайте с закрытым OAuth-токеном нет автоматического переноса: до запуска `storage sync YYYY-MM-DD` новая фотография хранится во временной очереди Firestore. В интерфейсе эти стадии обозначены отдельно.

<a id="storage-migration"></a>
## Повторная миграция и сверка

`storage sync` обрабатывает и ранее перенесённые записи: повторно сверяет файл на Диске, затем удаляет оставшуюся копию из Firestore. Если контрольная сумма недоступна или не совпадает, копия не удаляется и операция сообщает об ошибке. `storage sync-pages` обновляет ссылки материалов и убирает устаревшие поля локального кэша страниц из опубликованных планов.

После переноса нужно проверять **историю** обеих публикуемых веток, а также готовую сборку сайта. Если приватный файл уже попал в Git, удаление из очередного коммита не устраняет старые объекты; для очистки требуется отдельная проверенная операция переписывания истории и повторная сверка удалённого репозитория.

<a id="private-archive"></a>
## Закрытый архив локальных оригиналов

`npm run archive:local` из приложения переносит изображения работ, PDF учебников и другие локальные медиа семейного проекта в закрытую папку `app:/PETR/Личный архив/` на Яндекс.Диске. Для каждого файла сохраняет путь, размер, MD5 и SHA-256 в игнорируемом `.local/archive-manifest.json`; повторный запуск сверяет оригинал и удалённый файл. Скрипт **не публикует ссылки** на работы и полные PDF. Локальные оригиналы остаются для индексации и педагогической проверки, но корневой Git PETR игнорирует весь семейный архив.
