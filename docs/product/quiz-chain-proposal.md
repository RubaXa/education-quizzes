# Цепочка тестов: компактная история и итоговая проверка

**Статус: предложение для обсуждения, 16.10.2026. Не действует в опубликованном продукте.** Основание: запрос родителя о кнопке после 100%, проверке полной темы, обратном порядке истории и разборе внутри карточки. [Исследование и границы доказательств](../research/quiz-history-and-consolidation.md). Действующий контракт до согласования — [quizzes.md](quizzes.md), граф — [assessment-decision-graph.md](assessment-decision-graph.md).

## Обнаруженные причины

`QuizCard.tsx` показывает кнопку запроса только при `points < maxPoints`; 100% исключены намеренно прежним правилом. `earlier.map` выводит историю в причинном порядке исходный → продолжения. `QuizCardAttempt` содержит общий балл, но теряет вычисленные по вопросам исходы `grade`; число верных ответов из балла восстановить нельзя. Исходный тест рассматриваемого примера содержит семь вопросов на одиннадцать баллов, а не одиннадцать вопросов. Исправление одной видимости кнопки не создаст режим широкой проверки: очередь, закрытый план и валидатор также должны различать его и работу по ошибкам.

## Цели и неизменные границы

- Один общий `QuizCard` на странице дня и в списке тестов, общие CSS и ViewModel; предмет меняет источники и содержимое разбора.
- Родитель видит вопросы, верные/частичные/неверные ответы, процент и время в одном месте. Кнопка строки раскрывает разбор без ухода со страницы. Время — только иконка часов, по нажатию четыре прежних поля.
- Исходное задание учителя, страницы и история сохраняются. Завершённые ответы не переписываются; активная попытка и переключатель обязательности следуют действующему контракту без видимой подписи тумблера.
- Существующие ограничения раскрытия ответов действуют и внутри карточки. Родительский доступ не открывает ключи ребёнку автоматически. Перенос ResultCard требует общей безопасной проекции, а не копии UI с другими правами.

## Два макета для выбора

**Строки с разбором (предлагаемый основной):** текущая оболочка последнего теста, под ней постоянно видимые компактные строки истории. Название занимает свою строку, справа часы; в следующей строке одинаковая сетка «вопросов / верно / с ошибкой / % баллов». Баллы отдельно подписаны, если они отличаются от числа вопросов. Нажатие заголовка открывает ошибки непосредственно под этой строкой. Нет внешнего аккордеона с вложенными аккордеонами. При длинной истории показываются последние пять и действие «Ещё N».

**Таблица попыток:** заголовок и общая сводка те же; прошлые попытки — сравнительная таблица «тест / верно из вопросов / баллы / % / часы». Нажатие названия выбирает разбор под таблицей. Она компактнее по высоте, но на 320px хуже помещает длинные названия. Нельзя уменьшать основной текст до нечитаемого размера.

Ссылка на полный результат сохраняется внутри раскрытого разбора как вторичное действие. В последней попытке кнопка «Разбор» раскрывает те же сведения, заменяя необходимость внешнего перехода. Иконка итогового запроса находится перед ней. В макете условные даты и содержание пояснений помечены как демонстрационные.

## Данные, проценты и сортировка

Единый исход по вопросу: `correct | partial | incorrect | unanswered | pending | excluded`. Частичный ответ не считается полностью верным; отдельный счётчик показывается только при наличии таких ответов. `answered` не заменяет `correctCount`. Непроверенная попытка получает «Ждёт проверки», неизвестные числа не подставляются нулями.

Процент попытки = округлённое `100 × earned / possible`, как сейчас; это процент **баллов**, не доля вопросов. Общий процент цепочки = `100 × sum(earned) / sum(possible)` по полностью проверенным попыткам, включая последнюю. Рядом число включённых тестов; ожидающие проверку перечислены отдельно. Среднее процентов не используется. В примере вся цепочка — 18/32 балла, 56%; отдельно 16 верных из 26 вопросов. Эта историческая статистика не переводит текущие 100% в «не выполнено».

Причинная `quizChain` остаётся исходный → продолжения: от неё зависят последний тест, корень и обязательность. Только копия представления истории сортируется по `submittedAt DESC`; при отсутствующей дате — `createdAt DESC`, затем стабильный `testId`. Поздняя запись ручного разбора в `updatedAt` не переставляет старую попытку наверх. Открытая текущая попытка остаётся сверху; дата «Начат» имеет прежний смысл первой записи ответа. Завершённая история не сортируется по дате просмотра.

## Новый режим: итоговая проверка темы

Предлагаемое имя в модели — `topic-consolidation`; обычный `targeted-followup` сохраняет смысл адресного продолжения. Ниже 85% после предметной сверки действует прежний автоматический разбор ошибок. При проходном результате родитель может запросить итоговую проверку, включая 100%; она не возникает автоматически и не аннулирует правильные ответы. Для 85–99% сохраняется возможность выбрать адресную работу по ошибкам; тип запроса должен быть явным.

Итоговая проверка рекомендуется, если в цепочке был полностью проверенный результат ниже 50% либо не менее двух попыток ниже 85%, а широкая проверка текущей ревизии темы ещё не подтверждена. Короткие 100% после нескольких ошибок — именно такой случай. Рекомендация не создаёт новый обязательный долг сама по себе. Нажатие родителя фиксирует тип запроса, показывает ожидание и переводит самопроверку в «надо доделать» по прежнему правилу запросов. Генерация идёт в Education Sync. Повторное нажатие не создаёт второй запрос; при сбое запись не изображается успешной.

## Воспроизводимый план и объём

Вход: зафиксированная ревизия назначения МЭШ и источников, корень цепочки, полные проверенные исходы, подтверждённая карта навыков, версия политики и банка. Семантически одинаковый навык имеет один `skillId` независимо от подписи темы. Старые названия вроде «Группы духовенства» и «Белое и чёрное духовенство» требуют проверенного сохранённого сопоставления; сравнение строк не доказывает разные навыки.

1. `N0` — число вопросов исходного теста; баллы вместо него не подставляются. `K` — минимум пунктов по утверждённой карте всей назначенной темы. База `B = max(N0, K)`.
2. `H` — различные навыки с подтверждёнными ошибками за всю цепочку; дефекты вопроса, неразборчивый ответ и технические нули исключаются до планирования. `R = min(3, |H|)` — дополнительные проверки наиболее частых ошибок.
3. `S = 1` — успешная отдельная прежняя тема. `T = 1` — перенос в новый контекст. Общий размер **`N = B + R + S + T`**. Если план требует более 100 вопросов, выпуск блокируется до явного разделения темы, без тихого усечения покрытия.
4. База покрывает все обязательные цели карты темы; усиления не заменяют ни одной. Приоритет H: число подтверждённых ошибок убывает, затем дата последней ошибки убывает, затем `skillId` по возрастанию. Одна многократно повторённая ошибка не заполняет весь тест. Школьные требования берутся из МЭШ; интервальное повторение и перенос обозначаются как наши тренировочные элементы.
5. В обсуждаемом примере `N0=7`, исторических слабых навыков не менее четырёх (духовенство, аббат, исламская хронология, Рим); `R=3`. Если проверенная карта темы укладывается в семь базовых пунктов, получается **7+3+1+1=12**. Это предварительный объём; если полного охвата нужно больше семи пунктов, N увеличивается по той же формуле. Полная карта §§ 7–8 ещё должна пройти источник перед созданием теста.

Одинаковые входы, policyVersion, sourceRevision, skillMapRevision и bankRevision дают одинаковый план, порядок целей и questionIds. Вариант из проверенного банка выбирается стабильным seed от этих ревизий и ID завершённой попытки. Генерация LLM без банка сама по себе не детерминирована: недостающие варианты сначала создаются, предметно проверяются и фиксируются одной ревизией; повторный запуск использует сохранённый пакет. Пустой банк или отсутствие надёжной карты блокируют выпуск с конкретной причиной. Изменение входа создаёт новую ревизию, а не переписывает уже начатый тест.

Успешная широкая попытка по порогу 85% подтверждает результат этой проверки. Для долговременного освоения отдельно нужна отложенная проверка; семейное ДЗ не объявляется невыполненным только из-за отсутствия отложенного замера.

## Связь с кодом и чтениями

После согласования: `QuizCard.tsx/.css` — сетка и раскрытие; `quizCardViewModel.ts` — отдельный порядок представления и точные счётчики; `watchQuizOutcome.ts` — передача уже вычисленных `grade` исходов вместо потери этой информации; общий ResultCard — отображение с существующими правами. Сводка и часы используют уже загруженные данные; раскрытие не запускает подписку для каждой строки заново. Данные подробного разбора читаются адресно при раскрытии только если их нет в общем ролевом кэше, с единственным владельцем подписки и отпиской.

`store.ts`, `firestore.rules`, `sync-queue.mjs`, `assessment/*` и CLI должны передавать явный mode/topic revision, сохранять идемпотентный запрос и выполнять readback опубликованного итогового теста. Одна UI-кнопка без этих изменений недостаточна. Запрет новых фоновых сканов и общих коллекционных чтений ради сортировки/часов/раскрытия включается в матрицу чтений.

## Критерии будущих интеграционных тестов

- Родитель видит запрос итоговой проверки при полностью проверенных 100%; ребёнок не получает этого управляющего действия.
- 7 вопросов / 11 баллов отображаются раздельно; 4 верных не превращаются в 6; частичные, пропущенные и pending различаются.
- Текущий результат 100%, общий 18/32=56%; среднее процентов и 13/27 без последней попытки не подписаны как вся цепочка.
- История завершений идёт 7/9 → 0/7 → 6/11; начатый позже старый тест сортируется по завершению; неизвестные/равные даты дают устойчивый порядок.
- Поздний manual review обновляет счётчики и общий процент без перестановки по updatedAt; изменение последнего не меняет корень обязательности.
- Ошибки открываются на месте, часы показывают прежние четыре поля; два варианта экрана используют один ролевой разбор, без утечки готовых ответов ребёнку.
- Запрос сохраняется один раз, показывает ожидание, не заявляет готовность теста; старые ответы и исходное задание сохраняются. Ошибка записи показывает правду, повтор безопасен.
- `N0=7,K=7,|H|=4` даёт 12; `K=10` даёт 15; пустая/сомнительная история не выдумывает ошибки. Один и тот же набор входов и банка даёт одинаковые IDs при повторе.
- Короткий результат 100% не урезает базу широкой проверки до пяти; после полного провала адресное продолжение подчиняется действующему правилу без потери ошибок.
- 320/390/540px: сетка, длинные заголовки, часы, проценты, ожидание и раскрытый разбор помещаются; новые чтения и подписки на открытие часов/сортировку равны нулю.

## Следующее решение

Выбрать композицию и утвердить правило итоговой проверки. После этого обновить действующие спецификации и событийное правило, реализовать через общий компонент/CLI, запустить перечисленные регрессии и опубликовать с обратной проверкой. Этот черновик не разрешает автоматически выпускать новый тест или менять текущий интерфейс.
