# Сертификация пути карточки задания

Этот контракт дополняет [граф выбора](card-generation-policy.md#decision-graph) и [сквозной протокол](education-pipeline.md). Одинаковые данные источника должны давать одинаковые границы заданий, действия и состояние карточки независимо от предметной страницы. Предмет меняет способ разбора, а не правила учёта источника.

## Матрица переходов

| Вход | Решение | Инвариант перед публикацией | Проверка |
| --- | --- | --- | --- |
| Записи МЭШ | Отдельный `taskId` на каждое действительное назначение; указатель «Файл здесь» объясняется явно | Все ID и точные тексты представлены, ни один не слит молча | `assertSourceAligned`, сборка двух назначений |
| Вложения урока | Файл принадлежит конкретной записи либо связь не установлена | Один файл не копируется в обе карточки без доказательства общего назначения | `teacherAttachmentOwnershipErrors` |
| Полный лист учителя | Оператор отдельно осматривает каждый оригинал и фиксирует `sourceInventory.sources[]`: `sourceRef`, SHA-256, ссылку на запись сверки и состав групп | Для новой сверенной математической карточки опись обязательна для **каждого** прикреплённого файла; отсутствие номеров объяснено отдельно | `sourceInventoryErrors` в `day validate` |
| Группы листа | Несколько вариантов → разные ID и повторяемые печатные номера допустимы только между вариантами | Множество `variantId:number` в карточке в точности совпадает с описью | `practiceVariantErrors`, `sourceInventoryErrors` |
| Ожидаемый результат | Письменное решение либо добровольная практика выбираются по доказанному требованию учителя | `written` + `worked-solution` даёт загрузку; `check` + варианты оставляет добровольную загрузку каждого номера | `sourceInventoryErrors`, `photoUploadPolicy`, UI контракт |
| Номер задачи | Оригинал, фрагмент, условие, состояние, загрузка и родительский маршрут привязаны к устойчивому ID | У каждого внесённого номера есть исходник и закрытый маршрут; ученик может загрузить фото в любой номер | `day validate`, `ProblemTaskCard.contract` |
| Нумерованный лист и связанный тест | Тест и лист одного `taskId` остаются двумя видимыми результатами; выключенный вариант остаётся в листе | У теста свой счёт вопросов, у листа — обязательных задач; обратимый выбор меняет только знаменатель задач. Второй лист того же предмета не смешивается с первым; раскрытый номер сохраняет оригинал, текст и `Дано / Найти` | `src/DayPage.assignmentQuiz.integration.test.tsx`: обе роли, 8 сценариев карточек |
| Родитель и ребёнок | Одна карточка и место маршрута, две проекции доступа | Общие исходник, `Дано / Найти` и статус; у родителя полный закрытый маршрут и действия, у ребёнка только отправленные `dayGuidance` в той же раскрываемой форме. Подсказка не раскрывает соседний шаг | `ProblemTaskCard.contract`, `UnifiedTaskCard.test`, Firestore Rules; [матрица](problem-card-design-decisions.md#role-projection) |
| Одно фото на несколько номеров | Номер кнопки определяет точку отправки, весь снимок анализируется отдельно | Закрываются только фактически подтверждённые номера; второй лист не наследует завершение первого | `photoCoverage`, `reviewPresentation`, отдельная смысловая проверка снимка |
| Публикация | Ролевые страницы строятся из одной проекции | Отпечаток **и** последовательность `task/variant/problem`, вид работы и источник пункта совпадают после обратного чтения | `assertPublishedPageAligned`, `day audit` |
| Телефон | Группы и пункты сначала компактны; переход разворачивает только цель | Есть действие загрузки, текст и сетка читаемы в раскрытом и закрытом состоянии | компонентные тесты и отдельные Chrome viewport проверки |

Запись `needs-review` показывает точный текст МЭШ. Автоматическая классификация по фразе «решать из файла» не подтверждает ни сдачу, ни отсутствие сдачи. Оператор осматривает файл и ожидаемый результат; новая карточка версии 2 не проходит `day validate` без независимой описи. При изменении текста учителя прежние номера, варианты, маршруты и опись сбрасываются.

## Что было источником повторов

Проверки правильности *внесённых* данных не доказывали полноту переноса из PDF. Поэтому два назначения могли остаться разными, но два варианта внутри второго листа всё равно исчезали; все объявленные номера имели разбор, но пропущенный номер не обнаруживался. Старая разметка вариантов также переживала смену записи МЭШ. Теперь хэш оригинала, сверенный состав и карточка образуют проверяемую цепочку. Истинность самой ручной описи машина не устанавливает: её сверяют с полным PDF до записи.

## Регрессии и пределы

Обязательный набор для выпуска: `npm run check`, `npm run day -- validate DATE` для изменённых дней, публикация и обратная проверка обоих ролевых документов, затем браузерная проверка затронутого экрана. `day/card-flow-certification.test.mjs` соединяет два МЭШ назначения, три принадлежащих им файла, два варианта, повторный № 1, вид работы, одно фото на два номера и обратное чтение ролевой страницы; каждый разрыв ребра тестируется отдельно. `src/DayPage.assignmentQuiz.integration.test.tsx` рендерит действующую страницу с контролируемыми снимками подписок, проверяя восемь сценариев теста, листа, второго задания и раскрытого номера в обеих ролях. Это закрывает описанный сбой UI, но не проверяет живую доставку Firebase. Действующие unit/contract и DOM интеграционные тесты не заменяют интерактивный browser fixture с Firebase emulator для фактической загрузки, частичного статуса и повторной публикации. Нельзя называть этот путь пройденным или все карточки полностью покрытыми.

Chrome проверки расписания, колокольчика и фрагмента листа проверяют сетку и загрузку изображения на нескольких ширинах. Они пока вызываются отдельными командами, а не автоматически в `npm run check`. Содержательную правильность родительского решения и видимые номера на фото подтверждает отдельная предметная сверка. Нумерованная оболочка биологии и географии пока не реализована: код допускает `problems[]` для математического результата, общая предметная оболочка для остальных результатов остаётся целевой архитектурой.
