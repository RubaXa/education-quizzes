# Управление изменениями интерфейса Education

Статус: действующий процесс проверки **текущего** интерфейса. Макеты из `reports/2026-10-14-card-nesting-design-options.md` — варианты для обсуждения; они не меняют этот контракт и не являются согласием на новый экран.

## От смысла к проверке {#trace}

Для каждого изменения записывается цепочка `потребность и подтверждение пользователя → сценарий → источник данных/права → продуктовая спецификация → компонент → CSS/токены → тест поведения → проверка геометрии → выпуск`. [Карта файлов](../file-map.md) задаёт ближайший контракт и потребителя каждого файла, [система компонентов](../shared/design/components.md#registry) — канонический компонент, [дизайн-система](../shared/design/README.md) — общий язык экрана, [матрица задачи](../modules/reviews/problem-card-design-decisions.md) — слои нумерованной карточки. Наличие `@see` само по себе не доказывает совпадения поведения с контрактом.

Перед любым переносом элемента или изменением формулировки, роли, раскрытия либо цвета нужно назвать: что увидит пользователь до и после, какое действие изменится, какие состояния/ширины/роли затронуты и почему прежнее решение недостаточно. Новую функцию или переосмысление согласованного поведения показывают родителю в конкретном макете до выпуска. Прямая просьба исправить дефект уже даёт основание на исправление в обозначенных пределах; решение и доказательство всё равно записываются. Неоднозначное «сделать лучше» не заменяет утверждение нового продуктового поведения.

## Механический барьер {#mechanical-gate}

`npm run check:spec` сначала проверяет `file-map.md`, затем `scripts/check-ui-contract.mjs`. В `ui-contract-baseline.json` запечатаны SHA-256 209 действующих файлов продуктового кода: клиентские TS/TSX/CSS и модули `day/`, `storage/`, `diary/`, `assessment/`, `packages/`, `pwa/`, `sync/`, `scripts/` (без тестов и самого проверяющего скрипта). Новое ядро `operator/` проходит тот же барьер через решения. Базовый файл имеет контрольную сумму в проверяющем скрипте: его нельзя перегенерировать при изменении продукта. Любое изменение исходника, в том числе перенос элемента, смена класса, вычисляемого статуса или логики публикации, останавливает проверку. Этот барьер включён в `npm run check` и локальный pre-push.

Для намеренного изменения добавляется запись в `ui-change-decisions.json` **по каждому затронутому файлу**: новый SHA-256, путь к `docs/product/ui-decisions/<id>.md`, действующие спецификации, реальные регрессионные тесты и `authorization: {status, evidence}`. Допустимые статусы — `direct-request` (пользователь прямо потребовал данную правку) и `approved-mockup` (пользователь одобрил конкретное «было → стало»); `evidence` указывает конкретный запрос или решение. `pending` не проходит проверку. Документ решения обязан содержать разделы «Основание», «Было → стало», «Действия и роли», «Проверки», «Согласование» и перечислять файлы. Проверяющий скрипт подтверждает наличие и согласованность записи, **но не способен доказать подлинность согласия или качество теста**. Это предмет ревью.

Порядок правки: (1) сохраните приемлемое исходное поведение характеризационным тестом; (2) воспроизведите ошибку красным тестом, если это дефект; (3) запишите решение и обновите спецификацию; (4) измените общие компоненты/CSS; (5) выполните `npm run check` и нужные viewport-проверки; (6) сравните 320/390/540 px, обе роли и закрытое/открытое состояние; (7) только после этого решайте вопрос выпуска. Нельзя просто обновить отпечаток, оставив прежний тест, который не проверяет изменившийся сценарий.

## Сохраняемые действия и проверка фото {#photo-interactions}

Число зелёных тестов не заменяет проверку действия пользователя. Перед изменением общего компонента перечислить его существующие действия и все маршруты-потребители, затем выполнить их через реальный компонент. Проверка одного наличия картинки/кнопки не подтверждает открытие, переключение или закрытие. Макет UI Kit тоже использует рабочий контрол и должен реагировать на нажатие.

| Действие | Состояния и потребители | Обязательная проверка |
|---|---|---|
| Открыть/переключить/закрыть своё фото | День и выходной спецкурс; обе роли; проверенный снимок | Реальные клики в DayPage/WeekendMathSlot; UI Kit; браузерный прогон |
| Открыть локальное фото и сохранить выбор после передачи | До snapshot и после появления server upload | `WorkPhotoGallery.test.tsx`; реальная загрузка через file input в WeekendMathSlot test |
| Повтор неудачной передачи, удалить ожидающий файл, сохранить просмотр проверенного | Прежние права, compact и обычный вид | Общие action tests; быстрый крестик остаётся у исходной задачи |
| Сохранить место загрузки и ссылки | Общий снимок нескольких решений | Регрессии upload-origin; просмотр не размножает галереи |

День, выходной слот и UI Kit обязаны использовать `WorkPhotoGallery`. `scripts/work-photo-consumers.test.mjs` отклоняет прямое возвращение статичных `ArtifactAvatar`/`WorkArtifactImage` в этих потребителях. Полные тесты включают сценарии выше; при новом потребителе расширить и перечень, и реальный интеракционный тест. При переосмыслении действия сначала требуется прямое решение пользователя и обновление контракта; нельзя просто исправить ожидаемое значение теста под новый код. После переноса CSS проверить реальное нажатие мышью/с клавиатуры и размеры 320/390/540 px. Автоматические проверки уменьшают риск; смысл ожиданий и визуальные перекрытия всё равно требуют ревью.

## Честная граница покрытия {#coverage-limit}

Отпечаток ловит незаявленную правку исходников, но не изменение данных Firestore, шрифтов/браузера, внешнего изображения, косвенное влияние нового CSS-селектора или пропуск сценария внутри существующего теста. `check-problem-variant-viewport.mjs` использует фиксированный HTML-пример и реальный CSS, а не полностью собранную страницу с живыми данными; поэтому он не заменяет снимки родителя и ученика в опубликованной версии. Перед выпуском изменения карточек обязательна визуальная и ролевая сверка. Не следует называть покрытие «гарантией неизменности продукта» без этих проверок.
