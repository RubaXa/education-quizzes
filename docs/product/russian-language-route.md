# Письменный маршрут русского языка {#russian-route}

## Один родительский разбор после фото {#review-in-one-route}

Если для письменной работы опубликован `parentGuide.presentation=learning-route`, родитель видит исходное задание и **один** разбор в `ParentTaskGuide`. После фото он показывает короткое оставшееся действие и накладывает проверенные наблюдения на предметные этапы. Отдельный общий `WorkReview` с повтором трёх абзацев скрывается только в родительской роли; ученик продолжает видеть адресную обратную связь. Родительское решение о зачёте или спорном критерии сохраняет отдельный `WorkReview`, чтобы не пропало действие.

Для лексического упражнения этапы описывают **способ объяснения слова**, а не математические «Дано / Найти». Сначала показывается требование учебника, затем запись ученика и проверка подстановкой в коротком контексте. Например, «дюжина яиц» → «двенадцать яиц» сохраняет смысл и грамматическую фразу; «вековой лес» → «сто лет лес» не даёт заменяющего прилагательного. Родителю доступен ориентир «столетний», ученику — один вопрос, помогающий самому подобрать слово. Принятые ответы не требуют переписывания. Исправление текста разбора сохраняет фото, прежний вердикт и историю попыток.

Статус: схема данных и общий компонент реализованы. Смысловые тексты готовит LLM/оператор по точному заданию и семейному учебнику, затем человек сверяет источник. Никакой код React не содержит готовых ответов конкретного ребёнка. [Общий выбор](card-generation-policy.md#russian-adapter), [визуальные токены](design-system.md#cards-and-status), [граница требований](review-criteria-provenance.md).

## Выпуск очередной карточки {#pipeline}

1. Сохрани дословную запись МЭШ и страницу назначенного упражнения с `sourceRef`; раздели устную и письменную части. Для устной используй общий `QuizCard` с `QuizProgress` и историей. Для ЦДЗ требуется подтверждение результата, а не письменный разбор.
2. Если письменная часть проверена, задай `outputKind`, `cardPolicyVersion: 1`, `cardPattern` из конечного списка: `spelling`, `syntax`, `text-plan`, `composition`. Один урок может иметь разные задания и разные паттерны. Тип выводится из требуемого результата, не из одного названия предмета.
3. В закрытом `parentGuide` поставь `presentation: learning-route`, тот же `pattern`, `revision` и этапы с точными ID из `day/card-policy.mjs`. Каждый этап содержит сверенный `expected`, точный `source.kind/ref/excerpt`, `reviewLabels`, наводящий `hintPreview` и отдельный `revealPreview`. Подсказка не содержит полного ответа; раскрытие показывает только выбранный этап. Не добавляй число абзацев, пункты плана или форму как школьное требование без источника.
4. Для `spelling` этапы `rule → application → writing`; для `syntax` — `basis → relations → analysis`; для `text-plan` — `theme → speech → plan`; для `composition` — `idea → support → coherence → language`. При отсутствии назначенной грамматической или композиционной части этап может честно сказать «не требуется в этом задании», но нельзя приписать её учителю. Если четырёх этапов слишком много для короткой работы, следующий согласованный профиль добавляется как версия схемы после проверки, а не удалением этапа в одном JSON.
5. После фото каждое заключение `review.items` сопоставь с `stageId`; для старой записи допустим только явный `reviewLabels` из родительского этапа. Сохраняй `observed`, статус, основание и `uploadIds`. Верная иная формулировка принимается, нечёткое фото не считается ошибкой. При спорном критерии показывай причину и выбор родителя, не объявляя новый долг ребёнку.
6. Прогони `npm run day -- validate YYYY-MM-DD`. Для нового дня публикуй данные обычным `day publish`. Для уже опубликованного дня с доказанным неизменным условием и старой схемой выполни `day guide-upgrade YYYY-MM-DD task-id --dry-run`, затем ту же команду без `--dry-run`: она сверяет все ID/тексты и семейную связь, атомарно добавляет только три публичных поля и закрытый пакет, сохраняет фото, проверки, статусы и dashboard. При несовпадении полного плана с новым МЭШ выпуск останавливается до отдельной сверки. `dayPages` не содержат `parentGuide`, закрытый пакет попадает в `dayTaskGuides`. Проверь обе роли и передачу одного выбранного этапа через `dayGuidance`. Изменение одних данных видно через Firestore без выпуска PWA; изменение React/правил требует выпуска и записи новости.

## Реальный пример и ограничения {#example}

`mesh-351035247` (упр. 169, ДЗ к 12.10.2026) имеет `text-plan`: тема/основная мысль, тип/стиль, план. Сверенные страницы: Баранов, 6 класс, часть 1, печатные 90–91, PDF 91–92, `russian-baranov-6-part-1-2026#pdf-0091` и `#pdf-0092`. Приватный пакет сохранён в `.local/day-source-2026-10-11.json` и опубликован адресным атомарным `day guide-upgrade`; существующие `taskId`, ссылки и фото не заменены. Срез 09.10 остаётся прежним: его старый план уже расходится с текущим снимком МЭШ, и переиздание требует отдельной полной сверки. В фото все части предъявлены; форма плана спорна, поскольку МЭШ требует только план, а учебник называет тезисный. Пятый пункт не назначен. `reviewLabels` связывает прежние пять наблюдений с тремя этапами только для отображения; это не новая автоматическая оценка и не результат нового анализа фото.

Реализованы конечная схема, валидатор, общая родительская карточка и выборочная передача помощи. Семантический разбор нового фото по этапам пока выполняет оператор при проверке; незнакомую работу нельзя автоматически окрасить по сходству с образцом. Старые дни без `cardPolicyVersion` сохраняются до поштучной сверки. Текущий `DayPage` ещё не управляется Firestore-манифестом крупной компоновки: данные маршрута реактивны, набор верхнеуровневых секций пока закреплён кодом.
