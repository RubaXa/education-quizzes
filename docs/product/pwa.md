# Education как приложение на телефоне

Связанные контракты: [доступ и состояние](../modules/families/access-and-state.md), [экраны из данных](../modules/synchronization/backend-driven-ui.md), [события и уведомления](../modules/notifications/inbox.md). Карта: [спецификации](README.md).

<a id="install"></a>
## Установка

Сайт на HTTPS содержит манифест с постоянным `id`, названием, иконками, `display: standalone` и областью `/education-quizzes/`. На iPhone пользователь открывает адрес в Safari и выбирает «Поделиться» → «На экран „Домой“». Кнопка в шапке объясняет эти действия; на платформах с `beforeinstallprompt` запускает системное предложение установки. [WebKit описывает домашние веб приложения](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

Одна установленная оболочка открывает личный стартовый экран, страницы дня, списки и прохождение тестов внутри своего `scope`. Переход к материалам Яндекс.Диска ведёт на внешний сайт; учебные данные остаются в Firestore.

Стартовый URL общий для всех пользователей и не содержит токена дня, имени или идентификатора ребёнка. На личной странице есть кнопка «Скопировать личную ссылку». При первом запуске установленного приложения пользователь нажимает «Войти по ссылке из буфера». Safari не предоставляет постоянного разрешения `clipboard-read`: если программное чтение отклонено, поле обычной вставки раскрывается и получает фокус; вставка из системного меню сразу проверяет ссылку без второго нажатия. Пустой буфер, посторонний адрес и прежняя ссылка на отдельный день объясняются разными сообщениями. Далее Firebase Auth сохраняет техническую сессию на устройстве, а личный профиль восстанавливается из Firestore. У каждого родителя и ребёнка своя ссылка, а данные ребёнка общие для всех связанных с ним родителей. В Safari и установленном веб-приложении на iPhone локальное хранилище может различаться: WebKit копирует cookies при установке, но не LocalStorage; поэтому повторный вход при первом запуске и отдельный пустой стартовый URL предусмотрены намеренно. [Контракт входа](../modules/families/README.md#link-login), [WebKit о хранении при установке](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/), [Firebase о сохранении входа](https://firebase.google.com/docs/auth/web/auth-state-persistence), [поведение буфера в Safari](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API#security_considerations).

Когда личная ссылка отозвана, подписка на её доступ закрывает открытый личный экран и предлагает войти по новой ссылке; учебные работы остаются привязаны к прежнему профилю. Замена проводится отдельно для взрослого и ребёнка по [протоколу ротации](../modules/families/README.md#link-rotation). До выпуска новой сборки этот экран может показать ошибку доступа без автоматического возврата к форме входа. При временной сетевой ошибке восстановление сессии делает не более трёх повторов с паузами 2, 5 и 15 секунд, даже если браузер не прислал событие `online`; после них пользователь может нажать «Повторить подключение». Отказ в доступе и отзыв ссылки не запускают сетевые повторы.

Кнопка установки объясняет путь Safari → «Поделиться» → «На экран „Домой“» → «Добавить». Если iOS предлагает «Открывать как приложение», его оставляют включённым; этот переключатель появился в iOS 26. Иконка, имя и самостоятельное окно заданы манифестом. [WebKit об установке на iOS 26](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/).

Ссылка из мессенджера или Safari на iPhone открывается в браузере приложения либо Safari и не может программно перенаправить пользователя в установленное PWA. Манифест `scope` управляет навигацией **внутри** приложения, но не создаёт для домашней веб-иконки системные Universal Links. Для входа с иконки после установки пользователь один раз переносит личную ссылку; дальше открывает приложение с домашнего экрана. [WebKit о запуске домашнего веб-приложения](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [Apple о Universal Links для нативных приложений](https://developer.apple.com/documentation/xcode/allowing-apps-and-websites-to-link-to-your-content).

На узком экране весь dashboard остаётся в границах viewport. Горизонтально прокручивается только полоса дат; карточки, текст и кнопки не расширяют документ.

<a id="updates"></a>
## Обновление приложения и данных

При сборке `scripts/generate-sw.mjs` создаёт service worker с хешем исходников. Он предварительно сохраняет только HTML, JS, CSS, шрифты, манифест и иконки. Старые версии оболочки удаляются после активации новой. При открытии, возвращении в приложение, появлении сети и раз в 30 минут браузер проверяет новый worker. Если он готов, приложение показывает кнопку «Обновить»; перезагрузка происходит после действия пользователя, чтобы не прервать ввод ответа или загрузку фото.

Текущий HTML запрашивается через сеть; в отсутствие сети открывается согласованная закешированная версия оболочки. Приложение явно сообщает об отсутствии сети и повторяет вход после восстановления подключения. Личные ответы, фото, страницы учебников, OAuth-токены и ответы Firestore **не попадают в service-worker cache**. Живые данные приходят из Firestore отдельно; новая версия данных видна по его подпискам. Поэтому офлайн-оболочка пока не означает офлайн-доступ к личному учебному плану. Офлайн-данные требуют отдельной модели авторизации, очистки при выходе и разрешения конфликтов. [Firebase рекомендует отдельно учитывать доверенность устройства перед включением постоянного кеша Firestore](https://firebase.google.com/docs/firestore/manage-data/enable-offline).

Если Firestore прислал `schemaVersion`, которую текущий клиент не понимает, экран сообщает о необходимости обновления вместо отображения догадок. Это отдельная защита от несовместимости структуры данных и кода.

<a id="push"></a>
## Уведомления

Адресный [центр обновлений внутри приложения](../modules/notifications/inbox.md#in-app-center) получает через Firestore изменения ДЗ, новые оценки, этап и итог проверки, уточнение результата, родительский зачёт и описание важного выпуска; показывает их в колокольчике при открытом приложении без новой сборки для каждого события. Новая логика интерфейса сама по себе требует одного выпуска PWA, после чего содержимое центра публикуется данными. На iPhone Web Push поддерживается для приложения, добавленного на домашний экран, начиная с iOS 16.4; разрешение запрашивается только после нажатия пользователя. [WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [Apple](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers).

Системный Push не включён сейчас. Понадобятся привязка подписки устройства к постоянному `personId` и техническому `deviceUid`, серверная отправка и проверка на реальном iPhone. Firebase Cloud Messaging требует VAPID и регистрацию экземпляра приложения; это больше одной настройки проекта. [Руководство Firebase](https://firebase.google.com/docs/cloud-messaging/web/get-started). Пока не доказана совместимость выбранного транспорта с iPhone, не обещать push в интерфейсе. Внутренний центр не зависит от push.

<a id="release-build"></a>
## Отпечаток выпуска

Отпечаток сборки учитывает `src`, публичные ресурсы, конфигурацию и общие модули `packages`/`day`, которые импортирует браузер. Изменение общей модели Telegram обязано пересобрать UI Kit даже без правки JSX/CSS; тестовые файлы не инвалидируют сборку. Регрессия меняет файл общего пакета при неизменном src и проверяет новый fingerprint.

`scripts/build-inputs.mjs` учитывает только файлы, способные изменить опубликованную оболочку. Тесты `*.test.*` и `*.spec.*` внутри `src` не входят в отпечаток: их правка сама по себе не требует новой публикации. Изменение приложения, стилей, статических ресурсов или зависимостей должно менять отпечаток. После публикации сухой прогон `npm run publish:pages -- --dry-run` должен подтвердить отсутствие нового пакета.
