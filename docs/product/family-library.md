# Семейная библиотека и общий архив учебников

Связано с [семейной моделью](../architecture/family-data-model.md), [каталогом страниц](materials.md), [происхождением критериев](review-criteria-provenance.md), [формированием плана](plan-generation.md) и [хранением артефактов](../architecture/family-artifact-access.md). Состояние ниже описывает реализацию по слоям; опубликованный экран сам по себе не означает, что локальный приёмник PDF запущен.

## Обязательное различие

`StoredObject` — один проверенный оригинал в служебном архиве Яндекс.Диска, адресованный SHA-256. `materialBooks/{bookId}` — общая **внутренняя** запись издания и его страниц. `families/{familyId}/children/{childId}/books/{bookId}` — подтверждённая связь конкретного ребёнка с изданием. Родитель видит только свои связи, очередь своих загрузок и свои требования; общего списка книг в интерфейсе нет. Ни уже существующий объект, ни одинаковая школа, ни одинаковый класс **не создают семейную связь**. Новая семья начинает с нуля и передаёт свой оригинал PDF. При совпадении SHA система переиспользует существующий объект и издание; при ином PDF сравнивает издание и страницы, сохраняя оригинал и доказательства. Книга учитывается в комплекте только после установления связи с конкретным ребёнком.

Дедубликация имеет два уровня: равные байты → один `storedObjects/{sha256}` и один физический оригинал; разные сканы того же издания → один логический `materialBooks/{bookId}` после сверки выходных данных, условий, нумерации и минимум двух показательных страниц. Один хэш не доказывает, что это нужный предмет или класс; одинаковые заголовки/ISBN без сверки страниц не доказывают тождество редакции. Разные редакции, части и выпуски получают разные `bookId`. Семейная связь сохраняет происхождение собственной загрузки даже при общем объекте. Чужие семейные имена, загрузки и связи не попадают в каталог или UI.

## Покрытие расписания {#coverage}

После подключения МЭШ берём **наблюдаемые** предметы из опубликованного расписания каждого ребёнка. Учитываем только реально полученный горизонт; до его загрузки показываем «состав учебников уточняется», а не «все книги есть». Для обычных книжных предметов отсутствие подтверждённой семейной связи — красный пункт с загрузкой. Физкультура, ИЗО, музыка и технология по умолчанию не требуют учебника; для спецкурсов и новых названий показываем «уточнить материалы». Родитель может явно отметить отсутствие учебника у предмета; решение хранится в семейной записи `bookRequirements`, не переносится другой семье. Смена расписания или семейного правила пересчитывает список без выпуска PWA. Для составного курса/нескольких частей покрытия одной книгой может быть недостаточно: конкретные назначенные страницы и части проверяются отдельно при формировании задания.

Вверху кабинета находится заметный блок «Нужны учебники и материалы» со списком `ребёнок → предмет → состояние → загрузить PDF`. `requested/awaiting-upload/uploaded/needs-identification` не считается покрытием. После подтверждения полного набора **известных** книжных предметов этот блок перестаёт занимать верх и остаётся компактной семейной библиотекой ниже учебных карточек. Библиотека показывает подтверждённые и предварительно связанные книги этой семьи, включая книги вне текущего горизонта расписания; предварительное издание помечено отдельно и не закрывает требование предмета. В ней можно открыть **уже опубликованные для ребёнка страницы** через штатный просмотрщик; оригинал PDF остаётся приватным. Просмотр всех страниц книги ещё требует отдельной публикации изображений или защищённого медиа-шлюза.

## Загрузка PDF {#upload}

Первая версия принимает **только полный PDF до 100 МБ**. Фотографии, отдельные страницы и составные пачки отложены: неполный набор нельзя честно считать целым учебником. Родительский браузер записывает метаданные и SHA-256 в `families/{familyId}/children/{childId}/bookUploads/{uploadId}`, сохраняет Blob в локальном IndexedDB и передаёт байты напрямую по краткоживущему URL Яндекс.Диска. Токен Диска находится только у локального приёмника. Приёмник повторно проверяет сессию родителя, связь с ребёнком, размер, сигнатуру PDF и хэш; кладёт проверенный оригинал в общий служебный архив либо переиспользует уже имеющийся, а временную копию удаляет после подтверждения. `storedObjects/{sha256}` и путь общего файла не перечисляются из браузера. Совпадение с индексированным PDF того же предмета даёт семейную связь автоматически. Иначе состояние `needs-identification`: книга уже сохранена, но ещё **не подтверждена** для проверки задания.

Операторский шаг: `npm run family:library -- inbox <familyId>` → `pull <familyId> <childId> <uploadId>` → определить точное издание по обложке, выходным данным, тексту и рисункам → зарегистрировать PDF в `library/textbooks/registry.json` → `python3 tools/textbook_index.py build-all` → визуально сверить страницы → `npm run storage -- sync-catalog` → `npm run family:library -- link <familyId> <childId> <uploadId> <bookId>`. Последняя команда требует равный SHA-256 и предмет. Для другого скана уже индексированного издания оператор сохраняет закрытый JSON в `.local/family-library-evidence/` с `uploadSha256`, `bookId`, `targetSha256`, `conclusion: same-edition-and-content`, описанием выходных данных `editionEvidence` и минимум двумя визуально сверенными парами страниц `comparedPages: [{uploadPage, catalogPage, match: true}]`, затем вызывает `link-edition <familyId> <childId> <uploadId> <bookId> <evidence.json>`. Это ручная экспертная сверка, **не автоматическое распознавание**. Разные байты сохраняются как разные исходные оригиналы для аудита, но обе семейные связи ведут к одному логическому изданию. Миграция прежнего комплекта первого ребёнка — отдельная команда `seed-existing`, ограниченная прежним владельцем из локального реестра. Она требует закрытый `.local/family-library-evidence/legacy-seed.json` с точными `familyId`, `childId` и перечнем `books: [{bookId, sourceSha256, ownershipEvidence, bindingStatus?}]`. Для каждой книги оператор сверяет событие передачи полного PDF семьёй, оригинальный SHA-256, индекс и общий каталог; `--dry-run` проверяет весь набор без записи, затем один Firestore batch связывает только новые книги. Статусы каталога `family-page-matched` и `exact-edition-confirmed` сами по себе не доказывают владение семьи: необходима отдельная запись о передаче полного PDF. Параллельное издание допустимо только как `provisional` и не закрывает требование точного учебника. Первоначальная широкая миграция была отклонена автоматической проверкой; после поштучной сверки 11.10 связаны восемь подтверждённых и два предварительных PDF. После сверки всех ранее опубликованных `taskPageRefs` оператор вызывает `activate <familyId> <childId>`: это включает машинный барьер семейной библиотеки для прежнего контура, но не запускает его автоматически на неполном комплекте.

## Данные и права {#firestore-model}

`families/{familyId}/children/{childId}/bookUploads/{uploadId}`: `childId`, `subjectKey`, `originalName`, `contentType`, `size`, `sha256`, `deviceUid`, `status`, серверное время, затем закрыто добавляемые `storage` и `bookId`. Создаёт только взрослый этой семьи для доступного ему ребёнка; клиент вправе перевести только собственный файл из `awaiting-upload` в `uploaded`. `families/{familyId}/children/{childId}/books/{bookId}` записывает только доверенный процесс после проверки (`bookId`, `subjectKey`, `sourceSha256`, `status`, `evidence`, `confirmedAt`). `bookRequirements/{subjectKey}` — выбор взрослого этой семьи `required`/`no-book`, автор и время. `storedObjects/{sha256}` и общий `materialBooks` пишет и читает только оператор. Страницы назначенных заданий проецируются в `families/{familyId}/children/{childId}/bookPages/{bookId#pdfPage}`; клиент не читает общий каталог даже по известному `bookId`.

## Граф источников при каждом запуске {#source-graph}

Контекст строится **для пары `(familyId, childId)` и конкретного задания/ревизии**, а не глобально для класса. Узлы: снимок МЭШ и точная запись задания; семейная связь с изданием и проверенные страницы; вложение и критерий учителя; методические материалы конкретной школы, если семья их передала; найденные в интернете первоисточник задачи, официальный ключ и вторичные решения; попытки ребёнка и родительские решения. Каждая связь имеет `sourceRef`, время, степень совпадения, предмет/класс/учебный год, версию и ограничение. Семейное правило не копируется соседней семье и не превращается в требование учителя.

Порядок подготовки: точная запись МЭШ и оригинал → семейный учебник/приложение учителя → поиск опубликованного совпадающего ответа и методических материалов (официальные первыми, прямые ссылки и степень совпадения) → сверка школьных критериев → независимое решение только если ключ не найден, с отдельной пометкой → адресная проверка работы по доказательствам. Поиск решения **не расширяет** обязательное ДЗ. При другом имени или слегка изменённом тексте задачи фиксируются расхождения, а ключ не переносится без проверки. Если семейный учебник отсутствует или издание не определено, статус `source-needed`/`needs-review`; нельзя молча взять подходящий PDF из общего архива. `day publish` пересобирает граф из семейных книг, правил, подтверждённых школьных методик, задач, страниц и записанных в закрытом плане `sourcePacks[taskId].online` результатов поиска, сохраняет его в закрытом `.local/family-source-graph-YYYY-MM-DD.json` и для ребёнка с `libraryPolicyVersion: 1` останавливается, если `taskPageRefs` ведёт к неподтверждённой книге. Для интернет-источника нужны прямой URL, тип, степень совпадения и время сверки; запись остаётся в закрытом плане. Интернет-исследование и применимость ключа по-прежнему проверяет оператор; эта часть ещё не машинная.

## Состояние реализации

- Локально реализованы: семейные записи/правила, виджет статуса по наблюдаемому расписанию, приём полного PDF, прямой транспорт через локальный процесс, физическая дедубликация по SHA-256, точное связывание с уже индексированным PDF, очередь неизвестного издания, операторское связывание после индексации и пересборка семейного графа с барьером страниц при выпуске старого односемейного дня.
- Правила Firestore и React-страница опубликованы 11.10. Загрузка PDF ставит заявку в очередь, которую локальный приёмник на Mac обрабатывает только пока он запущен; состояние заявки видно взрослому.
- Не завершены: автоматически определять эквивалентные издания при разных байтах (пока есть ручной `link-edition`), полноценный просмотр всех страниц семейной библиотеки, индексировать и связывать новый PDF без операторского шага, подключать семейный граф как машинный барьер ко всем генераторам и синхронизациям. Фотографии отдельных страниц в версии 1 не принимаются. Локальный приёмник работает только пока запущен Mac; для круглосуточного приёма нескольких семей нужен постоянно доступный доверенный процесс.
