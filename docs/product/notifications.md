# Спецификация сервиса уведомлений `@agi_edu_bot`

**Статус:** рабочий черновик по интервью от 16.10.2026
**Реализация:** частичный runtime-срез включает opt-in Firestore/МЭШ observers с автоматическим обнаружением семей; оба UI link flow, grouping/digest и production rollout отсутствуют. Не считать сервис действующим наблюдателем.
**Назначение:** зафиксировать бизнес-цели и проектные решения для сервиса событий и уведомлений PETR через Telegram-бота `@agi_edu_bot`.

> Архитектурные границы, порты, расширение модулей и состояние реализации описаны отдельно в [корневой спецификации сервиса](../services/telegram-bot/README.md). Этот документ сохраняет бизнес-контракт и ответы интервью; детали адаптеров и хранения находятся в дочерних архитектурных спецификациях.

## Цель

Целевой результат — оперативно сообщать родителям и детям об актуальных событиях по детям, а команде PETR — о новых событиях, которые могут требовать синхронизации сервиса или проверки детских работ. Первая версия отправляет уведомления родителям и команде; подключение детей отложено. Сервис должен сократить ручные обходы источников командой.

Обработчик событий — обычный детерминированный скрипт без вызова LLM. Он обнаруживает изменения в источниках, определяет тип события по данным и шаблонам, сохраняет событие и отправляет структурированное сообщение.

## Аудитории и охват

- **Родители и опекуны:** получают изменения по всем детям своей семьи.
- **Дети:** прямые Telegram-уведомления не входят в первую версию. Подключение детских Telegram-аккаунтов отложено до отдельного сценария привязки. Это уточнение заменяет ранний ответ о доставке детям того же потока.
- **Команда PETR:** на первом этапе получает общий поток в личный Telegram `@ibnrubaxa`. Получатель должен быть заменяемым/расширяемым до группы или отдельного служебного аккаунта.
- **Запуск:** сразу для всех подключённых семей.
- **Целевая задержка:** до одной минуты от обнаружения события до сообщения. Фактическая задержка зависит от источника; для МЭШ задан отдельный более длинный интервал опроса.
- **Критерий бизнес-успеха:** сокращение ручных проверок источников командой.

## Итоги интервью

Семь раундов по пять вопросов пройдены 16.10.2026. Ответы встроены в разделы спецификации. Два вопроса не сохранили ответ; в соответствующих местах оставлены рабочие предположения, а не выданные за утверждённые требования.

## Подключение Telegram и семейная привязка

- Нажатие Start добавляет Telegram-пользователя в реестр. Само по себе это ещё не даёт ему доступ к данным семьи.
- Реестр должен хранить Telegram account, состояние подключения/отключения и историю изменений состояния.
- Привязка должна подтверждать принадлежность человека к авторизованному аккаунту/семье PETR через Firebase; ручной ввод идентификаторов семьи или ребёнка не желателен.
- В семье может быть любое число родителей/опекунов; каждый подключает свой Telegram отдельно.
- Пользователь с активной семейной привязкой получает события по всем детям семьи.
- Поддержать оба пользовательских маршрута привязки:
  1. **Начать в PETR:** авторизованный родитель нажимает «Подключить Telegram»; это действие подтверждает привязку и создаёт одноразовую ссылку в `@agi_edu_bot`; нажатие Start завершает связь.
  2. **Начать в Telegram:** пользователь нажимает Start; бот выдаёт одноразовую ссылку в PETR; пользователь входит в PETR и явно подтверждает привязку.
- Технический механизм кандидата: Telegram deep link `https://t.me/agi_edu_bot?start=<одноразовый_токен>`. Для обратного маршрута нужен связанный токен/переход в PETR, который позволяет после авторизации достоверно сопоставить Telegram-пользователя и не даёт подменить его. Оба маршрута должны сходиться в единую Firebase-операцию привязки.
- Токены короткоживущие, одноразовые, непредсказуемые и привязаны к конкретному Telegram account и авторизованному действию PETR. Точный срок действия/повторная выдача ещё не заданы.
- Один Telegram может быть связан с несколькими семьями; каждая связь имеет отдельную запись и область доставки.
- `/stop` не отключает все семьи автоматически: бот предлагает выбрать семейную связь для отключения. Отдельная команда глобально выключить бота пока не задана.
- Отключение прекращает доставку по выбранной семье и фиксируется в реестре как событие отключения; историческая связь сохраняется.
- Пользовательский способ отключения первой версии: команда `/stop` в личном чате бота. Запись о Telegram account и событии отключения остаётся в реестре.

## Источники и обнаружение изменений

- В охват входят все доступные события МЭШ и Firebase, включая расписание, оценки, ДЗ, загрузки работ, тесты и последующие изменения статусов. Предварительный каталог по текущим контрактам приведён ниже и требует проверки по актуальным данным.
- **МЭШ:** используется pull-модель. Предварительный стартовый интервал — раз в 15 минут, чтобы снизить риск ограничения частоты запросов. Официально опубликованный лимит частоты запросов в доступной документации не найден; интервал нужно проверить на фактическом API и корректировать по ответам/ошибкам источника.
- Сохранять последний снимок МЭШ. Синхронизация PETR использует сохранённый снимок, если его возраст меньше одной минуты; если старше — запрашивает свежий снимок.
- **Firebase:** предпочтительно слушать релевантные изменения через подписки/триггеры, если это позволяет текущая модель данных и инфраструктура.
- При первом подключении семьи начальный снимок становится базовой точкой. Исторические события не рассылаются; уведомляются только последующие изменения.
- Требуются защита от повторной доставки одного и того же изменения, устойчивое сохранение последнего обработанного состояния и восстановление после перезапуска. Детали ключа события, хранения курсоров и устранения гонок уточняются.
- При каждом подтверждённом изменении или удалении уже известной записи создаётся новое событие для уведомления.
- При ошибке чтения команда получает сигнал сразу. Сервис после этого автоматически повторяет попытки с паузами; последний успешный снимок/курсор сохраняется, а накопившиеся изменения обрабатываются после восстановления. Конкретный график повторов и способ восстановления истории нужно спроектировать.

### Предварительный каталог событий по действующим контрактам

| Событие | Источник / наблюдаемые поля | Условие нового события |
|---|---|---|
| Изменение расписания | Полный снимок МЭШ `schedule`: `start_at`, `finish_at`, предмет, `cancelled`, `replaced`, связи с ДЗ/оценками | Добавление, изменение или удаление по стабильному ID строки расписания |
| Новая/изменённая оценка | Полный снимок МЭШ `marks`: ID предмета/периода, состав отметок, вес, среднее, количество | Новая отметка или содержательное изменение; среднее/счётчик — сигнал для сверки, а не отдельная оценка |
| Назначение/изменение/отмена ДЗ | Полный снимок МЭШ `assignments`: `sourceItemId`, дата урока, текстовые задания, вложения учителя, `detailStatus` | Изменение назначения по стабильному ID и содержательным полям; неполный ответ не считать отменой |
| Работа загружена | Firebase `dayUploads/{studentDayToken}/files/{uploadId}` плюс `dayOwners` и ролевой день | Подтверждённое появление файла/статуса загрузки; одно фото может относиться к нескольким номерам, поэтому `taskId` загрузки не ограничивает содержание снимка |
| Тест начат/отправлен | Firebase `assignments/{quizToken}` и связанный список роли; `status`, `startedAt`, `submittedAt`, `updatedAt` | Подтверждённое изменение статуса попытки; ответы и ключи не отправлять в командный канал |
| Проверка работы обновлена | Firebase `dayProgress` и закрытая `dayReviewPrivate` | Изменение подтверждённого статуса проверки; закрытые пояснения не копировать в Telegram |

Это предварительная карта по существующим контрактам. Перед реализацией нужно сверить Firebase-пути, владельцев и ревизии в актуальном коде/данных и уточнить, какие изменения `dayPages` являются событием для семьи, а какие — только операторской публикацией.

### Граница наблюдателя

- Сервис уведомлений — отдельный детерминированный наблюдатель источников. Это проектируемая новая функция, а не описание уже работающего автономного процесса Education.
- Для МЭШ сравнивается полный успешный новый снимок с последним полным снимком по устойчивым идентификаторам и значимым полям. `fetchedAt`, перестановка строк, пустой/неполный ответ и сетевой сбой сами по себе не создают событие. Прежний полный снимок сохраняется при неудачном чтении. Эти правила следуют [контракту обнаружения и сверки](../modules/synchronization/change-detection-and-reconciliation.md).
- В Firebase сигнал изменения сверяется с актуальной записью, её владельцем, `familyId`/`childId`, ID события/задания, ревизией и статусом. Курсоры восстанавливаются после перезапуска; повторная обработка не создаёт повторное сообщение.
- Использовать доверенное серверное чтение. Связь `studentDayToken` с семьёй и ребёнком брать из `dayOwners`/`families`, не выводить владельца из текста задания или Telegram-профиля. Реестр Telegram-связей, журнал и очередь отправки хранятся отдельно; сервис не меняет исходные оценки, задания, загрузки и результаты тестов.
- Определение типа события — по явным полям и шаблонам источника. Сервис не оценивает правильность работы и не выводит завершённость из самого факта загрузки фото. «Загружено», «проверяется», «проверено» и «отменено» — отдельные статусы.
- Событие в служебном чате только сообщает о факте. В первой версии оно не пробуждает Codex, не запускает LLM и не начинает педагогическую проверку. Сейчас автономный наблюдатель изменений и адресный канал пробуждения не реализованы; создание Telegram-сервиса не меняет этот статус автоматически.

## Уведомления

- Изменения отправляются родителям/опекунам и команде PETR с учётом привязок и доступов. Детские сообщения отложены; будущая реализация должна ограничивать их профилем самого ребёнка.
- Все события в одном окне группируются в единое сообщение для получателя; внутри сообщение аккуратно делится на разделы по семье, ребёнку и типу события, чтобы взрослому было легко просмотреть весь пакет.
- Буфер группировки закрывается после 30 секунд тишины, но сообщение отправляется не позже 60 секунд после первого события.
- Если итоговый дайджест длиннее лимита Telegram, отправлять связанные пронумерованные части с общей группировкой и сохранением всех событий.
- Использовать доступное текстовое форматирование Telegram и строить читаемую визуальную иерархию: заголовки, короткие блоки, выделение значений/статусов, эмодзи только по смыслу и ссылки на контекст. Конкретный шаблон по категориям ещё нужно спроектировать.
- Внутренняя модель события должна допускать кнопки и действия в будущем; конкретные кнопки в первой версии не обязательны.
- Все категории уведомлений включены по умолчанию; настройки отключения отдельных категорий взрослым не входят в первую версию.
- Рабочий вариант структуры: ребёнок, тип события, предмет/задание, новое значение или статус, время события и ссылка/контекст при наличии. Пользователь не выбрал предложенный набор явно; формат требует подтверждения.
- Первая версия только уведомляет. Синхронизацию PETR и проверку работ человек запускает сам. Позже отдельно спроектировать удобный запуск действий из командного потока.
- После сбоя источника все подтверждённые накопившиеся изменения отправляются сгруппированным дайджестом с явной пометкой, что события задержаны и источник восстановлен.

## Рекомендуемый набор библиотек

### Для первой реализации

- **`grammy`** — основной Telegram Bot API framework. Поддерживает Node.js, JavaScript/TypeScript, long polling и webhooks. Для постоянно работающего Node-процесса предлагается начать с long polling: он не требует публичного HTTPS endpoint и проще в эксплуатации. Webhook оставить доступным вариантом смены размещения.
- **`@google-cloud/firestore`** — прямой серверный клиент Firestore для worker. Боту нужны доверенные чтения/записи Firestore, но он не использует Firebase Auth API; Admin SDK не следует тащить в production-граф только ради Firestore.
- **`firebase-admin`** — оставить в `devDependencies`: существующие локальные CLI-скрипты его используют. Бот не должен импортировать этот пакет.
- **Существующий `mesh-diary`** — переиспользовать текущий адаптер МЭШ, закреплённый в `education-quizzes/package.json`; отдельный MЭШ SDK не добавлять. До использования в круглосуточном многосемейном сервисе проверить входные учётные данные, изоляцию `(familyId, childId, sourceAccountId)` и лимиты источника.
- **`@grammyjs/auto-retry`** — небольшой рекомендуемый дополнительный модуль для Telegram 429, `retry_after`, временных сетевых ошибок и 5xx. Он не заменяет собственную очередь отправки, дедупликацию и повторы источников.

### Как читать Firebase

Для постоянного Node-worker отдельный listener package не нужен: `@google-cloud/firestore` предоставляет серверный `onSnapshot` для коллекций/запросов. Серверные библиотеки Firestore обходят Security Rules и используют IAM/ADC; worker должен получить отдельную минимально привилегированную учётную запись. Слушать только узкие пути и держать курсор/последнюю ревизию вместе с долговечной очередью уведомлений в Firestore.

**`firebase-functions` не добавлять в первый набор**, если выбран постоянный worker. Если размещение будет только в Firebase Functions, тогда добавить `firebase-functions` v2: Firestore triggers и `onSchedule` для обхода МЭШ, а Telegram принимать через grammY webhook. Cloud Firestore triggers могут прийти повторно и не по порядку, поэтому идемпотентность и долговечная очередь обязательны. Для функции также понадобится отдельное решение для таймеров группировки 30/60 секунд.

### Что уже есть и чего не хватает

| Пакет | Состояние проекта | Решение |
|---|---|---|
| `firebase` | Есть в `dependencies` как клиентская библиотека | Не использовать на backend бота |
| `firebase-admin` | Есть в `devDependencies` как `^14.5.0` | Оставить для существующих CLI; в Telegram worker не импортировать |
| `@google-cloud/firestore` | Добавлен в `dependencies` как `^9.3.1` | Использовать в worker для Firestore; production audit после замены: 0 уязвимостей |
| `mesh-diary` | Есть в `dependencies`, привязан к Git commit | Переиспользовать, аудитировать многосемейную работу |
| `grammy` | Добавлен в `dependencies` как `^1.46.0` | Использовать как framework бота |
| `@grammyjs/auto-retry` | Добавлен в `dependencies` как `^2.0.2` | Использовать для Telegram flood/network errors |
| `firebase-functions` | Не найден в текущих package files | Добавлять только при выборе Firebase Functions как хостинга |

**Выбор размещения остаётся открытым.** Рекомендация по библиотекам рассчитана на один постоянно работающий Node.js worker; фактический хост, способ хранения учётных данных и производственный secret store нужно выбрать до запуска.

### Проверка npm audit — 16 октября 2026

Исходный lock-файл из Git до установки Telegram-пакетов уже давал 17 предупреждений полного аудита (4 moderate, 13 high); все high связаны с dev-инструментами `firebase-tools` и `shadcn`. `grammy` и `@grammyjs/auto-retry` не попали ни в одну рекомендацию аудита. Перемещение существующего `firebase-admin` из dev в production добавило две moderate-находки в runtime-граф через `@google-cloud/storage → gaxios → uuid`. Поэтому `firebase-admin` возвращён в `devDependencies`, а для Telegram-сервиса выбран прямой `@google-cloud/firestore`. После изменения `npm audit --omit=dev` вернул 0 уязвимостей; полный аудит остаётся 17. Предложения полного `npm audit fix` требуют major-переходов существующих инструментов и пока не применяются.

## Источник по Telegram deep links

- [Telegram Bot Features — Deep Linking](https://core.telegram.org/bots/features#deep-linking): start-параметр передаётся боту при переходе по ссылке; официальный формат поддерживает `t.me/<bot_username>?start=<parameter>`.
- [grammY: Long Polling vs. Webhooks](https://grammy.dev/guide/deployment-types): grammY поддерживает оба режима и рекомендует long polling, когда нет причины предпочесть webhook.
- [grammY Auto Retry](https://grammy.dev/plugins/auto-retry): модуль повторяет API-запросы при Telegram rate limit и временных сетевых/серверных ошибках.
- [Firebase Admin SDK setup](https://firebase.google.com/docs/admin/setup): Admin SDK — серверный путь к Firestore и другим Firebase services; в Google Cloud поддерживается Application Default Credentials.
- [Cloud Firestore triggers](https://firebase.google.com/docs/functions/firestore-events): функция получает снимки до/после; события доставляются как отдельные document-level triggers, возможны дубли и отсутствие порядка.
- [Firestore Node.js `onSnapshot`](https://googleapis.dev/nodejs/firestore/latest/Query.html): серверный клиент поддерживает потоковые query listeners.
- [Firebase scheduled functions](https://firebase.google.com/docs/functions/schedule-functions): `onSchedule` использует Cloud Scheduler, если будет выбран serverless-вариант.
- [Telegram Bot API `sendMessage`](https://core.telegram.org/bots/api#sendmessage): сообщение ограничено 4096 символами после обработки entities; поддерживаются форматирование и inline keyboards.

## Ограничение исследования частоты МЭШ

Поиск по официальным доменам Москвы не выявил опубликованной спецификации API МЭШ с числовым лимитом частоты запросов. Это не доказывает отсутствие серверных ограничений: предел может быть не опубликован или зависеть от используемого интерфейса/учётной записи. До внедрения считать 15 минут безопасной бизнес-гипотезой, а не подтверждённым разрешённым интервалом; проверить контракт текущего коннектора, ответы сервера, коды ограничения частоты и устойчивость на малой нагрузке.
