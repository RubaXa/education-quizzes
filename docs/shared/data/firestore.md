# Модель данных Firestore: действующий граф v1

Это контракт **существующих** документов, по которым работают `DayPage`, `DayDashboard`, тесты и синхронизация. Источник истины, проекция и личный результат различаются. Изменение схемы требует проверки совместимости и миграции; добавление произвольного поля в документ не создаёт нового правила продукта. Ролевая интерпретация описана в [ViewModel](../../modules/reviews/subject-card-viewmodel.md#projections), причины разделения React-модулей — в [системе компонентов](../design/components.md#data-flow). Код проверки: [`day/data-contract.mjs`](../../../day/data-contract.mjs), [`day/placement-integrity.mjs`](../../../day/placement-integrity.mjs), [`scripts/day.mjs`](../../../scripts/day.mjs). Новая семейная модель описана отдельно в [архитектуре](../../modules/families/README.md); перенос v1 в неё ещё не завершён.

<a id="entities"></a>
## Узлы, владелец и назначение

| Путь | ID документа | Что хранит | Кто может менять | Срок жизни |
|---|---|---|---|---|
| `educationEvents/{eventId}` | SHA-256 action/revision identity | единая бизнес-очередь, lease/fanout/ack; [контракт](../../modules/synchronization/event-queue.md) | приложение создаёт разрешённый source+event batch; dispatcher меняет состояние; client reads запрещены | устойчивое событие и технический receipt |
| `operatorSyncTaskArtifacts/{artifactId}`, `operatorSyncTaskObservations/{eventId}` | хэш закрытых входов, event ID | неизменяемый адресный пакет и отдельная отметка свежести | доверенный dispatcher/CLI; client reads/writes запрещены | история входных ревизий |
| `operatorSyncJobs/{jobId}` | kind/family/child/event identity | исполнение конкретной задачи и указатель на пакет; [контракт](../../modules/synchronization/execution-artifact.md) | доверенный dispatcher/исполнитель | до проверенного done, затем история |
| `materialBooks/{bookId}` и `pages/{pdfPage}` | стабильный ID издания или листа, PDF-страница | общий дедублицированный оригинал учебника **или вложения учителя**, хэш, печатная страница, публичная ссылка изображения | индексатор | не зависит от семьи |
| `families/{familyId}/children/{childId}/bookPages/{bookId}#{pdfPage}` | ID общего материала и PDF-страницы | видимая проекция: для учебника право следует из **собственной загрузки семьи**, для листа учителя — из назначения МЭШ | доверенный издатель страниц | пока действует основание доступа |
| `dayPages/{dayToken}` | непрозрачный токен роли и даты | снимок задания, расписания, источников и ссылок, разрешённый роли | оператор публикации | исторические дни сохраняются |
| `dayDashboards/{dashboardToken}` | непрозрачный токен роли | календарный индекс дат; указывает на `dayPages` | оператор публикации | перезаписываемая проекция |
| `dayOwners/{studentDayToken}` | токен ученического дня | принадлежность `(familyId, childId)` | оператор доступа | пока существует день |
| `assignments/{quizToken}` | голый токен без slug | назначенный тест **и изменяемая попытка**: вопросы, ответы, статус, время | оператор создаёт; ученик отвечает | не перезаписывается выпуском дня |
| `dashboard/{boardToken}/assignments/{quizToken}` | тот же токен | запись теста в списке нужной роли | оператор тестов | пока тест назначен |
| `dayTaskGuides/{studentDayToken}/items/{taskId}` | устойчивый `taskId` | закрытый полный родительский разбор и проверенный источник | оператор разбора | новая ревизия без удаления истории работы |
| `dayUploads/{studentDayToken}/files/{uploadId}` | устойчивый ID загрузки | личное фото и стадия доставки; оригинал лежит вне Firestore | ребёнок/worker | история попытки |
| `dayProgress/{studentDayToken}/items/{taskId}` и `dayReviewPrivate/...` | устойчивый `taskId` | проверка работы и закрытые пояснения | оператор проверки | история прогресса |
| `dayHelp/{studentDayToken}/items/{taskId}` | устойчивый `taskId` | адресная подсказка конкретному ребёнку | взрослый/оператор | личный учебный маршрут |

**Граница дедубликации:** книга, страница и неперсональный исходный материал общие. Выбор семьёй именно своего учебника, попытка, ответы, фото, проверка, подсказка и траектория принадлежат `(familyId, childId)`. Наличие книги в общей библиотеке само по себе не даёт новой семье доступ. Вложение учителя становится доступным по подтверждённому назначению МЭШ этой семье; это отдельное основание, не семейная загрузка полного учебника.

<a id="ownership"></a>
## Владелец поля и направление данных

| Факт | Канонический узел | Производные записи | Почему нельзя менять производную запись отдельно |
|---|---|---|---|
| Точная формулировка ДЗ и назначенный лист | снимок МЭШ с исходным ID и временем проверки | `dayPages`, `dayDashboards`, страницы листа | повторная синхронизация должна уметь восстановить проекции |
| Файл отдельного задания | `homeworkEntries[].id` вместе с проверенным вложением урока | `dayPages.materialLinks[taskId]` | файлы одного урока нельзя автоматически копировать в каждое задание; общий файл требует явной связи |
| Содержание PDF и страницы | `materialBooks/{bookId}/pages/{pdfPage}` с хэшем оригинала | семейный `bookPages`, ссылки задания | общая страница не доказывает, что эту книгу выбрала семья |
| Выбор семьёй учебника | `families/{familyId}/children/{childId}/books/{bookId}` с хэшем издания и происхождением загрузки | семейный `bookPages`, подбор страниц для ДЗ | одинаковый учебник другой семьи не создаёт право доступа |
| Назначение теста и ответы | `assignments/{quizToken}` | ролевой список и `testPlacements` дня | связь без назначения даёт пустую карточку; выпуск дня не должен перезаписывать ответы |
| Проверка работы и подсказки | личные `dayProgress`, `dayReviewPrivate`, `dayHelp` | статусы в карточках | новый снимок МЭШ не стирает историю ребёнка |

В этой версии `dayPages` остаётся опубликованным снимком. Она не является каноническим хранилищем попыток, оригиналов PDF или права семьи на учебник. Изменение производной записи допускается только вместе с проверкой канонического узла и обратных ссылок.

<a id="cardinality"></a>
## Кратность и обязательные ключи связей

| Ребро | Кратность | Ключ и проверка |
|---|---|---|
| Семья → ребёнок → день | `1 → 0..N → 0..N` | `(familyId, childId, date)`; обе роли одного дня относятся к той же паре |
| Ученический день ↔ родительский день | `1 ↔ 1` после публикации | `parent.studentToken` указывает на опубликованную ученическую страницу; общие `taskId` совпадают |
| День → предмет → задача | `1 → 0..N → 0..N` | `subject.id` устойчив в дне; `task.id` уникален среди **всех** предметов дня |
| Задача → назначенный тест | `0..1` на конкретный `taskId` | `task.testToken = testPlacement.token = assignments/{token}`; второй тест готовится как отдельное назначение со своей связью, а не второй `testPlacement` того же задания |
| Назначенный тест → список роли | `1 → 1` для каждой опубликованной роли | одинаковые `quizToken` и `testId`; проверяется наличие реальных документов |
| Книга → PDF-страница | `1 → 1..N` | `(bookId, pdfPage)` плюс хэш полного оригинала и издание; печатный номер не служит уникальным ключом |
| Семейная книга → общая книга | `0..N → 1` | `bookId` и хэш издания совпадают; каждая семья должна иметь собственное основание загрузки |
| Задача → страницы материала | `0..N` | каждый `taskPageRef` ведёт к общей странице **и** разрешённой семейной проекции; принадлежность проверяется по книге либо конкретному вложению учителя |
| Задача → фото/проверки/подсказки | `0..N` | личные записи сохраняют `studentDayToken` и `taskId`; повторный выпуск дня их не удаляет |

Пустое `0..N` допустимо только когда соответствующее действие не назначено. Отсутствующий связанный документ при непустой ссылке — ошибка целостности, а не «ещё не загружено» для интерфейса.

<a id="v1"></a>
## Поля действующих документов

`dayDashboards.schoolCalendar` — необязательная компактная проекция персонального МЭШ-календаря: schemaVersion/source, диапазон покрытия, checkedAt/revision и интервалы `{from,to,title}`. Никаких raw ответов/МЭШ ID. Сохраняется в обоих принадлежащих ребёнку ролевых dashboard через проверенную транзакцию; неизменный повтор не переписывает документы. Старый/некорректный cache не даёт придумывать даты. Новые коллекции, Rules и подписки не нужны. [Полный контракт](../../modules/school-diary/school-calendar.md).

Общие учебные адреса используют canonicalToken и viewTokens{student,parent} у обеих dayPages/dayDashboards проекций одной пары familyId/childId. В личном shortcuts хранятся dashboardTokens/dayTokens aliases обеих проекций, а dashboardToken/dayToken остаются внутренним выбором членства. Это маршрутизация ресурса, не право: роль берётся из авторизованного члена семьи. Прежние private guides и результаты не перемещаются; rules не расширяются. [Контракт входа](../../modules/families/access-and-state.md#authenticated-learning-routes) определяет совместимость старых ссылок и проверку отзыва. Новый publisher и адресный attach-current-day сохраняют aliases; до публикации метаданных новой страницы выпуск общего интерфейса не считается завершённым.

`dayPages.assignmentRoutes[]` сохраняет подтверждённое семьёй различие исходного места вложения и учебного курса: schemaVersion, taskId, fromSourceDate/toSourceDate, fromDate/toDate, fromSubjectId/fromSubjectName, toSubjectId/toSubjectName, targetLessonId/targetLessonName, точный meshText, reason и decisionRef. Одинаковая запись есть у обеих сторон; только целевой день содержит активное задание, исходный — retiredTaskIds. Снимок МЭШ не меняется. Старые evidenceDayTokens связывают фото/проверки/решения того же ребёнка; новые результаты не создаются. [Контракт маршрутизации](../../modules/synchronization/plan-generation.md#assignment-routing) определяет проверку и пакетную публикацию; пустое поле не меняет отпечаток старой страницы.

`dayPages` v1: обязательны `schemaVersion: 1`, `kind: student|parent`, `date` (дата подготовки), `targetDate` (дата уроков), `boardToken`, `subjects[]`. Для `parent` обязателен `studentToken`. `familyId` и `childId` задаются вместе; при активных страницах материалов обязательны оба. Каждый `subject` имеет `id` и `tasks[]`; каждый `task` — уникальный в документе `id`, `title`, `kind` и `status`. `meshText` хранит точную запись МЭШ, `source` — происхождение, `steps` — подтверждённые действия. `task.testToken` и `testSlug` заполняются только если тест назначен этому заданию. `testPlacements[]` показывает его в предмете; это **связь**, а не самостоятельный источник нового задания. `materialLinks[taskId]` хранит адреса доказательств и может содержать архивные ссылки более раннего дня. `taskPageRefs[taskId]` хранит активные ссылки на страницы общего каталога. `evidenceDayTokens[]` связывает работу по прошлым дням. `notices`, оценки, расписания, `weekendSlot`, `planRevision` и `changes` — поля проекции и истории выпуска. `parentGuide` и найденный ключ ответа запрещены в обеих открытых страницах; они живут в `dayTaskGuides`.

Для сверенного листа подготовки `task.practiceVariants[]` задаёт стабильные ID вариантов, а `problem.variantId` связывает пункт с вариантом. `dayPages.practiceVariantIds[]` — ограниченный список допустимых ID для семейного переключателя. События `dayParentDecisions` с `variant-required`/`variant-optional` действуют до первой проверки и не меняют МЭШ или исходный лист. Ответы к пунктам по-прежнему находятся только в закрытом `dayTaskGuides`.

Для опубликованного родительского `learning-route` множество `dayProgress.checkableStageIds` после проверки фото равно множеству `dayTaskGuides.guide.stages[].id`; каждому ID соответствует хотя бы один `dayProgress.items[].stageId`. `checkedAt` задаёт версию этой проверки, а `dayParentDecisions` хранит отдельные решения семьи для неё. Отсутствие ID в старом разборе не трактуется как выбор «по желанию»; оно требует адресной коррекции связи, без переписывания фото или школьного задания.

`dayDashboards` v1: обязательны `schemaVersion: 1`, `kind`, `timezone`, `days[]`. В каждом дне уникальная `date`, `schedule[]`, `homework[]`; `dayToken` ведёт к расписанию выбранной даты, `homeworkDayToken` — к опубликованному ДЗ к этой дате и может указывать на более ранний день при точной ссылке МЭШ. `checkedAt` — время последней проверки МЭШ, не дата самого задания. `complete` говорит о полноте снимка, а не о выполнении ДЗ ребёнком. `weekendWork[]` сохраняет отдельные выходные работы.

<a id="dashboard-date-projection"></a>
### Дата календаря и дата сводки

`days[].date` — дата урока по Москве, `schedule[].start/end` — времена урока из снимка МЭШ (`day/dashboard-index.mjs`). Эти поля принадлежат опубликованному ролевому индексу; `DayDashboard` читает их, но не записывает обратно. `viewDate` — локальный выбор пользователя, при переходе из кабинета ребёнка он равен сегодняшней московской дате. Если сегодняшней строки в индексе ещё нет, интерфейс оставляет сегодняшний день без подтверждённого расписания: соседняя дата не подменяет его. Выбор другой даты внутри календаря остаётся локальным состоянием.

Сводка ребёнка в `ParentHome` вычисляет свой `focusDate` из первого начала урока **этого ребёнка**: до него показывает ДЗ к сегодняшнему уроку, после — к ближайшему следующему учебному дню. Нижняя карточка календаря вычисляет дату ДЗ отдельно, как ближайшую опубликованную дату позже `viewDate` с расписанием или ДЗ. Строки расписания относятся только к `viewDate`; завершение урока определяется `schedule[].end` и меняет раскрытие компонента, а не статус выполнения ДЗ. Некорректное либо отсутствующее время конца не служит доказательством, что урок закончился. `focusDate`, дата нижней карточки и состояние раскрытия не являются новыми полями Firestore и не требуют миграции v1. [Причина разделения](../../modules/school-diary/dashboard.md#progressive-schedule); [компоненты](../design/components.md#registry).

`assignments` v1: `testId` — стабильная идентичность теста, `title`, `subject`, `questions[]` с уникальными ID, `status: open|submitted`, `answers`, временные поля попытки. `familyId/childId` изолируют нового ученика; старые назначения без этих полей читаются через проверенную старую ссылку до адресной миграции. `linkedToTestId` обозначает следующий тест той же линии, не новую попытку первого. `dashboard/.../assignments/{quizToken}.testId` должен совпадать с `assignments/{quizToken}.testId`.

Выбор родителя по обязательности теста хранится только у исходного назначения: необязательное `familyOptional: boolean`, `familyChoiceAt`, `familyChoiceBy`. Отсутствие флага означает обязательный тест. Продолжения находят исходное назначение по `linkedToTestId`; правило записи ограничено родительской ролью и этими полями. Проекция обязательных действий описана в [спецификации тестов](../../modules/assessments/quizzes.md#optional-quiz).

Дополнительные поля v1 допускаются для старых клиентов, но не могут менять смысл перечисленных связей. Новое обязательное поле требует новой версии или адаптера чтения. TypeScript-типы: [`dayStore.ts`](../../../src/lib/dayStore.ts), [`dayDashboardStore.ts`](../../../src/lib/dayDashboardStore.ts), [`quiz.ts`](../../../src/lib/quiz.ts). Проверка формы в рантайме применяется к основным публикуемым узлам; полный перечень вторичных полей в типах ещё не превращён в независимую машиночитаемую схему. Это открытая граница проверки, а не молчаливое обещание полноты.

<a id="edges"></a>
## Инварианты связей

1. В одном `dayPage` каждый `task.id` уникален. Переиздание использует прежний `taskId`; работа и попытки не пересоздаются.
2. Если у задания есть `testToken`, существует **ровно одна** `testPlacement` с тем же `taskId`, `subjectId` и голым токеном. Маршрут `slug~token` хранится только как URL, никогда как `token`. Отдельный тест без `taskId` допускается в предмете.
3. Каждый `testPlacement.token` указывает на существующие `assignments/{token}` и ролевую запись `dashboard/{boardToken}/assignments/{token}` с одинаковым `testId`. При наличии владельца его `(familyId, childId)` совпадает со страницей.
4. Родительская и ученическая страницы одной даты содержат одинаковые публичные `taskId`; родительский `studentToken` указывает на ученическую страницу. Закрытый ключ не попадает в `dayPages`.
5. Активный `taskPageRefs` принадлежит существующему заданию, а ссылка ведёт на опубликованную общую страницу и совпадающую семейную проекцию. Для учебника новое право семьи подтверждается её загрузкой и `books/{bookId}`; назначенный учителем лист получает право из конкретного задания МЭШ. `materialStatus: textbook-page-linked` требует видимой ссылки страницы. Архивные `materialLinks` не удаляются лишь потому, что прежнего задания нет в текущем срезе.
6. Публикация не изменяет `assignments.answers`, `dayUploads`, `dayProgress` и личные подсказки. Дедупликация материалов не объединяет личные результаты.

<a id="integrity-gates"></a>
## Проверка перед записью и после неё

`npm run day -- validate YYYY-MM-DD` проверяет авторский источник. `publish` строит обе ролевые страницы, проверяет форму, уникальность ID, все ссылки тестов на **реальные** документы и основание семейного доступа к каждой странице до `batch.commit`; после записи перечитывает страницы и индекс. Создание теста также проверяет форму `assignment` перед записью и после неё; добавление теста в список роли отвергает повреждённое назначение. [`materialGrantError`](../../../day/material-access.mjs) не позволяет выдать страницу общего учебника семье без её собственной связи `books/{bookId}` и совпадающего хэша издания; лист учителя допускается только по назначенному вложению. `npm run day -- audit` читает все даты из закрытого реестра ссылок, сравнивает обе роли и доступность страниц общего и семейного каталога. При ошибке команда завершается неуспешно и называет дату/роль; это сигнал исправить данные, а не скрыть сообщение в интерфейсе. Эти проверки не гарантируют доступность внешних сервисов после выпуска.

`npm run check:spec`, `npm run typecheck` и тесты слияния, формы, графа и миграции проверяют код локально. Новый вид документа добавляется в этот контракт, валидатор, тесты обеих ролей и карту файлов до публикации.

## Совместимость и миграция

Клиент читает известные v0/v1 страницы через [`normalizeDayPage`](../../../src/lib/dayCompatibility.ts): нормализует старый формат токена и временно игнорирует устаревший дубликат связи, но **не пишет** исправление из браузера. Неизвестная будущая версия блокирует только несовместимый экран и предлагает обновить приложение. Сбой сети или отсутствие теста не трактуется как смена схемы.

Up-миграция узкая: снимок затрагиваемых связей в закрытой `.local`, сухой прогон, проверка новой формы и всех внешних узлов, атомарное обновление обеих ролей с проверкой `updateTime`, повторное чтение и полный аудит. Для старой ошибочной привязки: `npm run day -- repair-placements YYYY-MM-DD` (просмотр) и затем `--apply`; меняется только `testPlacements`, история попыток остаётся. Down допустим лишь когда сохранённый снимок **снова проходит текущие инварианты** и точно соответствует ожидаемой ревизии. Автоматически возвращать известную битую ссылку запрещено; снимок остаётся для расследования.

Для страницы листа учителя с подтверждённым заданием есть отдельная узкая команда `npm run day -- repair-teacher-projections YYYY-MM-DD [--apply]`: она проверяет оба ролевых документа и общий оригинал, затем добавляет лишь отсутствующую семейную проекцию. Для страницы учебника команда останавливается: сначала требуется доказать собственную загрузку семьёй и точное издание. Нельзя использовать уже существующий общий PDF как такое доказательство.

Ранние страницы дня могли хранить семейного владельца только в `dayOwners/{studentDayToken}`. Для страницы с материалами это недопустимая незавершённая миграция: клиенту нужен `(familyId, childId)` в самой ролевой странице. `npm run day -- repair-owner YYYY-MM-DD [--apply]` переносит **только** два поля из существующего `dayOwners`, проверяет даты и ревизии обеих ролей, сохраняет закрытый снимок и перечитывает результат. Никакой владелец не выводится из названия школы, учебника или токена.

Повторная публикация теста заменяет действующую связь атомарно в обеих ролях. Если прежний токен остаётся рядом с новым, граф нарушен и выпуск должен остановиться до изменения Firestore. Причина появления этого правила и адресная коррекция сохранены в [событии аудита](petr-private:events/2026/10/2026-10-12-033-firestore-model-integrity-and-migration.md); действующий контракт остаётся независимым от даты инцидента.

## Общие аудиозаписи

По [аудиоконтракту](../../modules/materials/audio-library.md) `materialAudioCollections/{id}` хранит только общий индекс и метаданные MP3; `storedObjects/{sha256}` — один объект Диска. `audioLibrary` в существующей подтверждённой семейной связи `books/{bookId}` проецирует выбранные записи ребёнку, `dayPages.materialLinks` — конкретному заданию. Общий каталог закрыт существующим deny; членство и прежние семейные правила ограничивают проекции. Прослушивание не пишет учебный результат.

Семейная библиотека: `children/{childId}/books/{bookId}` с `accessScope:family`, `inheritedFromChildId`, `status:provisional` — проекция права чтения загруженной семьёй книги, не подтверждение школьного назначения. Соответствующий проверенный манифест доступен в собственном `bookPages`; попытки, оценки и персональные evidence не наследуются. [Общий контракт](../../modules/materials/family-library.md#family-access).
