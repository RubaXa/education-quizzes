# Система спецификаций и связь с кодом

Корень продукта — [product/README](../product/README.md), вход для агента — [навигатор](../README.md), карта приложений и модулей — [ARCHITECTURE](../../ARCHITECTURE.md). Их цель — направить к необходимым контрактам без загрузки всего каталога в контекст.

## Один владелец правила

Пользовательский сценарий принадлежит продукту, поведение исполняемого процесса — сервису, предметная семантика — модулю. Общий контракт задаётся один раз и переиспользуется ссылкой. История решения остаётся в `decisions`, исследование — в `research`, датированная проверка — в `audits`, план — в `plans`. Перенос документа не разрешает удаление принятого требования или объявление целевой функции работающей.

## Метаданные

У каждого документа в `product/services/modules/shared/operations/decisions/research/audits/plans`, `docs/README` и `ARCHITECTURE` есть YAML: `id`, `status`, `implementation`, `parent`, `uses`, `sections`. Единственный корень `product.education` не имеет parent. Устойчивый `id` сохраняется при переносе файла.

- `status`: `draft` — проект; `accepted` — действующий контракт/принятое решение; `reference` — исследование, индекс или свидетельство; `superseded` — явно заменённое правило.
- `implementation`: `planned`, `partial`, `implemented`, `not-applicable`. Этот флаг относится к исходной реализации и не доказывает deployment. Смешанное состояние отмечается `partial` и уточняется в тексте.
- `parent` задаёт иерархию владения, без циклов; `uses` — явные зависимости на ID других контрактов. Допустим пустой список `[]`.
- `sections` — обязательные якоря всех разделов H2 в порядке документа; `[]` разрешён только при отсутствии H2. У каждого контракта ровно один H1, уровни заголовков не пропускаются. HTML-якорь не заменяет обязательный раздел. Для новых контрактов используй [шаблон](../templates/specification.md).
- `created` и `updated` — реальные календарные даты `YYYY-MM-DD`; `created` — первый известный git-записанный день документа, `updated` — день последнего содержательного или metadata-изменения. `created` не позже `updated`. Эти даты описывают историю документа, а не выпуск или deployment.
- `consumers` — непустой список уникальных строк с реальными потребителями контракта. `code` — список уникальных repo-relative runtime-путей (либо `[]` для черновиков, планов и документов без исполнения); каталог `docs/` и тестовые файлы сюда не входят.
- Дополнительные `related`, provenance и старые данные frontmatter сохраняются. ID не зависит от даты файла или конкретной семьи.

## Граф

Граф выводится из метаданных и единственной [карты файлов](../file-map.md). Рёбра: `contains` (из parent), `uses`, `implements` (файл → ближайший контракт) и `verified-by` (контракт → привязанный тест). Последнее фиксирует связь с проверкой, а не полноту всех требований.

У каждого файла в file-map есть действующий локальный контракт, назначение и потребитель. В сложном коде `@see` ведёт к конкретной секции; компоненты сохраняют обязательные ссылки. Файлы исследований и аудитов также имеют карту, но код должен ссылаться на нормативную границу, а исторический материал использовать как основание.

Для нормативных документов `product/services/modules/shared/operations` со статусом исполнения `partial` или `implemented` поле `code` непусто. Каждый указанный путь должен существовать в проверяемом snapshot, иметь строку в file-map с назначением и потребителем и содержать `@see` с прямым относительным URL на этот документ (разрешён `#anchor`). Связь many-to-many допустима: file-map не обязан назначать этот документ ближайшим/единственным владельцем кода. Проверка `@see` ищет именно аннотацию, а не произвольное упоминание URL в тестовых строках. `draft`/`planned` могут иметь `code: []`; решения, аудиты, исследования, планы и навигационные документы могут иметь `not-applicable` без кода. `implementation: implemented` описывает реализацию в исходниках и само по себе не означает rollout или deployment.

Производные `docs/generated/graph.json`, `graph.mmd` и [сводка состояния](../generated/status.md) детерминированы. Сводка отражает только метаданные и не доказывает смысловую полноту или deployment. `npm run specs:generate` обновляет артефакты; `npm run check:spec` отвергает устаревший результат. Отдельного ручного реестра графа нет.

## Размер и расширение

Один контракт обычно занимает 100–400 строк; предел — 700. Дочерний документ выделяется по самостоятельной ответственности, без копирования правил родителя. Карта файлов, машинные артефакты и учебные коллекционные индексы не являются монолитной спецификацией и не ограничиваются этим пределом.

## Проверки и приватные границы

Валидатор проверяет статусы, ID, даты, consumers/code, parent/uses, локальные Markdown-ссылки и якоря, `@see`, checkout boundary, карту исходников и актуальность графа. Рабочая папка и `--staged` используют один алгоритм на собственном snapshot; staged-проверка читает содержимое и наличие файлов только из Git index, не подмешивая рабочие копии. Значимые отрицательные сценарии валидатора находятся в `scripts/spec-graph.test.mjs`. UI gate продолжает проверять запечатанный baseline; перенос ссылок не меняет baseline и оформляется отдельным traceable решением.

Ссылки на закрытые события, навыки и отчёты PETR хранятся как явный `petr-private:<workspace-relative-path>` reference. Они сохраняют происхождение, но не являются переносимым контрактом checkout. Нормативное правило должно быть описано локально; приватное свидетельство не копируется в публичный репозиторий.

При изменении поведения обновляются ближайший контракт, code mapping, решение и подходящая проверка. Статическая связь не доказывает смысловую корректность: её проверяют по сценарию и фактическому источнику. Результат выпуска подтверждается отдельным readback/deployment evidence. Группирующий H2 может раскрывать содержание через дочерние H3; проверяется наличие раздела, а не смысловая полнота его текста.


## Быстрая проверка при коммите

`npm run check:docs` проверяет рабочую папку. Lefthook запускает `node scripts/check-docs.mjs --staged` на каждом pre-commit: проверяется точный Git index, включая частично подготовленные файлы и удаления. Ошибка блокирует коммит с именем файла и причиной. После установки зависимостей `npm run prepare` устанавливает Git-хуки.

Проверка использует только Node.js и локальный Git: YAML-метаданные, уникальные ID, обязательные H2 и их порядок, один H1, иерархия заголовков, предел 700 строк, parent/uses и циклы, локальные Markdown-ссылки (включая reference-style), якоря, ссылки `@see`, полнота и корректность карты файлов. Внешние URL и `petr-private:` не проверяются по сети. Учебные коллекции вне каталогов спецификаций проходят проверку локальных ссылок, но не шаблона секций.

Это статическая проверка без LLM, сборки приложения и тестов. Примеры внутри fenced code не считаются ссылками или разделами. `npm run check:spec` дополнительно проверяет актуальность производных graph.json/graph.mmd и UI-контракты. После изменения метаданных или карты файлов выполняй `npm run specs:generate`. Тесты инструмента: `scripts/spec-graph.test.mjs` и `scripts/check-docs.test.mjs`.
