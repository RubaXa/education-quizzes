# Сводка изменений и история работы

## Решение пользователя

18.10 родитель выбрал сводку изменений и связанную историю каждой работы по эскизам в чате. Уведомление сообщает, какая работа изменилась, что произошло, подтверждённый результат и короткое действие/причину, когда они есть в источнике. UI Kit — каталог разработки; кнопка перехода в него запрещена во всех новых уведомлениях, включая операторские демо. Каталог на сайте сохраняется.

## Идентичность работы

Связь выводится только из проверенных owner/page/task metadata. Имя, название, предмет и совпадение дат не являются ключом. Для Firestore upload/review одной exact day task передаётся единый hashed work reference; разные дети, семьи, задания и исходные дни не смешиваются. Перенос задания между днями требует явного подтверждённого alias; сходство названий не склеивает историю.

В ledger/checkpoint/outbox/history не добавляются raw task/day access tokens. Work reference, scope и любые новые поля проходят единый port/schema validation; повторная нормализация сохраняет identity. Контекстное обогащение baseline не создаёт нового учебного события.

Сериализуемый контракт расширяет v2 optional полями; legacy части без них остаются валидны:

| Поле | Валидация и смысл |
|---|---|
| `event.workRef` | `{kind: "day-task", id: SHA-256 hex}`; только подтверждённые Firestore upload/review, без дополнительных ключей |
| `part.workRefs[]` | Точные уникальные работы, фактически показанные в этой части |
| `part.workOrderBindings[]` | `{workRef, order}` для всех показанных уникальных событий; order = canonical ISO detectedAt + `:` + eventId, включая объединённые файлы |
| `part.replyToMessageId` | Положительный safe integer; только фактически подтверждённый receipt в том же изолированном recipient scope |

Для каждого workRef receipt выбирает максимальный order именно своей части; eventId/detectedAt history row соответствуют этому событию. Число изменений в шапке считает уникальные подтверждённые события, а не число сгруппированных строк.

## Сводка и продолжение

Одновременные подтверждённые изменения остаются одной компактной сводкой в окне30с тишины/60с максимального возраста. Общие ребёнок/предмет/дата не повторяются у каждой строки; смешанные и отсутствующие значения не приписываются соседям. Максимум6записей об изменениях/1200символов на часть сохраняется, подробности не превращают её в огромную карточку.

Несколько upload.confirmed с разными подтверждёнными eventId одной exact workRef внутри одной reply bucket отображаются одной строкой с числом полученных файлов. Повтор одного eventId счётчик не увеличивает; разные работы/отсутствующие identity не склеиваются. Все соответствующие orders остаются привязаны к части.

Первое отправленное сообщение может содержать несколько работ. Следующее изменение известной работы отвечает на её фактически отправленное сообщение Telegram. Если в пачке есть разные цепочки, они получают корректные отдельные parts; reply target нельзя выбирать по первой строке всей пачки. Работа, впервые появившаяся в этой системе, начинает новую сводку; исторические уведомления не пересылаются для построения цепочки.

Переход результата показывается только при известном предыдущем состоянии: «Нужна правка → проверено». Краткая причина/следующий шаг берётся из разрешённого публичного результата проверки, санитизируется и ограничивается; отсутствие текста не заменяется догадкой. Нельзя обещать подсчёт ошибок/фото без подтверждённых полей. Детектор/formatter не вызывает LLM.

## Подтверждённая история

Persistent история изолирована по chat/family/person/link/child/work. Она хранит receipt messageId и минимальное состояние последней отправки, а не дублирует исходные работы/ответы. Receipt части и соответствующие work pointers фиксируются атомарно под действующей job lease. Повтор записи receipt идемпотентен; перезапуск между частями не теряет связи и не повторяет подтверждённую часть.

Поздний retry старой job не откатывает указатель более нового сообщения. Параллельные claims одной работы сериализуются либо используют эквивалентное доказуемое fencing; остальные семьи продолжают обслуживаться. Отзыв доступа проверяется перед каждым send, прежняя link не передаёт историю новой привязке.

## Ошибки и совместимость

Новые parts хранят immutable reply plan и принадлежность работ частям. Legacy v1/v2 без work reference продолжают исполнение и не склеиваются по названию. Отсутствующая история — нормальный первый message, не причина dead-letter. ReplyParameters использует allow_sending_without_reply:true: Telegram может доставить сообщение при удалённом parent без второго вызова. Network/429/5xx не запускают дополнительный немедленный send. [Официальный контракт Telegram](https://core.telegram.org/bots/api#replyparameters), проверено18.10.2026.

Любой at-least-once риск между send и receipt сохраняется; exactly-once не обещается. Уже отправленные сообщения не удаляются и не переписываются для миграции. Старые outbox parts остаются неизменяемыми; запрет UI Kit применяется к отправке клавиатуры, а не к повторной рассылке старых событий.

## Проверки

Обязательны: upload→review→correction, первоначальная сводка нескольких работ и корректные последующие replies, одинаковые названия разных работ, разные children/families/links, mixed цепочки в одной пачке, перезапуск/partial receipts/429/timeout, deleted reply target, competing workers и delayed retry, отозванная link, first/legacy events без истории, отсутствие UI Kit кнопки во всех transport/демо путях. UI Kit использует тот же production VM и показывает сводку/историю на условных данных без семейных чтений. Реальный внешний readback отдельно от unit tests и макета.
