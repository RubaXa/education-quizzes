# Local-first синхронизация Education

Статус: **вариант расширенного протокола**, полный протокол ещё не реализован. По [пересмотру через горячие пути](../../decisions/local-first-hot-path-decision-2026-10-12.md) `head → delta` больше не считается обязательным первым шагом или универсальным решением: сначала измеряются маршруты, сокращаются широкие чтения и проверяется встроенный постоянный кеш Firestore. Этот документ сохраняет проект протокола для тех путей, где измерения докажут его выгоду. Изолированный [пилот проверки head → delta](local-first-verification.md) работает на фейковом источнике и IndexedDB, не подключён к рабочему клиенту. Связанные контракты: [семья и роли](../../modules/families/README.md), [модель данных](../../shared/data/firestore.md), [глобальный сбор](../../modules/synchronization/global-sync.md), [тесты](../../modules/assessments/quizzes.md), [экраны](../../modules/synchronization/backend-driven-ui.md).

Фактическая разбивка Cloud Monitoring и Usage Insights от 12.10.2026, а также исправление повторного подсчёта страниц: [разбор нагрузки](../../audits/firestore-usage-2026-10-12.md). Для каждой группы данных, её владельца, причины изменения и правила локального чтения есть [матрица ревизий](../../shared/data/revisions.md). [Исследование сокращения чтений и выбора движка](../../research/firestore-read-reduction-research-2026-10-12.md) содержит варианты, критерии, риски и сценарии измерения.

<a id="decision"></a>
## Решение

Экран строится только из локальной IndexedDB. Firestore остаётся долговременным общим хранилищем между устройствами, но браузер использует его для получения **изменений**, подтверждения записи и проверки доступа. На старте приложение показывает последний целостный локальный срез, проверяет компактный указатель ревизий и загружает только изменившиеся каналы. При открытой странице подписка существует на указатель, а не на все документы дня, тестов, страниц и попыток. Исключение — точечное подтверждение действия, для которого нужна актуальная версия сервера.

Общие учебные материалы дедублицируются по содержимому и изданию. Семейный канал содержит разрешённые ссылки на них. Попытка теста, фото, подсказки, ошибки и траектория принадлежат конкретному ребёнку. Родительский эталон и ключи никогда не попадают в ученический канал или его локальную базу.

<a id="audit"></a>
## Что сейчас создаёт чтения

Это статический аудит путей, **не** распределение показанных в консоли 48 тысяч чтений по источникам. Такое распределение требует метрик Firestore; в день исчерпания квоты новые запросы ради аудита не запускаются.

|---|---|---|

Одинаковые подписки внутри одной вкладки SDK может объединить; два React-потребителя не доказывают двойной счёт. Но они сохраняют сложность и риск повторных подписок при навигации. Firestore тарифицирует документы первоначального результата запроса и изменения в подписке; без постоянного кеша переподключение может тарифицироваться как новый запрос. Поэтому обычное включение SDK-кеша полезно, но **не заменяет** узкие запросы и протокол ревизий. [Правила тарификации](https://firebase.google.com/docs/firestore/pricing), [постоянный веб-кеш](https://firebase.google.com/docs/firestore/manage-data/enable-offline).

<a id="operator-upload-index"></a>
### Индекс активных загрузок PDF

Оператору нужны только `bookUploads` со статусами `requested`, `awaiting-upload`, `uploaded`; законченные PDF остаются в истории семьи, но не должны читаться при каждом перезапуске процесса. Для фильтрованного `collectionGroup` нужен отдельный индекс `bookUploads/status` с областью `COLLECTION_GROUP`. [Описание индексов Firebase](https://firebase.google.com/docs/firestore/query-data/index-overview). `scripts/ensure-book-upload-index.mjs` читает текущие настройки поля, сохраняет существующие индексы коллекции и по явному `--apply` добавляет только этот индекс. Пока он строится, `direct-upload-worker.mjs` сохраняет прежний listener и повторяет узкий запрос раз в пять минут. Старый listener снимается только после получения полного первого снимка активной очереди. Обработчик по-прежнему перечитывает саму заявку перед записью результата.

Этот шаг сокращает первоначальный набор PDF-заявок, а не все чтения процесса: глобальный `dayOwners` и подписки на фото ещё остаются. Следующий шаг — адресная очередь активных владельцев с параллельной записью старого формата, сверкой активных заявок и сохранением прежнего обнаружителя до полноты новой очереди. Нельзя просто ограничить владельцев текущей неделей: старая загрузка может оставаться незавершённой.

Измерение 12.10 до переключения: агрегированные счётчики Firestore показали 2 PDF-заявки, 0 активных PDF-заявок, 7 владельцев дней и 2207 семейных `bookPages`; Cloud Monitoring за 19–21 ч МСК показал 10 568 QUERY и 5383 LOOKUP. Разные счётчики нельзя складывать или приписывать одному экрану. Узкий PDF-listener экономит при рестарте только исторические PDF-документы; более значимая следующая гипотеза — отдельный компактный манифест готовой книги, получаемый при открытии вместо сотен `bookPages`, с неизменными правами семьи и прежним постраничным путём как fallback. Сначала проверить размер манифеста и сравнить оплачиваемые чтения, время показа и переданный объём.

<a id="model"></a>
## Контракт ревизий и каналов

1. У каждой публикуемой сущности есть `schemaVersion`, стабильный `entityId`, `entityRevision`, `scope`, `sourceRef`, `contentHash` и состояние `active`/`deleted`. Удаление — явный tombstone, чтобы локальная копия не оставалась навсегда.
2. У каждой семейной аудитории есть один малый **head**: `familyId`, `audienceId`, `epoch`, `minSupportedSchema`, `channels: {name: revision}`. Аудитория задаётся человеком и ролью; нельзя передать родительскую часть через ученический head. Каналы: `calendar`, `tasks`, `materials`, `submissions`, `reviews`, `quizzes`, `guidance`, `grades`, `inbox`, `access`. Каналы ребёнка адресуются также `childId`.
3. Изменения публикуются неизменяемыми пакетами `{channel, revision, previousRevision, epoch, operations[], checksum}`. Пакет содержит только разрешённые аудитории проекции, в разумном ограничении размера документа Firestore. Публикатор записывает пакеты и новый head как один согласованный коммит; head никогда не указывает на неполный пакет.
4. IndexedDB хранит `entities`, `channelCursors`, `outbox`, `conflicts`, `scopeMetadata`. Ключ каждого личного объекта включает `personId/familyId/childId/role`; общий материал хранится по хэшу, а право его показать определяется отдельной локальной семейной проекцией.
5. `epoch` и миграция `schemaVersion` позволяют заменить формат без пересоздания попыток. При несовместимом формате клиент держит локальный черновик, прекращает отправку и показывает действие обновления приложения. v1 и v2 работают параллельно до сверки и закрытия старых клиентов.

<a id="algorithm"></a>
## Алгоритм клиента

1. После восстановления личности открыть её namespace в IndexedDB и показать последний **целиком применённый** снимок с пометкой времени сверки. Не считать локальный снимок доказательством свежести МЭШ.
2. Один раз на старт подключить head для каждой доступной семьи/аудитории; затем держать **одну** подписку на head, общую для всех маршрутов и вкладок этого профиля. На неизменной ревизии не запрашивать сущности. Локальные переходы между экранами обращаются только к IndexedDB.
3. Для канала, где `remoteRevision > localRevision`, получить пакеты диапазона `(localRevision, remoteRevision]` страницами. Если пакеты отсутствуют, последовательность нарушена или checksum не совпал, запросить ограниченный полный снимок этого канала и поднять диагностический сигнал; не объявлять синхронизацию успешной.
4. Применить операции, tombstones и новый курсор одной транзакцией IndexedDB. До её завершения React продолжает видеть старый целостный срез. При обрыве повторить пакет идемпотентно. При нескольких открытых вкладках одна вкладка владеет сетевым каналом, остальные получают локальное оповещение через `BroadcastChannel`.
5. Любое действие пользователя сначала записать в IndexedDB outbox с `operationId`, `baseRevision` и фазой `local/queued/sending/acknowledged/rejected`; только затем обновить экран. Передавать при сети небольшими пакетами с ограничением параллельности и повтором. Подтверждение сервера или последующий delta-пакет снимает запись outbox. Конфликт не стирает локальный ответ: он остаётся доступным для сверки.
6. Завершение теста разрешать только после серверного подтверждения всех ответов и самой команды отправки. Прогресс на экране отдельно показывает локально сохранённое, принятое сервером и окончательно отправленное. Фото и PDF используют свои долговечные очереди файлов; метаданные входят в тот же протокол ревизий.

Первый запуск нового устройства требует начального снимка. Он может состоять из нескольких документов/пакетов из-за лимита размера документа; обещание «одно чтение на всё» было бы технически ложным. Один head служит **одной точкой проверки ревизий**; после него читаются только недостающие пакеты. Если у человека несколько семей, есть по одному изолированному head на семью.

<a id="publisher"></a>
## Публикатор EducationSync

Операторский цикл хранит собственные курсоры источников локально (для Node — SQLite/журнал, не браузерная IndexedDB). Сканирование МЭШ, Яндекс.Диска, очередей фото и тестов идёт независимо и с ограниченной параллельностью. Каждая подтверждённая перемена сохраняет исходный артефакт, обновляет нормализованную общую сущность или личную сущность ребёнка, пересчитывает затронутые ролевые проекции и публикует только изменённые пакеты семейных каналов. Пустой прогон не повышает ревизию и не создаёт клиентских чтений. Состояния очереди и ошибки остаются отдельными данными, не переписывают уроки. В конце цикл повторно проверяет входящие события, возникшие во время обработки.

Миграция операторской очереди отдельно убирает полные `collectionGroup`-обходы из регулярного цикла: новые события попадают в индексированную очередь при загрузке/публикации; полный аудит истории запускается редко и явно. Курсоры, подтверждённое окно и контрольные суммы позволяют продолжить после сбоя без повторной публикации всех дней.

<a id="rollout"></a>
## Внедрение без потери действующего теста

1. **Инцидент.** Открытую старую вкладку ученика не обновлять. Сохранить текстовые ответы вне приложения; число `15 из 21` показывает только состояние экрана. При исчерпанной квоте нельзя подтвердить, сколько принято Firestore. Новую версию не выпускать как повод принудительно перезагрузить текущий тест.
2. **Страховка записи.** Перенести черновик теста из временного `localStorage` в IndexedDB, импортировать существующие ключи v1 без удаления до подтверждённого сервера, добавить outbox и отображение локальной/серверной фаз. Аналогично использовать существующую IndexedDB-очередь фото. Эта стадия восстанавливает запись, но ещё не снижает все чтения.
3. **Приоритет P0: фоновый загрузчик.** Убрать глобальные listeners всех дней и книг из `direct-upload-worker.mjs`, а также лишний `get()` уже завершённой загрузки. Передавать событие в адресную операторскую очередь при создании или смене фазы; worker берёт только активные элементы по курсору. Сверить полноту очереди и уже лежащих на Диске файлов до выключения старого пути.
4. **Наблюдаемость и быстрые сокращения.** Учесть число открытых потоков и начальных документов по экрану; убрать дубли inbox/профиля, ограничить историю тестов и страницы книги, не пересоздавать неизменные подписки. Сопоставить с Cloud Monitoring/Query Explain, не утверждая задним числом причину 48 тысяч.
5. **Параллельная публикация v2.** Добавить family/audience heads, пакетные delta-каналы, валидаторы и сверку проекций. Продолжать публиковать v1 для уже открытых клиентов. Проверить, что ученический пакет не содержит родительские ответы/ключи.
6. **Локальный рендер.** Переключать экраны по одному на IndexedDB-селекторы и общий sync-адаптер: сначала календарь/ДЗ, затем тесты и результаты, материалы, inbox и личные действия. На каждом этапе сравнивать v1/v2 хэши и результат карточек для обеих ролей.
7. **Отключение старых чтений.** Только после проверки всех семей и действующих клиентов удалить массовые подписки v1, затем закрыть старые ссылочные правила. Поддержать обратимый путь на время перехода; завершённые попытки и исходные фото не удалять.

### Текущий локальный срез миграции

Первый срез сокращения чтений сделан в коде, но не опубликован: [родительский экран](../../../src/components/ParentHome.tsx) сохраняет идентичность семейных списков между обновлениями; [колокольчик](../../../src/components/NotificationBell.tsx) больше не перечитывает профиль при каждом маршруте; [список тестов](../../../src/App.tsx), [сводки дня](../../../src/lib/useDayQuizOutcomes.ts), [сводка ребёнка](../../../src/lib/useParentChildOverview.ts) и [календарь](../../../src/lib/useDashboardDayWork.ts) не открывают прежние подписки заново, когда состав токенов не менялся. [Фоновый приёмник](../../../scripts/direct-upload-worker.mjs) слушает только активные статусы фото; старые завершённые фото не попадают в его начальный снимок. Для семейных PDF он пока отсекает завершённые элементы после глобального снимка: их чтения ещё предстоит убрать через адресную очередь, сохранив обработку старых заявок.

Черновик теста теперь дополнительно пишется в [IndexedDB](../../../src/lib/quizLocalStore.ts), а прежний `localStorage` остаётся совместимой страховкой открытого клиента. Опубликованные страницы подтверждённой семейной книги [кешируются в отдельной IndexedDB](../../../src/lib/materialPageCache.ts) по семейной привязке и её ревизии; [читатель книги](../../../src/components/FamilyLibrary.tsx) перечитывает Firestore при первом открытии нового набора, при неполной публикации или если локальный набор отсутствует. Одна книга теперь не держит постоянную подписку на сотни статичных страниц. Кеш принимается только при известном числе страниц, полном диапазоне PDF-номеров и совпадении хэша источника. Пакетные серверные операции добавлены к статусам синхронизации, повторным уведомлениям и чтению связанных результатов; они уменьшают сетевые раунды, **не** число оплачиваемых операций по документам.

Это **частичные локальные слои**, не полный local first: [Firestore-подписки](../../../src/lib/dayStore.ts) ещё открываются напрямую, а семейные heads, пакеты ревизий и атомарная проекция не опубликованы. По [новому порядку](../../decisions/local-first-hot-path-decision-2026-10-12.md) сначала измеряются повторные чтения, убираются ненужные потоки и на отдельном маршруте проверяется постоянный кеш Firestore. Серверный delta-контракт и сравнение IndexedDB с Dexie нужны только для пути, на котором будет доказана польза. RxDB Firestore plugin потребовал бы миграции существующих документов и всех писателей. До замера нельзя утверждать, что старт приложения делает только один запрос или что тариф Blaze устранил избыточные чтения.

Критерии приёмки: повторный вход без изменений не скачивает день, книгу или список тестов; изменение одного канала не читает остальные; повторное открытие экрана не увеличивает число подписок; офлайн-ответ переживает закрытие PWA и синхронизируется без дубля; пропуск ревизии восстанавливается; две вкладки не дублируют сеть; отозванная роль не получает новые пакеты; старый клиент сохраняет действующий тест; после полного EducationSync head меняется только для семей с изменениями.
