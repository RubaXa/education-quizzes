# Нагрузка Firestore: разбор 12 октября 2026

## Что измерено

Скриншот родителя показывает достижение отметки 50 тысяч чтений к 10:00 на оси Firebase Usage и пик 437 слушателей при 17 соединениях. Метрики проекта `education-9d7c6` прочитаны отдельно через Cloud Monitoring, без чтения документов Firestore. За окно 08:34–20:34 МСК: 39 707 чтений типа `QUERY`, 16 048 `LOOKUP`, 455 `NOT_FOUND`, 157 созданий, 1305 обновлений и 2628 `UPDATE_NOOP`; пик 437 слушателей и 17 соединений. `QUERY` составляет около 71% успешных чтений за это окно. Наибольшие почасовые пики `QUERY` пришлись на 16:00 (7579), 17:00 (9908) и 19:00 (5950) МСК. Даже без обновлений документов с 03:00 до 10:00 МСК сохранялось около 90 `QUERY` чтений в час. Эти числа относятся к окну мониторинга, а не к счёту на оплату.

Usage Insights в Google Cloud на момент просмотра показывал за скользящие сутки 29 509 операций чтения, с задержкой данных 1–2 часа. Лидирующие коллекции: семейные `bookPages` — 5752 read operations, 9506 scanned documents, 71 030 scanned index entries; `operatorSyncJobs` — 1613; `assignments` — 1390; страницы четырёх общих учебников — от 1042 до 1301 на книгу; `dayPages` — 1013. Эти счётчики Usage Insights имеют иную границу периода и состав, поэтому их нельзя складывать с 12-часовым рядом Monitoring или напрямую приравнивать к платёжному счёту.

Query Insights за скользящие сутки дополнительно показывает нормализованные запросы `COLLECTION /operatorSyncJobs` — 1463 read operations при 39 исполнениях — и `COLLECTION /dayUploads/*/files` — 1373 при 222 исполнениях. Это подтверждает повторные сканы очереди и множество запросов по дневным папкам фото. Метрика группирует одинаковую форму запроса и не сообщает, какой конкретно экран или запуск его вызвал.

У Google есть готовые инструменты: [Usage Insights](https://firebase.google.com/docs/firestore/enterprise/usage-insights) даёт группировку по коллекциям; [Query Insights](https://cloud.google.com/firestore/docs/query-insights) показывает нормализованные запросы, число исполнений и read operations; [Cloud Monitoring](https://firebase.google.com/docs/firestore/monitor-usage) даёт поминутные LOOKUP/QUERY, слушатели и соединения. [Query Explain](https://cloud.google.com/firestore/docs/query-explain) пригоден для конкретного запроса. Для глубокого журнала вызовов можно отдельно включать [Data Access Audit Logs](https://cloud.google.com/firestore/native/docs/audit-logging); он не восстанавливает события до включения и требует отдельной оценки объёма логов. Консоль Usage оценивает использование; при расхождении с ней платёжный отчёт имеет приоритет.

Бесплатная суточная доля — 50 000 чтений и сбрасывается около полуночи тихоокеанского времени, то есть 12 октября около 10:00 МСК. На Blaze пересечение этой отметки означает переход к тарифицируемому использованию, а не норму для нашего продукта. Смена тарифа не устраняет избыточные запросы. [Правила тарификации](https://firebase.google.com/docs/firestore/pricing).

## Вывод из кода и исправленный путь

`projectPublishedBookToFamily()` вызывался для каждой семейной книги во время каждого `sync:books` и выполнял `count()` по всем её страницам даже при совпадении завершающего маркера. На наших десяти семейных привязках это повторное сканирование индексов для 2192 уже опубликованных страниц. Теперь обычная синхронизация доверяет маркеру, который записывается **после** проверки полного числа страниц; при отсутствующем или устаревшем маркере перепроверка и публикация сохраняются. Для явного аудита есть `npm run sync:books -- --verify-family-pages`. Это сокращает регулярные чтения без перепубликации страниц. Доля этого конкретного `count()` в 5752 операциях Usage Insights исторически не установлена: ту же коллекцию читает браузер при открытии всей книги, и она использовалась при первичной публикации.

`sync:queue scan` теперь хранит локально отпечатки источников. Повторный проход по неизменившимся кандидатам не открывает для каждого из них отдельную транзакцию Firestore. Новый или изменившийся отпечаток по-прежнему проверяется и сохраняется в серверной очереди; отсутствующий или повреждённый локальный файл вызывает полную сверку. `npm run sync:queue -- scan --full-audit` принудительно проверяет всех кандидатов заново. Кеш записывается только после успешного полного прохода. Это оптимизирует повторный проход, но обнаружение источников всё ещё читает их из Firestore и потому не является полным дельта-протоколом.

В конце `scan` снимок активной очереди переиспользуется для отчёта, если во время разрешения задач не было изменений. При изменении серверная очередь читается заново, чтобы отчёт не показывал устаревший статус.

Остаточные источники требуют отдельного исправления: `sync-inbox` повторно сканирует общие коллекции; клиент одновременно открывает подписки на день, фото, разборы и связанные дни; локальный загрузчик держит `dayOwners` и по одной подписке на каждый набор фото владельца. Книга и подтверждённые ссылки страниц исправлены в отдельных выпусках ниже; это не закрывает остальные пути. Пик 437 слушателей подтверждён, но без трассы клиента нельзя честно назвать точную долю каждого экрана. [Пересмотр по горячим путям](local-first-hot-path-decision-2026-10-12.md) сначала проверяет сокращение широких чтений и постоянный локальный кеш; [расширенный delta-протокол](local-first-sync.md) остаётся условным вариантом там, где его выгоду докажут замеры. Частичные исправления страниц и очереди не означают завершение local-first перехода.

Срез открытия подтверждённой книги и последующий манифест выпущены поэтапно: опубликованную книгу теперь можно прочитать через один семейный манифест с кешем IndexedDB, а неполная публикация сохраняет прежний путь. Для дня опубликованные проверенные ссылки на страницы также читаются без дополнительных постраничных подписок; неполные связи продолжают проверяться. Классы данных и причины изменения описаны в [матрице ревизий](local-first-revision-matrix.md), порядок выпуска — в [поэтапном плане](local-first-release-plan-2026-10-12.md). Исторические метрики выше измерены **до** этих срезов; они не доказывают снижение всего счёта после выпуска.

## Как сравнивать дальше

<a id="сопоставимые-окна"></a>
`npm run firestore:usage -- 24` печатает агрегированные метрики Monitoring по часам МСК; `--minutes 10` даёт минутные корзины, а `--window ISO_FROM ISO_TO` — фиксированный интервал для пары «до/после» одинаковой длины. Команда не делает чтений Firestore. Сравнивать `QUERY`, `LOOKUP`, пик слушателей и сканирование коллекций в Usage Insights только при одинаковом числе открытых клиентских вкладок и без синхронизации/миграции посреди окна. Это общепроектный сигнал, не причинный A/B тест одного экрана. Прежде чем выключать старые подписки, подтвердить сохранение новых фото, тестов и обратную совместимость открытых клиентов.
