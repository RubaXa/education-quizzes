# Проверка перехода на семейные ревизии

Статус на 12.10.2026: **локальный пилот, без подключения к рабочему Firebase и без выпуска PWA**. После [пересмотра горячих путей](local-first-hot-path-decision-2026-10-12.md) это проверка одного возможного протокола, а не выбранный первый этап перехода. [Контракт синхронизации](local-first-sync.md#decision) описывает вариант; `src/lib/localFirstPilot.ts` проверяет его на настоящих транзакциях IndexedDB и подменённом источнике данных. Нынешние экраны по-прежнему читают документы v1. Успех пилота не равен успеху миграции приложения.

## Зачем два уровня проверки {#contract}

`fake-indexeddb` исполняет браузерный API IndexedDB в памяти Node. Поддельный Firestore-адаптер в `localFirstPilot.test.ts` отдаёт `head`, пакеты и снимки, считает прочитанные документы и позволяет намеренно терять/портить данные. Это проверяет наш код применения ревизий без доступа к семье и без оплачиваемых запросов. Локальное пространство адресовано `(familyId, role:personId/childId)`: два ученика одной семьи не делят кеш. `makePacket` и `makeSnapshot` вычисляют контрольную сумму из канонического JSON; клиент принимает пакет только для той же семьи, роли и участника, эпохи, канала и ожидаемой ревизии. Все изменившиеся каналы попадают в одну локальную транзакцию. Если пакет пропущен, нужен целый снимок; если и его нет, старое состояние остаётся целым.

Отдельный уровень для выпуска — **локальный Firestore Emulator Suite** с настоящими `firestore.rules` и тестовыми ролями. По [документации Firebase](https://firebase.google.com/docs/emulator-suite/connect_firestore) он изолирован от рабочего проекта, умеет очищать тестовую базу и показывает трассировку правил. Но он не проверяет составные индексы и все ограничения продакшена. Здесь он пока **не запускался**: на машине нет Java Runtime. Чисто поддельная база не доказывает права доступа и не измеряет оплачиваемые чтения. До включения v2 на реальных экранах нужны тесты правил на эмуляторе и ограниченный замер по реальным метрикам.

## Воспроизводимые сценарии {#scenarios}

Команда: `npm run test:local-first`. Фикстуры синтетические, без ученических данных. На локальном прогоне прошли восемь сценариев протокола и два сценария кеша страниц.

| Сценарий | Пилот v2 | Модель текущего пути | Вывод |
|---|---:|---:|---|
| Повторное открытие дня с dashboard и 8 отдельно назначенными страницами при новом подключении | 1 `head`, 0 тел | 9 документов по нынешней схеме отдельных подписок | Выигрыш **только для такого повторного подключения**; SDK может сохранить уже действующие слушатели, а кеш читателя полной книги — отдельный путь |
| Изменились только `tasks` | 1 `head` + 1 пакет | Зависит от числа открытых v1-подписок | Другие каналы не перечитываются |
| Календарь из одного документа без изменения | 1 `head` | 1 dashboard | Равенство по числу документов |
| Тот же календарь после изменения | 1 `head` + 1 пакет | 1 обновлённый dashboard | v2 читает **больше**; переход такого экрана пока не оправдан |
| Потерянный пакет | `head`, попытка пакета, снимок канала | — | Полное восстановление без частичного состояния |
| Порча пакета и отсутствие снимка | Ошибка; ни один канал не меняется | — | Сохранён предыдущий целый срез |
| Отзыв доступа к роли или ребёнку | Удалён только его локальный namespace | — | Взрослый и второй ребёнок той же семьи остаются изолированными |

Счётчик адаптера отражает **полученные документы в этих фикстурах**, а не счёт Firebase. Старый сценарий задан по текущему `watchMaterialPages`, который открывает отдельный listener на каждый назначенный `sourceRef`; он не является замером оплаченных чтений. В реальном Firestore начальные снимки слушателей, индексные записи, правила, переподключения и наличие уже открытой подписки влияют на итоговую стоимость. [Правила тарификации Firebase](https://firebase.google.com/docs/firestore/pricing) требуют измерять это отдельно.

## Миграция и обратная совместимость {#migration}

Пилот создаёт новую базу `education-projection-pilot-v2`; он не повышает версию существующей `education-local-v1` и не удаляет её черновики. Импорт старого dashboard идемпотентен и хранит совместимую копию. До прихода целого v2-снимка виден старый локальный срез; после успешной транзакции — новый. Тест одновременно сохраняет незавершённый ответ из действующего `quizLocalStore`. Отдельный кеш учебника принимает только полный набор страниц с тем же хэшем и ревизией привязки.

Серверной миграции пока **нет**: publisher `head`/delta, параллельная запись v1 и v2, правила Firestore для новых путей и механизм обратного переключения экрана ещё не реализованы. Поэтому проверка локального импорта не даёт права отключить v1. Старые клиенты должны продолжать читать и писать прежние документы до отдельного доказанного этапа.

## Барьеры перед переключением экрана {#release-gate}

1. На эмуляторе проверить `firestore.rules`: взрослый и ребёнок получают только свою проекцию; чужая семья, ключи и родительские эталоны ученику недоступны; обновление `head` и пакета публикуется атомарно.
2. Прогнать двойную публикацию v1/v2 и сравнить нормализованные карточки одной семьи в обеих ролях на одинаковом источнике; проверить повтор операции и откат к v1 без потери черновиков и фото.
3. Проверить два окна, офлайн, разрыв после записи пакета, повреждённую IndexedDB и отзыв семейного права в браузере, включая установленную iOS PWA. Поддельная база не воспроизводит поведение Safari целиком.
4. Сравнить холодный и повторный старт, `QUERY`/`LOOKUP`, billed reads, Rules reads, число listeners, записи и время до актуального экрана до/после на том же маршруте. Канал с одним документом не переводить только ради единообразия, если он станет дороже.
5. Включать v2 по одному экрану с флагом возврата; `v1` и текущие подписки остаются рабочими, пока метрики и целостность не подтвердят замену.

Для этапа эмулятора использовать [официальный запуск и очистку базы](https://firebase.google.com/docs/emulator-suite/connect_firestore) и [тестирование правил](https://firebase.google.com/docs/firestore/security/test-rules-emulator). Эмулятор не заменяет последний ограниченный замер живой системы.
