# Education: действия, просмотры и новое

Связанные контракты: [модель семьи](family-data-model.md), [экраны из данных](backend-driven-ui.md), [dashboard](../product/dashboard.md). Карта: [спецификации](../product/README.md).

<a id="implementation"></a>
## Состояние реализации

Адресный inbox работает для изменений ДЗ, которые публикует `scripts/day.mjs`: сервер записывает отдельные документы в `users/{personId}/inbox`, а клиент показывает их по живой подписке. Системные Web Push и журнал навигации остаются неактивными. Клиентские функции записи действий и просмотров подготовлены, но страницы их не вызывают. Для полного журнала открытий файлов дополнительно нужен [медиа-шлюз](family-artifact-access.md).

<a id="events"></a>
## Журнал действий

`families/{familyId}/activity/{eventId}` — добавляемый один раз факт. Событие содержит `schemaVersion`, `actorPersonId`, `deviceUid`, `childId`, `type`, `viewId`, `sectionId`, `entityId`, `sessionId`, `occurredAt` (серверное время). Основные типы: `page_opened`, `section_opened`, `day_opened`, `task_opened`, `test_started`, `test_submitted`, `submission_uploaded`, `notification_opened`. Для учебных изменений от сервера: `homework_published`, `homework_changed`, `homework_removed`, `grade_added`, `review_ready`.

Клиент не пишет в событие текст задания, ответы, фото, токены ссылок, OAuth-ключи или полный URL. Секреты и персональные материалы остаются в своих защищённых документах. `sessionId` — случайный идентификатор сеанса, не ключ доступа. Повторный показ того же раздела в одном сеансе не создаёт поток одинаковых событий; действия отправки сохраняются отдельно и связываются с предметной записью. Сбой записи аналитики не отменяет отправку работы.

Клиентские события описывают навигацию и взаимодействие, но не доказывают, что тест сдан или файл сохранён: такой итог подтверждается соответствующим документом и серверным событием. Родительский отчёт различает эти два источника.

<a id="read-state"></a>
## Просмотр и прочтение

Посещение страницы **не означает**, что ребёнок прочёл все блоки и выполнил ДЗ. `users/{personId}/views/{viewKey}` фиксирует увиденную ревизию конкретного раздела только после его открытия; действие хранит также `seenAt`. Новизна вычисляется относительно ревизии источника (`sourceRevision`), а не сравнением двух часов. Для индивидуальных уведомлений `users/{personId}/inbox/{notificationId}` хранит адресата, ссылку на предметное событие, `createdAt`, `readAt?`; открытие уведомления отмечает только его.

При публикации изменённого ДЗ `scripts/day.mjs` сравнивает новый индекс с предыдущим Firestore-индексом. Для добавленного, изменённого или снятого предмета каждому активному участнику семьи, имеющему доступ к ребёнку и нужную роль, создаётся личная запись. Первичная публикация индекса не вызывает шквал уведомлений. ID записи вычисляется из ребёнка, даты, предмета, типа, текста и времени источника; повторная публикация без изменения не создаёт дубль. Новые оценки и проверки пока не порождают записи inbox автоматически. Родительское прочтение не меняет состояние ученика, и наоборот.

<a id="in-app-center"></a>
## Центр обновлений внутри приложения

`NotificationBell` в общем заголовке подписывается на `users/{personId}/inbox`. Счётчик показывает непрочитанные записи, а список кратко указывает событие, предмет и дату. Открытие колокольчика ничего не помечает прочитанным. Нажатие на запись ставит `readAt`, выбирает дату на dashboard и раскрывает предмет в расписании. При открытом приложении новое событие появляется без перезагрузки и без навязчивого тоста. Это **внутреннее** обновление: при закрытом приложении оно не появляется на экране блокировки. Для нового типа события требуется привязать его к источнику, адресату и экрану назначения; нельзя показывать готовый текст ответа или персональные секреты в краткой записи.

Основание выбора: [Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/notifications) рекомендует при открытом приложении добавлять новое содержание и обновлять счётчик без отвлекающего баннера, не дублировать одно событие и показывать в счётчике именно непрочитанные записи. Цвет и точка не являются единственным признаком новизны: рядом остаётся текст события. Системное разрешение на уведомления для такого внутреннего списка не требуется.

<a id="analytics"></a>
## Отчётность и срок хранения

Журнал позволяет ответить, когда и кем был открыт день, конкретный раздел или задача, начат тест, загружена работа и прочитано уведомление. Для родителя это история действий ребёнка с серверным временем и ссылкой на предметную запись; отсутствие события означает только отсутствие зафиксированного действия. Сводки строятся сервером из журнала, а не доверяются клиентскому счётчику. Нужен явный срок хранения сырых посещений и агрегатов перед включением сбора для других семей; пока схема и правила подготовлены, но сбор не активирован.
