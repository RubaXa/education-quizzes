# Выпуск приложений и правил

Статический интерфейс Education собирается Vite и выпускается на GitHub Pages; данные публикуются в Firestore независимо от PWA. `npm run publish:pages -- --dry-run` показывает необходимость выпуска, обычный `publish:pages` использует проверенный build. Push `main` сам сайт не обновляет. Публикация Firestore Rules — отдельная операция.

Перед выпуском пройти штатные gates, проверить приватность исходной и сайт-ветки; реальные работы, токены и изображения материалов не входят в Git. Изменение исходников не считается deployment: выпуск должен подтвердить свой артефакт/адрес, а публикация данных — адресное обратное чтение.

Локальный upload worker устанавливается `npm run storage:install-worker` как LaunchAgent согласно [хранению](../modules/materials/storage-privacy.md); повторный ручной worker одновременно с ним не запускается. Установка после изменения кода отдельна от выпуска PWA.

Telegram worker установлен на согласованном Mac; актуальные release, readiness и ограничения доступности описаны в [операционном контракте](../services/telegram-bot/operations.md). Изменение worker выпускается штатным installer с тем же общим vault, затем проверяются running/readiness и совпадение release с итоговым кодом.

## Короткие итерации

`publish:pages` перед полноценным выпуском получает актуальный `origin/main` и требует чистое исходное дерево, совпадающее с ним. После сборки проверка повторяется перед push; изменение main прерывает выпуск. В сайт попадает `.source-release.json` с исходным commit/tree и отпечатком сборки. `--dry-run` и `--prepare-only` остаются диагностикой/локальной подготовкой и не публикуют сайт. Восстановление старого дерева gh-pages недопустимо: исправление объединяется с текущими исходниками и выпускается заново. Нормальный push без force защищает от конкурирующей записи сайт-ветки.

Основная интеграционная ветка репозитория — `main`. По прямому решению пользователя18.10.2026 завершённую согласованную итерацию доводим до неё в текущем цикле работы. Рабочая ветка и PR служат временной границей изменения.

1. Перед интеграцией получить актуальный `origin/main`, объединить изменения и разрешить конфликты по действующим контрактам; производный граф пересобрать штатным генератором.
2. Выполнить `npm run check` на объединённом коде и штатные Git-хуки. Сохранить параллельные изменения и незакоммиченные данные; не перезаписывать их ради чистого checkout.
3. Отправить проверенную итерацию и слить PR в `main`; проверить remote commit и результат слияния. Готовый PR сам по себе не считается завершённой интеграцией. Исключение — явное указание пользователя оставить черновик либо конкретная блокировка, о которой нужно сообщить.
4. Обновить соответствующий исполняемый сервис из итогового кода основной ветки и подтвердить установленный артефакт/readiness. Для неизменившегося runtime достаточно доказать побайтное совпадение с уже установленным release; лишний перезапуск не требуется. PWA выпускается при изменении её артефакта, правила и данные — своими штатными инструментами.
5. Синхронизировать основной локальный checkout с `main`, сохранив посторонние рабочие правки. В отчёте указать main commit, release и фактически выполненные проверки. Следующая итерация начинается от актуальной основной ветки.

При длительной незавершённой работе регулярно включать изменения `main` и выделять минимальные законченные инкременты. Не накапливать несколько готовых выпусков в отдельной ветке.
