# Local-first через горячие пути: пересмотр решения

**Состояние:** исследование и порядок проверки, без переключения рабочего клиента. Цель родителя — снизить оплачиваемые чтения Firestore и показывать сохранённые данные с устройства сразу. `head`, дельты и ревизии являются возможными средствами, а не требованием к каждому виду данных. [Прежний протокол](../services/web-app/local-first-sync.md) и [изолированный пилот](../services/web-app/local-first-verification.md) остаются материалом для сравнения; они не доказывают, что этот протокол нужен всему приложению.

## Что подтверждено

- Веб-клиент создаёт Firestore через `getFirestore(app)` в `src/lib/firebase.ts`; постоянный веб кеш SDK явно не включён. Офлайн хранение отдельных черновиков и страниц книги уже есть в своей IndexedDB. По документации Firebase в веб SDK по умолчанию используется кеш в памяти, а persistent cache можно включить явно. [Firebase: offline persistence](https://firebase.google.com/docs/firestore/manage-data/enable-offline).
- Стартовый родительский кабинет монтирует детальную сводку ребёнка даже при закрытой карточке; сводка открывает день, фото, разборы, решения и связанные тесты. Календарь одновременно читает выбранный и следующий день; страница дня добавляет отдельные подписки на страницы учебника. Это подтверждено путями `src/components/ParentHome.tsx`, `src/lib/useParentChildOverview.ts`, `src/DayDashboard.tsx`, `src/DayPage.tsx` и `src/lib/dayStore.ts`. Число React-подписчиков **не равно** числу оплаченных чтений: SDK может объединять одинаковые запросы.
- [Исторический снимок нагрузки](../audits/firestore-usage-2026-10-12.md) за разные окна показал 50 тысяч чтений на графике Firebase, пик 437 слушателей при 17 соединениях; в Usage Insights `bookPages` — 5752 операций, `operatorSyncJobs` — 1613, `assignments` — 1390, `dayPages` — 1013. Query Insights показал повторные сканы `operatorSyncJobs` и фото. Эти ряды нельзя складывать или приписывать одному экрану без трассы.
- Firestore тарифицирует начальные результаты и изменившиеся документы слушателя. При web persistence отключение/подключение может снова тарифицироваться как новый запрос; с persistence это происходит после отключения дольше 30 минут. Даже постоянный кеш сам по себе не обещает ноль чтений после долгого отсутствия. [Firebase: billing listeners](https://firebase.google.com/docs/firestore/pricing#listening_to_query_results).

## Политика по типам данных

| Данные | Как показать сразу | Когда обращаться к источнику | Где сейчас риск |
|---|---|---|---|
| Неизменяемые PDF-страницы, фото, исходные артефакты | Проверенный локальный файл/метаданные по хэшу и принадлежности семье | Первый доступ, неполный кеш, новая редакция или отзыв права | Манифест и кеш книги уже выпущены; локальная фикстура даёт 240 → 1 документ, но фактическая экономия оплаченных чтений проекта не измерена |
| Календарь и закрытые дни | Последний локальный снимок с временем сверки | Изменение дня/семьи или ограниченная фоновая сверка при входе | Несколько экранов создают перекрывающиеся потоки |
| Текущие задания, фото, проверки, оценки, доступ | Локальный снимок с явной свежестью; детский черновик сохраняется первым | Узкая подписка на активно открытый набор или сигнал изменения | Широкие коллекции и все связанные дни/тесты открываются заранее |
| Открытый тест и отправка фото | Долговечный IndexedDB outbox; отдельно показывать локальное и серверное подтверждение | Отправка/проверка только нужной попытки | Query cache не заменяет гарантию сохранения ответа и идемпотентность записи |
| Операторские очереди EducationSync | Локальный курсор/отпечаток процесса | Новые или изменённые активные события; редкий явный полный аудит | Повторные широкие сканы `operatorSyncJobs`, фото и семейных книг |

**Граница возможности.** После долгого офлайна нельзя знать о перемене на другом устройстве и одновременно совсем не обращаться к серверу без какого-либо внешнего сигнала. Выбираем по типу данных: живую узкую подписку, фоновую проверку по времени, компактный указатель изменения или неизменяемый объект по хэшу. Универсальный `head → delta` не следует из этой границы автоматически.

## Варианты и достижение цели

| Вариант | Где действительно помогает | Что сам не решает и цена внедрения | Вывод для текущего кода |
|---|---|---|---|
| **Firestore persistent cache + узкие общие listeners** | Сразу отдаёт кешированный снимок, поддерживает офлайн чтение и синхронизацию записей; не меняет модель Firestore | Широкий listener всё ещё читает свой первый набор и переподключается; кеш на устройстве переживает сессию, поэтому нужны очистка и проверка смены роли | Первый клиентский кандидат, но сначала проверить приватность на общем устройстве и два окна. Убрать ненужные потоки параллельно |
| **TanStack Query + IndexedDB persister** | Даёт явные `staleTime`, dedup, контролируемую повторную проверку и реактивный UI для разовых чтений | По умолчанию данные сразу stale и refetch на mount/focus/reconnect; сам не сжимает оплаченные документы и не заменяет Firestore listener или долговечный outbox. Появляется второй кеш | Пилотировать на **одном разовом редко меняющемся пути**, если ручная политика кеша сложна; не оборачивать все live-подписки механически. [Important Defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults), [Persist Query Client](https://tanstack.com/query/latest/docs/framework/react/plugins/persistQueryClient) |
| **Свой тонкий repository + текущая IndexedDB** | Управление ключами семьи/роли, временем сверки, атомарным локальным сохранением и нужными подписками без нового движка | Нужно поддерживать транзакции, реактивность и миграции; легко разрастись в самописную базу | Подходит для первых изолированных горячих путей; ограничить интерфейс и проверять сложность |
| **Dexie поверх IndexedDB** | Упрощает транзакции и реактивные локальные запросы, в том числе между вкладками. [Dexie liveQuery](https://dexie.org/docs/liveQuery%28%29) | Не меняет стоимость Firestore; требует перевести локальные записи и проверить Safari/права | Брать, когда нормализованный локальный слой действительно выходит за несколько простых кешей; сравнить с тонким repository на одном маршруте |
| **RxDB + Firestore replication** | Полная локальная реактивная база и двусторонняя репликация. [RxDB Firestore](https://rxdb.info/replication-firestore.html) | Существующим Firestore-документам/внешним публикаторам нужны поля и правила репликации; широкая миграция, начальная репликация и конфликтная логика | Пока не выбирать для работающего приложения; польза не доказана на его текущих коллекциях |
| **Компактный указатель, materialized view, позже дельты** | Может заменить повторное чтение многих редко меняющихся документов одной проверкой; адресная сводка сокращает fanout | Дополнительные записи, миграции, обеспечение атомарности и ролевой приватности; для одного изменившегося документа указатель+тело может стоить дороже | Вводить **только в конкретный путь**, если после кеша/ленивой загрузки метрики показывают повторные платные чтения и расчёт выигрыша положителен |

TanStack Query отвечает за жизненный цикл запросов и UI-кеш; Dexie — за удобную локальную БД; Firestore SDK — за серверные слушатели и собственный офлайн кеш. Их нельзя сравнивать как полные взаимозаменяемые системы. Две независимые локальные копии приватных данных без единого владельца и очистки при смене роли создадут риск рассинхронизации.

## Порядок работы и проверка выбора

1. **База измерения.** Отдельно снять фон без открытых вкладок, холодный и повторный вход одного родителя, переход по дням, открытие книги, один тест, один `EducationSync`. Записать `QUERY`/`LOOKUP`, Usage/Query Insights по коллекциям, listeners, время до первого локального и свежего экрана. Для конкретного серверного запроса использовать [Query Explain](https://firebase.google.com/docs/firestore/query-explain); он не измеряет стоимость живого listener.
2. **Устранить ненужные чтения.** Лениво монтировать детали детей/библиотеку/доступ, делить одно семейное inbox, ограничить историю тестов, не держать назначенные страницы как отдельные живые listeners, заменить регулярные глобальные обходы очередей адресным активным индексом. Для книги сравнить уже созданный кеш с компактным манифестом, сохранив прежний путь на время перехода.
3. **Local-first без новой серверной схемы.** На одном маршруте сравнить Firestore persistent cache с текущим поведением. Сначала показать кешированный снимок, потом статус серверной сверки; проверить родителя/ученика на одном устройстве, отзыв роли, отсутствие сети, две вкладки и старую открытую попытку. Для редко меняющегося разового чтения отдельно проверить TanStack Query persisted cache с заданным `staleTime`, `gcTime`, ключом `family/role/person`, адресной инвалидацией и очисткой при отзыве доступа.
4. **Решение по фактическому остатку.** Если основные платные чтения остались из-за широких первоначальных снимков, выбрать минимальную форму сигнала/сводки для конкретной коллекции. Полный пакетный delta-протокол нужен лишь если число изменяемых сущностей и повторное чтение тел оправдают его сложность. Для однодокументного календаря сравнение пилота уже показало случай 1 старое чтение против 2 новых после изменения; это синтетический тест, не продакшен-замер.

**Критерий выпуска:** снижение оплаченных чтений на одинаковом сценарии подтверждено живыми метриками; открытый тест и фото сохраняются при сбое; роли не смешиваются; старые клиенты продолжают читать v1; интерфейс получает изменение без перезагрузки там, где это требуется. Не выбирать библиотеку и не выпускать новую схему только по числу строк кода или по синтетическому тесту.

Первичные источники: [Firebase offline persistence](https://firebase.google.com/docs/firestore/manage-data/enable-offline), [Firebase billing](https://firebase.google.com/docs/firestore/pricing), [Firebase Query Explain](https://firebase.google.com/docs/firestore/query-explain), [TanStack Query defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults), [TanStack persistence](https://tanstack.com/query/latest/docs/framework/react/plugins/persistQueryClient), [Dexie liveQuery](https://dexie.org/docs/liveQuery%28%29), [RxDB Firestore replication](https://rxdb.info/replication-firestore.html). Выводы о приоритетах — наша оценка текущего кода и исторических метрик, а не утверждение авторов этих библиотек. Реальное снижение затрат ещё не измерено.
