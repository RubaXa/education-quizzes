# Продление связанного клиента mos.ru до SSO-запасного пути

## Основание

При расследовании отказа нового входа обнаружена ошибочная прежняя правка:
refresh_token был объявлен основным по общему OAuth-предположению. Первичный
README и token.js используемой mesh-diary описывают особый связанный клиент
mos.ru: client_credentials не зависит от SSO-сессии, refresh_token — запасной.
Источник: https://github.com/voenniy/mesh-diary#авто-обновление-токена .

## Было → стало

`packages/education-connect/lib/mesh.mjs` снова пробует client_credentials первым,
затем refresh_token при доступном запасном маркере и неуспехе основного. При
invalid_client прекращает запросы: та же аннулированная пара не исправляется
сменой grant. Ошибки регистрации, продления и сети сохраняют точную классификацию.
Если основной источник упал по сети/503, а запасной SSO-грант истёк, сетевой сбой
не превращается в требование нового входа. Активация, сохранение и retry чтения
остаются прежними.

## Действия и роли

Нет новых разрешений, регистрации устройств или использования чужих credentials.
Применяется только сохранённая проверенная пара текущего аккаунта под его lock.
Токен не сохраняется при отказе; старый refresh не расходуется при успехе основного
grant. Новое подключение с400access_denied на этапе регистрации не считается
исправленным этой правкой. Учебные данные и зачёты не меняются.

## Проверки

Проверены успешный основной путь без вызова истёкшего SSO refresh, запасной путь
с ротацией, invalid_client без лишней попытки,503плюс истёкший запасной grant,
сохранение точной безопасной диагностики и отсутствие записи при отказе.
Реальная регистрационная проба отдельно требует согласия, так как создаёт
внешнее OAuth-состояние; тесты используют фикстуры.

## Согласование

Продолжается прямое поручение родителя01.11 исправить недоступность и ошибки
инструментов. Прежнее изменение refresh-first было ошибкой реализации, а не
предпочтением пользователя. Точечный возврат контракта не расширяет полномочия.
